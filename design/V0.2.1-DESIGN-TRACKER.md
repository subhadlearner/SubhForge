## 0. Purpose, scope and tenets

**Objective.** Build an opinionated, reliable and cost-conscious Kilo + VS Code workflow for Subhadeep's own serious projects (MFHistory, Arthabeacon, subhbrain and similar). It must cover the path from idea to verified implementation, including projects that run for weeks or months. v0.2 evolves Stable v0.1. It is not a platform.

**Scope rule.** Every capability must pass one test: *does it materially help design, build, verify or resume my own projects?* If the answer is unclear, the capability is not added.

- **Prefer:** Kilo-native capabilities, simple and explicit solutions, Markdown/Git, deterministic behaviour, human-controlled decisions and measurable gains.
- **Avoid:** building for hypothetical users, provider abstraction, plugin frameworks, extensibility-first design, solving problems we haven't met, and platform-building.

**Tenets (✅).**
1. Personal workflow first.
2. Reconciliation is first-class.
3. Correct decomposition matters more than scheduling.
4. Canonical ordering is advisory only.
5. `/implement SPEC-*` is the minimum reliable delivery path.
6. Humans choose what runs and when.
7. Foundations and cost controls are front-loaded.
8. Reuse the v0.1 machinery and extend it minimally.
9. Handoffs harden through use.
10. Spend complexity only where it reduces real risk.

> **Kilo makes Subhadeep's decisions safer, clearer and cheaper to execute. It does not replace him as project manager.**

**Command-on-demand (✅).** Kilo acts only when explicitly invoked. It creates artifacts, produces the canonical order, reconciles, implements, verifies and reviews only on request. It never self-starts or schedules work. *A dependency is information and a constraint, never permission to act.*

**Completion rule (✅).** A settled decision is reopened only for a contradiction, an implementation limitation, new evidence or a genuine workflow problem.

## 1. Global rules

### 1.1 Standing Safety Principle (✅)

When Kilo cannot confidently classify an authority owner, dependency, impact, reconciliation conflict, lifecycle transition or other workflow-significant ambiguity, it must not guess. It stops that decision path and returns `HUMAN_DECISION_REQUIRED`, naming the exact ambiguity and the concrete choices. `HUMAN_DECISION_REQUIRED` is the **single shared global stop token**. No command aliases or specializes it.

### 1.2 Mode discovery 🆕

A project is **LARGE** if and only if `docs/project/PROJECT-001.md` exists. Otherwise it is **STANDARD**.

- The mode is never re-specified per command.
- `/project-init` echoes the mode into the project `AGENTS.md` for human visibility only; that copy is not authoritative.
- STANDARD keeps v0.1 behaviour and v0.1 artifact formats. The artifact schema and lifecycle in §2 apply to LARGE only.

### 1.3 Output conventions

- **✅ Final token rule:** a command's final status token is its last line. Consumers compare the whole token and never infer meaning from a suffix.
- **✅ Blocked Output Contract:** reuse the v0.1 shape — *Blocking issue · Owner · Why it blocks · Required action · Next command* — followed by the final token.
  - Owner vocabulary 🆕: the v0.1 values (`PRODUCT`, `ARCHITECTURE`, `PROJECT_INIT`, `SPECIFICATION`, `REPOSITORY`, `USER_APPROVAL`) plus `DISCOVERY`, `EPIC` and `FEATURE`. This extends the existing vocabulary; it is not a new enum.
- **✅ Persistence-before-result:** a result is returned only after every authoritative mutation that makes it truthful has persisted. Otherwise the command returns `PERSISTENCE_FAILURE`.
- **Shared diagnostics (✅, never collapsed):**
  - `INVALID_LIFECYCLE_TRANSITION`: the transition table forbids it.
  - `PERSISTENCE_FAILURE`: a required authoritative write could not be established.
  - `LIFECYCLE_INTEGRITY_FAILURE`: parseable artifacts form a contradictory lifecycle combination.
  - `AUTHORITATIVE_ARTIFACT_INVALID`: an artifact is malformed or truncated.
  - `ARTIFACT_NOT_FOUND`, `DUPLICATE_ARTIFACT_ID`, `ARTIFACT_IDENTITY_MISMATCH`.
  - `CONTEXT_CEILING_EXCEEDED`.
  - Non-failure signals: `SPEC_CONTEXT_PRESSURE` and `DEPENDENCY_GAP` (a finding that is repaired, not a stop).
- **Visible side effects (✅):** parent lifecycle transitions and integrity repairs are always printed, for example:
  ```text
  Parent Lifecycle Transition: EPIC-003  READY_FOR_FEATURE_DECOMPOSITION → ACTIVE  Trigger: first durable Feature created
  ```

### 1.4 Resume 🆕

- There is no `/continue` or `/resume` command.
- **Resume means re-invoking the owning command on the same target**, for example `/implement SPEC-014` or `/feature FEATURE-003`. This replaces the tracker's "`/continue` or equivalent" wording in Point 04.8.
- Resume is always reconstructed from current authoritative state (§8.3). It restores position, never permission.

## 2. Artifact model (LARGE)

### 2.1 Identity (✅)

- **ID format:** `<TYPE>-<SEQ>` with `TYPE ∈ {PROJECT, EPIC, FEATURE, SPEC}`, a zero-padded sequence of at least 3 digits, validated by `^(PROJECT|EPIC|FEATURE|SPEC)-[0-9]{3,}$`.
- **Stability:** IDs are uppercase, immutable, and never encode hierarchy or title.
- **Allocation:** sequences are independent per type. Allocation is `max(existing)+1` computed from Markdown/Git. IDs are never reused; gaps are harmless.
- **Consumption:** an ID is consumed once it enters durable history. A never-persisted, discarded draft consumes nothing.
- **Scope:** IDs are unique per project repository only. There are no UUIDs and no cross-project references.
- **Singleton:** the Project is always `PROJECT-001`.

**Record IDs 🆕.** The same monotonic rule applies to `REC-###` (reconciliation), `ESC-###` (escalation), `BLK-###` (blocker), `VERIFY-<ID>-###` (verification, v0.1 naming) and `ACCEPT-<ID>-###` (human acceptance). Obligations are namespaced inside their package, for example `REC-004/OBL-002`.

### 2.2 Front matter (✅ fields, 🆕 `exemptions`)

The front matter is flat YAML in this canonical order:

```yaml
id: SPEC-014
type: SPEC                 # PROJECT | EPIC | FEATURE | SPEC  (never inferred from path)
title: Checkout order submission
state: READY_FOR_IMPLEMENTATION
created_at: 2026-09-26T10:00:00+05:30   # RFC3339 with timezone
updated_at: 2026-09-26T12:00:00+05:30
parent_id: FEATURE-003     # null only for PROJECT
resume_state: null         # PROJECT only
depends_on: [SPEC-011#CreateOrderContract]   # always present, [] when none
governed_by: [ADR-007]                         # always present, [] when none
exemptions: [{authority: ADR-004, authorized_by: ADR-009}]   # 🆕 optional; omitted when none
```

**Field rules (✅).**
- `updated_at` changes only on authoritative semantic or metadata change: state, dependencies, governance, contract, acceptance criteria, scope or title.
- A title rename bumps `updated_at` but is not material.
- Children are never persisted; they are derived from `parent_id`.
- 🆕 **Format rule (TODO-2):** `depends_on`, `governed_by` and `exemptions` are **single-line flow-style lists** (`depends_on: [A, B#X]`; `exemptions: [{authority: ADR-004, authorized_by: ADR-009}]`). One-line lists are what make the anchored `git grep` lookups in §6.5 exact. A multi-line list returns `AUTHORITATIVE_ARTIFACT_INVALID`.
- There is no `blocked`, `verification_status`, `reconciliation_status`, `owner`, `priority`, `progress`, `*_at` stage timestamp or state history.

**`exemptions` 🆕.** This is the physical form of Point 02.6's `Exempted from` / `Authorized by`. Absence is never interpreted as exemption, so the field may be omitted when empty; `depends_on` and `governed_by` must stay present because an empty list means "audited, none".

### 2.3 Reference format 🆕

References take the form `<SOURCE-ID>[#<anchor>]`.

- **Source IDs** are the artifact IDs plus the v0.1 documents: `PRD-###` (`docs/prd/`), `ARCH-###` (`docs/architecture/`) and `ADR-###` (`docs/adr/`).
- **Anchors** are stable in-document identifiers: `FR-n` (PRD), `AC-n` (acceptance criteria in Features and Specs), or a named contract heading (`#CreateOrderContract`).
- **Claims** are the unit of verification. A claim is `(artifact_id, AC-n)` at **every level**. There is one identity rule and one sidecar format. 🆕 The claim IDs are:
  - **`AC-1…n` (Spec, Feature, Epic):** acceptance criteria proven by `/verify` evidence. For an **Epic**, each Verification Intent journey *is* an acceptance criterion and is written as `AC-n: Journey — <start> → <outcome>` (happy path and negative paths are separate ACs).
  - **`AC-0` (Feature, Epic only):** reserved for the Human-Evaluable Capability or Outcome statement itself. Only an `ACCEPT-<ID>-###` record can prove it; `/verify` never does.
  - **Stability:** AC IDs follow the artifact-ID rules — they are immutable and never renumbered or reused. A removed AC keeps its number as retired, and a new AC takes the next number, so evidence associations never point at the wrong claim.

**Pending dependency** (answers Point 02.3, which the tracker deferred to 05 but 05 never defined):
- Form: `depends_on: [PENDING:FEATURE-007:CreateOrderContract]`.
- Detail lives in a body section `## Pending Dependencies` (required contract, why it is needed, expected owner).
- The pending entry **is** the tracked grooming obligation, linked to the owner's scope by the owner ID inside it. There is one record (on the consumer), so there is no second copy that could drift.
- **Owner must exist.** The owner ID must name an existing artifact that is not RETIRED.
  - If the natural owner hasn't been authored yet, name the nearest existing scope that will create it: the parent Feature for a future Spec, or the parent Epic for a future Feature. That scope's command then owes the creation.
  - If the owner is unknown, or is RETIRED, return `HUMAN_DECISION_REQUIRED`.
- **Owner-side processing is mandatory 🆕** (this makes the obligation actionable, as Point 02.3 required):
  1. **Surface.** Every invocation of the owner's command (`/epic`, `/feature` or `/spec` on the owner ID), including gate evaluation and `complete`, runs the reverse lookup `PENDING:<owner-id>:*`. It prints an **Owed Contracts** section in its output, listing each consumer, the contract and its current disposition. An empty result is printed as `Owed Contracts: none`, so a skipped lookup can be seen as a defect.
  2. **Process.** For each owed contract, the owner command must take one of these actions and persist it:
     - (a) **Provide:** the contract lands as a named, anchored heading in the owner's scope (or the owner creates the child that will provide it). This follows normal grooming, including the §2.5 material-change rules.
     - (b) **Route as scope change:** the contract is outside the owner's accepted scope, or the owner is COMPLETE (which never reopens). The owner routes it to `/shouldreconcile`, or to new work in another scope, and writes a BLK record referencing both artifacts.
     - (c) **Reject ownership:** the owner is not the right place for the contract. The owner writes an ESC record (`HUMAN_DECISION_REQUIRED`) to reassign it.
  3. **Gate.** The owner cannot pass its READY gate, or reach COMPLETE, while an owed contract has no action a/b/c recorded (§10.2, §11.4).
- **Closing the loop.** Once the contract becomes consumable (§4.4), the owner's output lists the consumers that are now unblocked. The consumer's next command invocation replaces the entry with the real reference and reruns its local audit. `/status` lists every open `PENDING:` entry grouped by owner (§8.6), so nothing stays invisible between invocations.

### 2.4 Lifecycle states and transitions (✅)

| Type | States | Allowed transitions |
|---|---|---|
| Project | DISCOVERY, PLANNING, ACTIVE, MAINTENANCE, PAUSED, COMPLETE, RETIRED | DISCOVERY→{PLANNING,PAUSED,RETIRED}; PLANNING→{ACTIVE,PAUSED,RETIRED}; ACTIVE→{MAINTENANCE,COMPLETE,PAUSED,RETIRED}; MAINTENANCE→{ACTIVE,COMPLETE,PAUSED,RETIRED}; PAUSED→{resume_state,RETIRED}; COMPLETE→{RETIRED} |
| Epic | DRAFT, GROOMING, READY_FOR_FEATURE_DECOMPOSITION, ACTIVE, COMPLETE, RETIRED | DRAFT→{GROOMING,RETIRED}; GROOMING→{READY_*,RETIRED}; READY_*→{ACTIVE,RETIRED}; ACTIVE→{COMPLETE,RETIRED}; COMPLETE→{RETIRED} |
| Feature | DRAFT, GROOMING, READY_FOR_SPEC, ACTIVE, COMPLETE, RETIRED | same shape as Epic |
| Spec | DRAFT, READY_FOR_IMPLEMENTATION, ACTIVE, COMPLETE, RETIRED | DRAFT→{READY_FOR_IMPLEMENTATION,RETIRED}; READY→{ACTIVE,RETIRED}; ACTIVE→{COMPLETE,RETIRED}; COMPLETE→{RETIRED} |

`RETIRED` is the only terminal state and has no outgoing transitions.

**Invariants (✅).**
- **Excluded states:** there are no BLOCKED, RECONCILING, VERIFYING, VERIFIED, FAILED, DECISION_REQUIRED or PLANNED states. Blockage, reconciliation and verification are overlays.
- **No backward moves:** GROOMING→DRAFT is forbidden, and COMPLETE never reopens. The only backward-looking transitions are the Project's MAINTENANCE→ACTIVE and PAUSED→resume_state. New work becomes a new artifact; small fixes use maintenance.
- **Transition validity:** a transition needs an allowed edge, a satisfied guard and a successful persist. It is atomic together with its related metadata (for example `state: PAUSED` plus `resume_state`). It bumps `updated_at`. Git is the only history.
- **Illegal transitions** return `INVALID_LIFECYCLE_TRANSITION` with current, requested and allowed states and a reason.
- **Retirement** is always explicit and human-requested, never inferred from age or inactivity.
- **Ambiguity:** a Spec ambiguity discovered during `/implement` leaves the Spec in its state and creates an escalation record.

**Transition triggers 🆕 (the tracker left who and when open):**

| Transition | Performed by | Trigger / guard |
|---|---|---|
| (create) Project → DISCOVERY | `/ideate` | first persisted ideation session |
| Project DISCOVERY → PLANNING | `/ideate` | on `IDEATION_READY_FOR_PRD` |
| Project PLANNING → ACTIVE | `/project-init` | on `PROJECT_INIT_READY` (PRD + architecture + repo baseline settled) |
| Project MAINTENANCE → ACTIVE | `/epic` | an Epic reaches `READY_FOR_FEATURE_DECOMPOSITION` while the Project is in MAINTENANCE |
| Project → MAINTENANCE / COMPLETE / PAUSED / RETIRED, and PAUSED → resume | **developer edits `PROJECT-001` front matter directly** | rare human-owned acts; every command validates Project state and `resume_state` consistency on read (`AUTHORITATIVE_ARTIFACT_INVALID` if inconsistent) |
| Epic/Feature (create) → DRAFT | owning command, or a parent decomposition | intent only |
| DRAFT → GROOMING | `/epic`, `/feature` | the owning command begins grooming |
| GROOMING → READY_* | `/epic`, `/feature` | readiness gate (§10) passes |
| Spec DRAFT → READY_FOR_IMPLEMENTATION | `/spec` | Spec gate passes |
| Epic READY → ACTIVE | `/feature` | first durable child Feature (✅) |
| Feature READY → ACTIVE | `/spec` | first durable child Spec (✅) |
| Spec READY → ACTIVE | `/implement` | prerequisites validated and execution admitted (✅) |
| Spec ACTIVE → COMPLETE | `/review` | final decision `APPROVE` with the **effective delivery gate** (§11.1) `CLEAR` or `CLEAR_WITH_EXCEPTION` — which includes Contract v1 `MATCH` — and no OPEN ESC/BLK/REC obligation referencing the Spec (matches the v0.1 Definition of Done; CI/PR stays the human workflow) |
| Feature/Epic ACTIVE → COMPLETE | `/feature <ID> complete`, `/epic <ID> complete` | §11.4 guard, including the recorded human acceptance |
| any → RETIRED | `<owning command> <ID> retire` | refused while non-RETIRED artifacts `depends_on` it, unless done under a REC `RETIRE_REQUIRED` obligation whose dependents were assessed |

**Project state preconditions 🆕.**
- `/epic` requires the Project to be ACTIVE or MAINTENANCE.
- In PAUSED, COMPLETE or RETIRED, every mutating LARGE command stops with its `*_BLOCKED` token (owner `USER_APPROVAL`). The Project state is the durable record, so no BLK record is written.
- Read-only `/status` always works.

### 2.5 Material change (✅)

A change is **material** when it alters what an artifact means, requires, promises, constrains, depends on or must prove. That includes requirements, behaviour, contracts, acceptance criteria, scope, `parent_id`, `depends_on`, `governed_by`, `exemptions` and authoritative assumptions. Spelling, formatting and meaning-preserving wording are editorial.

The effect depends on the artifact's state:
- **Mutable artifact:** rerun its local dependency audit and gate, and re-evaluate declared dependents. There is no repository-wide scan.
- **READY_* artifact:** it is not demoted. Reliance on the old gate is suspended until the gate reruns. A pass keeps it ready. A fail blocks downstream work; this is a workflow block, not a state change.
- **COMPLETE artifact, or accepted authority:** only through `/shouldreconcile` → `/reconcile`.
- **Uncertain materiality:** `HUMAN_DECISION_REQUIRED`.

*`updated_at` changed ≠ material ≠ reconciliation required.*

### 2.6 Completion (✅)

- Completion is never inferred or automatic. It is evaluated when requested and never persisted as a flag.
- **Hard floor:** an Epic or Feature cannot reach COMPLETE while any non-RETIRED child is not COMPLETE. Children are derived from `parent_id`.
- The floor is necessary but not sufficient. Each level also has its own criteria (§11).
- The Project is a human judgement and is not derived from its Epics.

### 2.7 Records (✅ patterns, 🆕 locations and shapes)

All records reference artifacts. Artifacts never reference records back.

| Record | Path | Mutability | Status |
|---|---|---|---|
| Reconciliation package | `docs/workflow/reconciliation/REC-###.md` | mutable | package `ASSESSING→OPEN→CLOSED` (or `ASSESSING→CLOSED`); obligations `OPEN|RESOLVED|SUPERSEDED` |
| Escalation 🆕 | `docs/workflow/escalations/ESC-###.md` | mutable status, immutable body | `OPEN|RESOLVED|SUPERSEDED` |
| Blocker 🆕 | `docs/workflow/blockers/BLK-###.md` | mutable status | `OPEN|RESOLVED|SUPERSEDED` |
| Verification report | `docs/verification/VERIFY-<ID>-###.md` | immutable (v0.1) | result `DONE|NOT_DONE`, report gate `CLEAR|BLOCKED` (the effective gate is derived; see §11.1) |
| Human acceptance 🆕 | `docs/verification/ACCEPT-<ID>-###.md` | immutable | `ACCEPTED|REJECTED`; when `ACCEPTED` it proves claim `AC-0` and gets a sidecar like any report |
| Applicability sidecar | `docs/verification/applicability/<report-name>.md` | mutable | per claim `APPLICABLE|INAPPLICABLE|SUPERSEDED` (+ `reason`, `superseded_by`) |
| Waiver | `docs/verification/waivers/` | v0.1 | v0.1; a valid, unexpired waiver makes the *effective* gate `CLEAR_WITH_EXCEPTION` (§11.1) |

**Escalation and blocker are distinct (✅).**
- **ESC** records an unresolved *decision*. Its body follows the §7.4 envelope plus `origin`, `blocking_scope`, `resolution_ref` (a link to the owning artifact where the answer was promoted) and a short historical resolution summary.
- **BLK** records an unavailable *prerequisite, evidence, access or authority*. It holds: affected artifact, condition, what is missing, discovered-at, responsible owner, unblock-check condition, and status.
- Neither is ever authority. Current truth lives in the owning artifact (§7.5).

## 3. Authority & reconciliation (✅ Point 01, 🆕 operational details)

### 3.1 Principles

- Completed artifacts are immutable during normal work.
- Reconciliation happens only by explicit human initiation.
- Ordinary implementation changes that stay within accepted authority never trigger it.

### 3.2 `/shouldreconcile`

- **Input:** a proposed *delta* (old decision → new decision). A bare artifact ID is not enough.
- **Output:** a classifier result — `SHOULDRECONCILE`, `NORECONCILENEEDED` (with a route to the normal owning command, `/implement` or `/fix`), or `HUMAN_DECISION_REQUIRED`.
- **Persistence 🆕:** it writes nothing. `/reconcile` re-derives the classification itself (the next rule), so no pre-reconciliation state is needed.

### 3.3 `/reconcile` algorithm (✅, with 🆕 marks)

Precondition 🆕: explicit human authorization *and* the accepted new decision. **A new run** (no existing package for this delta) re-validates `SHOULDRECONCILE` at start and refuses on `NORECONCILENEEDED`. **A resumed run** (`/reconcile REC-###`, or a new invocation whose delta matches an `ASSESSING` package) never re-classifies. Its authority is the recorded delta and authorization (see *Crash safety* below).

1. **Locate the authority root(s)** by artifact semantics. If ambiguous, return `HUMAN_DECISION_REQUIRED` with an ESC record and no package.
2. **Compute the candidate closure once** with `kilo_graph closure <ROOT>` (§6.5), deterministically, from persisted `parent_id`, `depends_on`, `governed_by` and effective governance. Semantic search never builds the graph. The closure is found by following *other artifacts'* edges back to the root, so editing the root in step 4 cannot change it. If the root edit changes the root's own relationship metadata, that structural delta is picked up in step 7. If the helper reports `blocked` (for example `DUPLICATE_ARTIFACT_ID`), stop before step 3 with that integrity diagnostic. No package is created, and the repository must be repaired first.
3. **Create `REC-###` in `ASSESSING` in a single write, before any authority is edited.** It records:
   - the accepted delta (old → new decision, verbatim) and the human authorization;
   - the root ID(s), each with its **pre-edit fingerprint** (§5.4);
   - 🆕 the **closure list** as an audit snapshot and resume anchor. This is the Point 01 decision that Point 06.7 deferred.
4. **Revise the root minimally** in `RECONCILE_ONLY` mode, then persist its `REVISED` disposition with its post-edit fingerprint. This step is idempotent (see *Crash safety*).
5. **Classify each candidate against its effective incoming delta** (§3.5), reading the full candidate artifact. Persist each disposition as it is made.
6. **Record obligations:**
   - `NEW_WORK_REQUIRED` goes to normal grooming and is never authored here.
   - `RETIRE_REQUIRED` preserves history and never mutates state here.
   - `DECISION_REQUIRED` blocks that path only.
   - `REVERIFY` flips affected applicability to `INAPPLICABLE`.
7. **Run one bounded consistency scan** for stale references and undeclared coupling. Repair any `DEPENDENCY_GAP` in metadata and assess its impact once.
8. **Finish:** `CLOSED` if no obligation is OPEN, otherwise `OPEN`.

Reconciliation does not wait for implementation, grooming, retirement or reverification. Work that depends on an OPEN obligation cannot be claimed complete.

**Batched reconciliation 🆕 (a legitimate wide blast radius, not an oversized accident).** A cross-cutting change (e.g. a foundational ADR) can produce a closure with no semantically valid way to shrink it. `CONTEXT_CEILING_EXCEEDED` in this case is not "reduce scope" — it is a signal to spread step 5 across multiple human-initiated invocations of the same package.

- **The closure is computed once, at step 2, and frozen for the life of the package.** It is never recomputed mid-sequence. If an out-of-band material change to the graph (a new edge, a retirement, another accepted delta) is detected while a package still has unclassified candidates, that is a moving-target conflict: the package **stays `ASSESSING`**, the affected path's disposition is persisted as `DECISION_REQUIRED` (§3.4) with an ESC record (§3.7's overlap rule), and reconciliation does not silently reshape the remaining batches around it. The package only reaches `OPEN`/`CLOSED` (§3.3 step 8) once every candidate — including that path, after its `DECISION_REQUIRED` obligation resolves — has a disposition.
- Step 5 partitions the frozen closure into batches by natural boundary (e.g. subtree under a root, or artifact type) that respect the 100k ceiling per invocation — never an arbitrary fixed count.
- Each invocation persists exactly which candidates it classified and their dispositions before returning. `RECONCILE_INCOMPLETE` covers this case as well as a crash: resuming re-reads the package, skips already-dispositioned candidates (as in *Crash safety* below), and classifies the next batch.
- `RECONCILE_OPEN` / `RECONCILE_CLOSED` are only reachable once every candidate in the frozen closure has a disposition — a package cannot close with unclassified candidates remaining, batched or not.

**Crash safety 🆕.** Every step either writes its result into the package or is safe to redo, so an interrupted run always resumes from the package and never from chat.

- **Crash before step 3:** there is no package and no authority has been edited. Re-invoking starts a fresh run, and the fresh classification is valid because nothing has changed.
- **Resume a package in `ASSESSING`:** load the recorded delta, roots, fingerprints and closure, and do not re-classify. The package is the proof that the human authorized this delta.
- **Root step, idempotent.** For each root with no persisted disposition, compare its current state with what the package recorded:

  | Root now | Action |
  |---|---|
  | fingerprint = recorded pre-edit fingerprint | untouched; apply the minimal edit (step 4) |
  | already expresses the recorded *new* decision, and the diff from pre-edit is limited to that delta | the edit landed before the crash; persist `REVISED` + post-edit fingerprint without re-editing |
  | anything else (a third-party change, a partial or different edit, or a semantic check that is uncertain) | do not replay a stale patch; mark the root path `DECISION_REQUIRED` and write an ESC record (§3.7) |

  Git provides the pre-edit content for the diff check (the working tree against `HEAD`, or the commit that holds the pre-edit fingerprint's blob). If the pre-edit content can't be recovered, the root falls into the "anything else" case.
- **Candidate steps (5–7):** candidates that already have a persisted disposition are skipped. Unassessed candidates are classified against the *current* artifact. The same three-way root check applies to a candidate whose `REVISED` edit may have landed without its disposition being persisted, compared against the package's recorded delta for that path.
- **Duplicate run guard:** a new `/reconcile` whose delta matches an existing `ASSESSING` package resumes that package rather than creating a second one. A partial match (overlapping but not identical delta) returns `HUMAN_DECISION_REQUIRED`, per the overlap rules (§3.7).

### 3.4 Dispositions (✅, per package, never an artifact state)

| Disposition | Meaning |
|---|---|
| `UNCHANGED` | Still truthful as written. |
| `REVISED` | Minimal edit made; records the semantic delta. |
| `DECISION_REQUIRED` | The path is suspended. |
| `RETIRE_REQUIRED` | The artifact is obsolete. |

The `RECONCILE_ONLY` result `CHANGED` maps to `REVISED`, and `HUMAN_DECISION_REQUIRED` maps to `DECISION_REQUIRED`.

### 3.5 Propagation (✅)

- A `REVISED` artifact passes on only its *effective* delta. `UNCHANGED` passes nothing along that path, although a candidate reachable through another changed path is still assessed.
- Compatible incoming effects combine into one disposition. Conflicting effects return `HUMAN_DECISION_REQUIRED`.
- `NEW_WORK_REQUIRED` never expands the graph.
- **Premise test (Point 02.7):** a change propagates across an edge only if the effective delta changes the premise that edge represents. Uncertain cases propagate as a candidate; candidate status is not impact.

### 3.6 Evidence after reconciliation (✅)

- Applicability is reassessed per **claim association**, never per whole run.
- A changed claim, contract, assumption or acceptance criterion makes that association `INAPPLICABLE`. Editorial changes do not.
- Reconciliation never deletes evidence and never runs tests.
- Uncertain applicability returns `HUMAN_DECISION_REQUIRED`; it is never counted as current.

### 3.7 Overlap (✅)

- Obligations on the same effective work or claim are merged, with links to every originating REC, or superseded by the latest accepted delta.
- Conflicting deltas return `HUMAN_DECISION_REQUIRED`.
- A stale patch is never replayed. On resume, re-read the artifacts and the package.

### 3.8 `RECONCILE_ONLY` mode ⚠ (unifies the v0.1 and v0.2 meanings)

`RECONCILE_ONLY` is one internal planning-worker mode — *minimal targeted edit to an existing artifact against a supplied delta, never re-authoring*. It has two entry sources:

| Source | Supplied by | Scope |
|---|---|---|
| `AUTHORITY_DELTA` | `/reconcile` | The ✅ Point 01 contract: accepted delta, REC ID, artifact and role, reason selected. Output per artifact: `CHANGED | UNCHANGED | HUMAN_DECISION_REQUIRED` + delta/rationale + reference fixes + downstream contracts affected + gaps + obligations. No code, tests or verification claims. Completed artifacts are editable only here. |
| `ADVERSARIAL_FINDINGS` | `/architect`, `/spec`, `/epic`, `/feature` after `/adversarial-check` | The v0.1 contract, unchanged: classify findings (misread / actionable / accepted trade-off / noise), make the smallest edits, and report whether another adversarial pass is justified. Only artifacts not yet COMPLETE; otherwise route through `/shouldreconcile`. |

**The two sources share only the name and the minimal-edit discipline.** Their inputs, allowed targets and allowed edits stay distinct as shown in the table, and neither may use the other's. A missing source returns `WORKER_MODE_REQUIRED` (v0.1 behaviour). Smoke S2 guards the v0.1 path. The mode never self-starts and never expands its own scope.

### 3.9 Obligation resolution 🆕 (the tracker never said who closes obligations)

The command that satisfies an obligation updates that obligation in the REC file. When the last obligation resolves, the same command sets the package to `CLOSED`.

| Obligation | Resolved when | By |
|---|---|---|
| `NEW_WORK_REQUIRED` | the new artifact reaches its READY_* state | `/epic`, `/feature` or `/spec` |
| `RETIRE_REQUIRED` | the artifact becomes RETIRED | owning command `retire` |
| `DECISION_REQUIRED` | the decision is promoted into its owning artifact (§7.5) and the path is re-assessed | `/reconcile REC-###` (resume) |
| `REVERIFY` | fresh `APPLICABLE` evidence exists for the claim | `/verify` (or the acceptance record, §11.4) |

`SUPERSEDED` is set by a later `/reconcile`. A package is never closed from cached counters.

## 4. Dependency & impact model (✅ Point 02)

### 4.1 Relationships

There are exactly three relationship kinds:

- **Contains:** derived from `parent_id` and never authored.
- **Governed by:** reference to an accepted authority such as an ADR, a PRD clause or an Epic policy.
- **Depends on:** reliance on another source's decision, behaviour or contract.

A link makes something a *candidate*, never *impacted* (*candidate ≠ effective impact ≠ disposition*). Test and evidence associations are not dependencies.

### 4.2 Cross-cutting concerns

- Declare Governed by at the highest scope where the policy applies uniformly, and at a narrower scope only where applicability starts there. Descendants inherit through Contains. There is no mirrored `governs` list.
- **Exemption** (§2.2) removes one inherited authority from a subtree.
  - It must carry an `authorized_by` decision that explicitly addresses that override. An unrelated decision at an authority tier is invalid.
  - An exemption that is unauthorized or ambiguous has no effect, and readiness returns `HUMAN_DECISION_REQUIRED`.
  - A descendant re-enters coverage only through an explicit direct Governed by.
  - A change to the authority *or* to the authorizing decision is reconciled normally.

### 4.3 Discovery

- **During authoring:** identify what the artifact actually relies on and record it on the dependent side.
- **At readiness:** run a local audit (parent, declared dependencies, relevant authority). Broaden it only when the local audit shows uncertainty.
- **At lookup:** follow persisted references only. Never infer a dependency from code, prose, naming, proximity, call patterns or intuition.
- **Gaps:** a missing edge found later is recorded as `DEPENDENCY_GAP`, the metadata is repaired, and the impact is reassessed. Dependency completeness is best-effort, and that residual risk is accepted.

### 4.4 Cross-Feature dependencies

- A cross-Feature dependency is an ordinary Depends on, declared at the **lowest level that owns the reliance**.
- It is never auto-promoted and never persisted as a transitive edge. Roll-ups are informational only.
- A later Feature-level invariant is added alongside the existing lower-level edges, not in place of them.
- Dependency order is not implementation order.

**Consumable-contract condition 🆕** (Point 02.5 required Point 05 to define this; Point 05 never did). A consumer may rely on a provider contract when either:
- (a) the provider artifact is at READY_* or later and not RETIRED — Spec READY_FOR_IMPLEMENTATION/ACTIVE/COMPLETE, Feature READY_FOR_SPEC/ACTIVE/COMPLETE — because its gate settled the contract; or
- (b) the contract is settled in accepted authority (PRD, ARCH or ADR).

DRAFT or GROOMING providers are consumed only through a `PENDING:` entry. A RETIRED provider is a `DEPENDENCY_GAP` that blocks readiness.

A consumer can be *implemented* against a consumable contract, but cannot reach COMPLETE while the integration evidence it requires is outstanding (§11).

### 4.5 Cycles

- A cycle is a readiness blocker when it prevents either side from establishing its contract independently.
- Resolve it by checking for a shared or higher authority or a wrong decomposition. If that fails, return `HUMAN_DECISION_REQUIRED`. Never invent an ordering to hide a cycle.
- The cycle check reruns whenever an edge is persisted, including during reconciliation and gap repair. A READY artifact may therefore need its gate re-run.

### 4.6 Structural moves

- Reparenting is a delta. Recompute ancestry and effective governance, then propagate wherever the premises changed.
- **Persist meaning; derive mechanics; reassess when the facts behind the mechanics change.**

### 4.7 Premise test (Point 02.7)

- **Depends on:** propagate on an observable change to the relied-upon behaviour or contract. A refactor, tracing or formatting change does not propagate.
- **Governed by:** propagate only when the enforceable rule or its applicability changes. For example, "OAuth2" → "OAuth2 + PKCE" propagates; rewording the ADR does not.
- **Contains:** propagate structural and governance effects only.

**Validation anchors (✅, reused by smoke L5).**
1. A Spec→Spec contract change propagates to its consumers, but a refactor does not.
2. Reparenting recomputes the effective context.
3. The Governed by → Exempted from → Authorized by chain: revoking the authorization reactivates coverage, while a change to the exempted authority does not reach a validly exempt subtree.

## 5. Context management (✅ Point 03)

**Stage contracts.** Each stage has a mandatory starting set plus pull-based expansion:

| Stage | Mandatory starting context |
|---|---|
| Ideation | Project artifact plus answered/unresolved questions |
| PRD | full ideation (Project) artifact |
| Architecture | full PRD plus the ADR index — the deliberate asymmetry |
| Epic | relevant PRD, ADRs and the Epic |
| Feature | parent Epic, relevant PRD, governance and the Feature |
| Spec | parent Feature, relevant Epic/PRD/ADR, the Spec and its declared or pending dependencies |
| Implement | full Spec, applicable contracts and the relevant code |
| Verify | claims, implementation and evidence context |
| Review | the change, governing requirements and evidence |
| `/shouldreconcile` | the delta, the affected artifact and enough authority to classify |
| `/reconcile` | the delta, root, package and metadata; full candidates as each is assessed |
| Resume | current artifact plus records; never chat history |

**Rules.**

1. **Minimum-sufficient context.** The working artifact is loaded in full. Authority and dependency context are loaded relevance-scoped. Persisted truth always beats conversation.
2. **Agents.**
   - An agent receives its stage context plus a role overlay.
   - Delegation passes intent, IDs, scope and mode, never the caller's expanded context.
   - Fresh or adversarial reviewers get the artifact plus its governing contract, and never the author's reasoning.
   - Context follows authority, not model identity.
3. **Context classes** are conceptual labels only: `MANDATORY_START`, `MANDATORY_ON_DEMAND`, `OPTIONAL` and `EXCLUDED`.
   - Context is mandatory if omitting it could violate authority, contracts, workflow state or acceptance.
   - Mandatory does not mean preloaded.
   - Never guess past missing mandatory context.
4. **Freshness.**
   - Resolve every mandatory source from current authority, including the uncommitted working tree, at assembly time. Freshness is established at assembly, not assumed from the source's age.
   - Each invocation works from a bounded snapshot.
   - 🆕 **Fingerprint = Git blob ID from `git hash-object --no-filters <path>`**. This is the same primitive as Contract v1 and is already permitted in `kilo.jsonc`.
   - 🆕 **Groomed-against provenance:** a `*_CONTINUE` artifact records `Groomed against: <parent-id> @ <parent updated_at>` in its body. The timestamp is a cheap **prompt to compare meaning, not proof of drift**:
     - **Timestamp unchanged:** skip the drift comparison. Editorial edits don't move `updated_at`, so none are missed. Gates still read the *current* parent (§10), so a gate never relies on the timestamp alone.
     - **Timestamp changed:** `updated_at` also moves for non-material metadata such as a title rename (§2.2), so this is *not* evidence of material drift. Compare the parent's recorded content (retrieved from Git at the commit where that `updated_at` was set) with its current content, and classify using §2.5: editorial or title-only → refresh the provenance line and continue; material → apply the §8.4 parent-drift rules; uncertain → `HUMAN_DECISION_REQUIRED`.
     - **Old content can't be retrieved 🆕 (corrected):** never assume there is no drift, and never hard-code which section governs — different artifact types carry the relevant authority in different places (Constraints, Contract Boundaries, Acceptance Criteria, and so on), so a fixed section name could omit mandatory authority and violate rule 1 above. Instead apply rule 6's own bounded-portion discipline here: start with the smallest current authoritative portion(s) that plausibly govern the child's settled decisions, expand progressively per rule 6 if the judgment stays uncertain, and load the full parent only if it does not settle. Uncertain after full-parent comparison → `HUMAN_DECISION_REQUIRED`.
5. **Staleness.**
   - Revalidate fingerprints at meaningful boundaries: before finalizing a result, when pulling on-demand context, on resume, and after out-of-band changes.
   - Invalidate in a targeted way, and judge the semantic change, not the byte change.
   - The agent's own writes are not staleness.
   - Genuine conflict returns `HUMAN_DECISION_REQUIRED`.
   - There are no watchers, TTLs or polling.
6. **Full artifact or bounded portion.**
   - Load in full when judging the whole artifact: the working artifact, the PRD for architecture, reconciliation candidates, and whole-artifact consistency checks.
   - Otherwise use a bounded authoritative portion, expanding progressively (section → wider section → full artifact).
   - A relationship alone never justifies loading, and "full" means that artifact only.
   - *Test: could reading the source change this result?* If not, a reference is enough.
7. **No duplication.**
   - Each decision has one authoritative home.
   - There are no persisted summaries or context caches.
   - Deduplicate by provenance within an invocation; a broader copy replaces a narrower one.
   - Similar text in different artifacts is not deduplicated, and refined child truth is legitimate.
8. **Ceilings ⚠.**
   - 20–40k tokens of Kilo-assembled context is normal. **40k is a pressure threshold, not a cutoff:** above it Kilo keeps going and surfaces the pressure, and it never drops required context to get back under. **100k is the hard ceiling:** above it Kilo returns `CONTEXT_CEILING_EXCEEDED`.
   - `CONTEXT_CEILING_EXCEEDED` names the major contributors. Scope must be reduced; content is never truncated.
   - Spec artifact guidance is 5–15k tokens. `SPEC_CONTEXT_PRESSURE` fires when a Spec is above that or pushes working context over 40k.
   - One policy applies to all commands. Model window size never raises the budget.
   - This replaces v0.1's "30–60k preferred / 60–80k warning" wording in `AGENTS.md` and `spec.md` (§18).
9. **Large-project assembly.**
   - Assemble task-outward: identity → working artifact → minimum authority chain → declared dependencies → execution surface → earned expansion.
   - Phase A builds a deterministic skeleton. Phase B spends semantic effort only where content can change the result.
   - Anti-patterns (never): loading all docs, loading all ancestors, loading all ADRs, preloading siblings, repo-wide semantic retrieval, replaying history, or relying on mega-summaries.
10. **Discovery loop.**
    - State the missing premise first.
    - Look things up deterministically before searching. Search only when the *location* is unknown, and treat results as locators.
    - Chain from one source to the next only when each step earns the next.
    - Discovery reveals gaps; it never creates edges.
    - There is no fixed count limit. Stop when the premise is resolved, the result cannot change, the next step is speculative, the ceiling is reached, or authority conflicts.
11. **Cost.**
    - Cost is a tie-breaker among options that are already correct.
    - Optimize in this order: drop irrelevant context → bounded portions → dedupe → deterministic lookup → right-size the scope → use a cheaper model → accept the cost.
    - Never drop mandatory context for cost.
    - Measure the whole work unit.
12. **Token observability 🆕 (TODO-4 result, checked in the Kilo CLI source).**
    - **Exact usage needs no Kilo-side machinery.** Kilo records usage on every assistant message: `tokens {input, output, reasoning, cache.read, cache.write}` plus `cost`. Subagent cost is propagated to the parent session.
    - Retrieval:
      - `kilo stats [--days N] [--models] [--project ""]` for aggregates;
      - `kilo export <sessionID> [--sanitize]` for per-message JSON;
      - `kilo run --format json` for per-step events.
    - Smoke runs and dogfooding use these for exact figures. The smoke run record stores the session ID of each stage, so the numbers can be pulled afterwards.
    - **Ceiling checks use an estimate.** The 40k/100k rule counts only *Kilo-assembled* context, which platform totals (these include system prompts and tools) cannot isolate. Commands therefore estimate the content they loaded as **characters ÷ 3.5, rounded up**. This is deliberately conservative against Claude tokenizers, which can use up to ~1.35× more tokens than ÷4 suggests. Commands print `Assembled context ≈ Nk tokens (est.)` only when above 40k, or with `CONTEXT_CEILING_EXCEEDED`.
    - Expansion count and tokens added per expansion are listed in the command output only when the pressure signal fires. No always-on logging.

## 6. Persistence & resume (Point 06) — DECIDED (developer, TODO-1): **v0.2 starts with Markdown/Git only**

### 6.1 Decision and what it replaces

- **The Point 06.14 empirical gate was *not* run.** No SQLite trial or measurement exists.
- The developer has **replaced** the old requirement ("trial SQLite before building") with a simpler rule: **build v0.2 on Markdown/Git, and consider SQLite only if measured lookup or resume problems justify it.**
- The measurement is TODO-2, taken on a synthetic large fixture and during dogfooding.
- If SQLite is ever reconsidered, the archived Point 06.1–06.14 design and its evaluation contract (correctness in all four conditions, material benefit, no sunk cost) still apply.

**Supporting reasoning (why skipping the trial is acceptable, not proof of the outcome):**
- For a single-developer repository with at most a few hundred small artifacts, deterministic lookup (front matter, `git grep` for reverse references) should cost the model almost nothing.
- Both approaches must read the same semantic content, and latency differences should be negligible at this scale.
- SQLite would add a schema, targeted refresh, rebuild, recovery, diagnostics and smoke surface.

**Observability tripwire 🆕 (not a discovered ceiling).** The §6.5 POC validated single-hop `git grep` and `kilo_graph` at 200/400 Spec fixtures — that is evidence the mechanisms work at that scale, not a discovered architectural limit, and the tracker should not be read as implying a "400" alarm threshold. What actually matters is measured friction, not a headcount: a project with 800 artifacts and clean relationships may work fine; one with 250 pathological ones may not. So `/status` (§8.6) reports simple artifact counts (Epics/Features/Specs/records) as a standing observability line, and SQLite reconsideration (§6.1) stays triggered only by measured lookup/resume latency, tool-call cost, or other operational friction surfaced during dogfooding — never by artifact count alone.

### 6.2 Rules that remain in force regardless (✅)

1. **Authority invariant.** Delete every non-Markdown/Git file and Kilo must still reconstruct all accepted truth without asking the developer to remember or re-decide anything.
2. **Lookup** resolves ID → path by deterministic search of the canonical directories (§16), then validates front matter `id` and `type`. Integrity failures return `ARTIFACT_NOT_FOUND`, `DUPLICATE_ARTIFACT_ID` or `ARTIFACT_IDENTITY_MISMATCH`, never a semantic guess. Moving a file changes only the locator.
3. **Only direct relationships are authoritative.** Reverse, transitive, roll-up and effective-governance views are always computed on demand.
4. **Timestamps, mtimes and commit times never decide truth.** Authority wins.

### 6.3 Resume and checkpoints

- There is **no checkpoint store**.
- Every command's continuation point is derived from authoritative state: the artifact's state and body, its OPEN ESC/BLK/REC records, and the REC closure-plus-dispositions (§3.3).
- If execution stops before a persist, the unfinished step is repeated rather than assumed done.
- Workflow resume never overloads Project `resume_state`, which remains solely the Project's return-from-PAUSED lifecycle value.

### 6.4 `.kilo/` (✅ Point 06.10)

- The target project's `.kilo/` is a disposable local runtime namespace. It is fully ignored in `.gitignore`, has no carve-outs, and is kept per worktree.
- In v0.2 it holds only transient Claude handoff files (§14). Anything that needs Git history lives outside it.

### 6.5 Lookup mechanics 🆕 (TODO-2 result — see `poc/todo2-lookup/RESULTS.md`)

The measurement covered 200 and 400 Spec fixtures against a ground-truth oracle. It found that single-hop lookups and resume are cheap and exact, but multi-hop queries done by an agent need up to 210–633 tool calls (the planner's step budget is 30) or 19–38k tokens of raw edges. So:

- **Single-hop lookups** (reverse dependents, reverse governance, children, owed `PENDING:` entries, records referencing an ID) use **front-matter-anchored `git grep`**, e.g. `git grep -n -E "^depends_on: \[.*\bSPEC-011([#,]|\])" -- docs/project docs/epics docs/features docs/specs`. This is exact, takes one call and costs about 20 tokens. Unanchored `git grep <ID>` is not allowed for relationship lookups, because it is 100–150× more expensive.
- **Multi-hop queries** use **`kilo_graph.py`**, a read-only, deterministic calculator: Python 3.8+ standard library, about 200 lines, installed globally as `tools/kilo_graph.py`.
  - Subcommands: `closure <ROOT>` (§3.3 step 2), `cycles` (§4.5), `integrity` and `order` (§8.6), and `owed <OWNER>` (§2.3).
  - It reads the current working tree, never writes, and stores nothing. Its output is compact JSON.
  - It **fails closed**: a closure that reaches a duplicate or unresolvable ID reports `blocked` instead of returning a partial list.
  - It is a calculator, not a store, so §6.2 is unchanged and none of SQLite's refresh, rebuild or recovery concerns apply.
- **Prerequisite:** Python 3.8+ on PATH for LARGE projects. `/project-init` checks it. If it is missing, `/reconcile` and `/status` stop with the operational diagnostic `KILO_GRAPH_UNAVAILABLE`. This is never `HUMAN_DECISION_REQUIRED`, and they never fall back to an agent-driven multi-hop grep walk. Single-hop commands are unaffected.
- **SQLite:** not needed. No measured lookup or resume problem remains for a store to solve (§6.1 rule satisfied). Revisit only if dogfooding shows otherwise.

## 7. Escalation model (✅ Point 04, 🆕 records)

### 7.1 Ladder

```text
04.1 Local implementation choice       → agent decides
04.2 Required behaviour unclear        → SPECIFICATION_CLARIFICATION_REQUIRED
04.3 Durable system-level constraint   → ARCHITECTURE_ESCALATION_REQUIRED 🆕 (token name for "architecture issue")
04.4 Developer priorities / trade-off  → HUMAN_DECISION_REQUIRED
```

### 7.2 Classification tests

- **Autonomy (04.1).** All of the following must hold:
  - the context is fresh;
  - the choice is consistent with, or unaddressed by, authority;
  - it does not change behaviour, acceptance or accepted decisions;
  - it does not touch external contracts;
  - it sets no project policy;
  - reversing it later needs no migration or coordination;
  - verification proves existing behaviour rather than defining it;
  - no constructed argument is needed to justify it.
  - Persisted formats, external API/event shapes, deploy/config contracts, shared abstractions and security semantics are presumptively *non-local*.
  - Tests never choose the expected result.
  - *Test: would any artifact, consumer, sibling or future implementation need to know which option was chosen?*
- **Specification clarification (04.2).** Reasonable options would produce materially different observable behaviour. Examples: missing cases, conflicting requirements, undefined error, state, ordering, idempotency, default or boundary behaviour, or verification that would have to invent the expected result.
  - The de minimis rule applies.
  - Classification is provisional: triage routes to the Spec owner, to architecture, or to a human.
- **Architecture issue (04.3).**
  - A decision is architectural if it establishes, changes or reinterprets a durable system-level constraint, contract, boundary or pattern. This holds even before any dependents exist (foundational decisions count).
  - Potential reuse alone does not make a decision architectural.
  - Applying an existing ADR is not an architecture issue; an ADR whose application is unclear goes to 04.2.
- **Human approval (04.4).** Required when the decision depends on the developer's priorities, risk, cost, lock-in, scope or a reserved decision. Classify conservatively.
  - Being architectural, hard or multi-option is not itself a trigger.
  - `HUMAN_DECISION_REQUIRED` presents a *bounded choice*: the decision, why it is human-owned, options with trade-offs, a technical assessment and a recommendation.
  - **Cumulative effect 🆕:** assessed within the invocation's scope. There is no cross-invocation aggregation machinery; `/review` and `/adversarial-check` are the backstop, and this is an accepted residual risk.
  - **Developer-reserved decisions 🆕:** listed in the owning authority's body under `## Developer-Reserved Decisions`. Agents treat any listed item as `HUMAN_DECISION_REQUIRED`.

### 7.3 Blocking, pause and resume

- **Blocking.** Blocking is a *property*, not a category. The test: *would this work remain correct under every reasonable resolution?* If not, it is blocked at the narrowest scope (path, work unit, or project). Easy reversibility never licenses a guess.
- **Pause.**
  - Only the dependent scope is paused. Safe continuation is a standing test.
  - A paused path never proceeds on placeholders, weakened checks or early completion.
  - A gate passes over an unresolved dependency only if the developer explicitly excluded it through a 04.4 decision.
  - If the blocked scope widens, update the existing ESC record; do not create a duplicate.
- **Resume.** All three must hold:
  1. the resolution has been promoted into its owning artifact;
  2. the developer explicitly re-invokes the owning command (§1.4);
  3. current state proves the path is safe — no dependent reconciliation is pending.
  - Valid independent work is preserved.
  - Control returns to the owning workflow.

### 7.4 Report envelope

Every escalation report uses this fixed envelope:

```text
ESCALATION REPORT
Classification · Origin · Unresolved decision · Why escalation is required · Authority consulted
Options / interpretations · Technical assessment · Blocking assessment · Blocked work
Safe continuation (mandatory; "None" + reason if none) · Resolution required
```

- Report one decision per escalation, except a composite 04.4 cumulative case.
- Complete the bounded discovery first, then stop searching once the escalation threshold is met.
- Give references, not copied content, and conclusions, not transcripts.
- 🆕 Persist the report as `ESC-###`. The command then ends with `HUMAN_DECISION_REQUIRED` (for 04.4) or with its own `*_BLOCKED` token (for 04.2 and 04.3), naming owner `SPECIFICATION`/`EPIC`/`FEATURE` or `ARCHITECTURE`.

### 7.5 Durable knowledge

- The answer is promoted into the artifact that semantically owns the decision. The ESC record keeps provenance only.
- A genuine 04.2 always produces an artifact edit.
- A change to COMPLETE or accepted authority goes through reconciliation.
- Rejected options never become truth.
- ESC records persist indefinitely but are never part of default context. They are loaded on demand only.
- *Test: delete the ESC record — is the decision still discoverable from the artifacts?*

### 8.3 Shared input rules (✅)

- The user supplies intent and any new constraints. Kilo loads persisted authority itself and never re-asks what is already known.
- A target may be inferred only when exactly one eligible candidate exists. Kilo never picks "most recent".
- Missing authority is never invented.
- User constraints that conflict with authority are surfaced.
- Supporting commands need a bounded target.
- Readiness preconditions cannot be bypassed:
  - `/feature` needs its parent Epic at `READY_FOR_FEATURE_DECOMPOSITION` or ACTIVE (adding a Feature to an ACTIVE Epic without a material scope change is allowed 🆕, by symmetry with the Point 05.3 rule for Specs);
  - `/spec` needs its parent Feature at `READY_FOR_SPEC` or ACTIVE;
  - `/implement` needs its Spec at `READY_FOR_IMPLEMENTATION` (normal path) or an approved bounded maintenance change.
- Exact CLI syntax is an implementation detail.

The ✅ per-command input table in the v0.2 tracker (Point 07.3) is carried forward unchanged.

**Lifecycle-action syntax 🆕:** `/epic <ID> complete|retire`, `/feature <ID> complete|retire`, `/spec <ID> retire`. These act on the named artifact only and apply the §2.4 guards.

### 8.4 Output contracts

**Discovery/support (✅).**

- **`/grill` in LARGE:** the subject may be an artifact's content *or* a decomposition boundary (Epic→Feature, Feature→Spec). The result is one of `GRILL_RESOLVED` (the bounded scope is clear, including the agreed split for a boundary subject; this is not artifact readiness, and answers are persisted by the owning command), `GRILL_BLOCKED` (evidence, access or authority missing) or `HUMAN_DECISION_REQUIRED`.
- **`/grill` in STANDARD ⚠:** keeps the v0.1 pre-PRD tokens `DISCOVERY_READY` and `DISCOVERY_BLOCKED` and the `DISC-###` brief. The mode discriminates.
- **`/ideate`:** see §13.

**Decomposition family (`/epic`, `/feature`, `/spec`) — shared (✅).**

| Result | Meaning |
|---|---|
| `<X>_CONTINUE` | Useful local work remains; the artifact has been persisted. |
| `<X>_WAITING` | Local work is exhausted and readiness waits only on a declared, normally progressing dependency. Its current state has been freshly verified. This is never used for parent drift. |
| `<X>_BLOCKED` | No viable normal path; writes a `BLK-###`. |
| `<X>_READY` | Gate passed and state is READY_*; returns a compact handoff. |
| `HUMAN_DECISION_REQUIRED` | A developer decision is needed. |
| Integrity diagnostics | §1.3. |

Tables do not set precedence; the discriminators do.

- Non-primary waiting, blocking or decision conditions found along the way are surfaced and persisted by reference. They never live only in chat.
- Every result includes the mandatory **Owed Contracts** section (§2.3), with `none` when empty.
- **Preflight** checks only the immediate parent.
  - *Case A* — a child exists while the parent is still READY: repair the parent forward and surface the repair.
  - *Case B* — the parent is ACTIVE but no child exists: `LIFECYCLE_INTEGRITY_FAILURE`, and the next owner is `/diagnose`.
  - *Case C* — the artifact is malformed: `AUTHORITATIVE_ARTIFACT_INVALID`.
- **Parent drift** (`/feature`, `/spec`):
  - Reload the parent. A non-semantic change just refreshes context.
  - Settled decisions are never silently reopened, and `/shouldreconcile` is never invoked automatically.
  - An unreconciled accepted parent change leads to `*_BLOCKED` with routing to `/shouldreconcile`.
  - There is no Feature-internal decision graph.

**Ready handoffs (✅, 🆕 for Spec).**
- **`EPIC_READY`:** ID, state, Human-Evaluable Outcome, Major Boundaries, Non-Goals, Dependencies, Locked Assumptions, Verification Intent as journey ACs (`AC-1…n`, E2E), Next: `/feature`.
- **`FEATURE_READY`:** ID, state, Human-Evaluable Capability, Observable Surface, Scope Boundaries, Integration/Contract Boundaries, Non-Goals, Dependencies, Assumptions, Acceptance Intent, Verification Intent (integration), Next: `/spec`.
- **`SPEC_READY` 🆕:** ID, state, Behavioural Slice, AC IDs, Contracts provided and consumed, Dependencies (with consumable status), TDD applicability, Verification Requirements, Next: `/implement`.

**`/spec` specifics 🆕.**
- The LARGE family is `SPEC_CONTINUE`, `SPEC_WAITING`, `SPEC_BLOCKED` (v0.1 token kept) and `SPEC_READY`.
- `/spec FEATURE-###` may decompose the Feature into several DRAFT Specs in one invocation, which activates the Feature.
- The final token is `SPEC_READY` only if every Spec targeted in that invocation is READY. Otherwise the discriminator picks the result, and the output lists each Spec's state.
- STANDARD keeps v0.1 set-level `SPEC_READY` / `SPEC_BLOCKED`.

**Reconciliation 🆕.**
- **`/shouldreconcile`** — see §3.2.
- **`/reconcile`:**
  - `RECONCILE_CLOSED`: assessment is complete and no obligation remains open.
  - `RECONCILE_OPEN`: assessment is complete and obligations remain. Lists them with their next owners.
  - `RECONCILE_INCOMPLETE`: the session ended during `ASSESSING`. Resume with `/reconcile REC-###`, which resumes from the recorded delta and never re-classifies (§3.3 *Crash safety*).
  - `HUMAN_DECISION_REQUIRED`: the root is ambiguous. An ESC record is written and no package is created.
  - `PERSISTENCE_FAILURE`.

**Delivery (v0.1 tokens retained ✅, with extensions 🆕).**
- **`/implement`:** `IMPLEMENTATION_READY_FOR_VERIFY`, `IMPLEMENTATION_BLOCKED` (for 04.2/04.3, with ESC) or `HUMAN_DECISION_REQUIRED`.

- **`/verify`:** result `DONE` / `NOT_DONE` + report gate `CLEAR` / `BLOCKED` (the effective gate is derived; see §11.1).
- **`/fix`:** `FIX_APPLIED` / `FIX_BLOCKED`.
- **`/diagnose`:** `DIAGNOSIS_READY` / `DIAGNOSIS_BLOCKED`.
- **`/waive`:** `WAIVER_APPROVED` / `WAIVER_BLOCKED`.
- **`/review`:** `APPROVE` / `CHANGES_REQUIRED` / `REQUEST CHANGES`.
- **`/adversarial-check`:** `ADVERSARIAL_CLEAR` / `ADVERSARIAL_FINDINGS`.
- **`/smoke`:** v0.1 tokens.
- **`/status` 🆕:** its sections and final token are defined in §8.6.

### 8.5 Modes, resume and ownership 🆕

**Planning-worker modes (v0.1 mechanism, reused for model-override delegation).**
- `AUTHOR`: create or update the artifact.
- `CONTINUE`: resume within a session after the user answers. Continuation state *references* the persisted artifact; the parent passes only identity, scope and mode (Point 03.4, rule 6).
- `RECONCILE_ONLY`: see §3.8.

**Resume per command.** Each command derives its continuation point from authority (§6.3):
- `/ideate` and `/epic`, `/feature`, `/spec`: the artifact state, its Open/Frontier sections, and OPEN BLK/ESC records.
- `/reconcile`: the REC closure minus the assessed dispositions.
- `/implement`: the Spec state plus the working tree (v0.1 behaviour).
- `/smoke`: its v0.1 run record.

**Verification ownership.**
- `/verify` owns all *deterministic* evidence at Spec, Feature and Epic level.
- Human acceptance is recorded only by the completion action (`/feature|/epic <ID> complete`).
- `/waive` owns risk acceptance.
- `/review` owns judgement and the Spec completion transition.

**Escalation ownership.**
- The originating command writes the ESC record.
- The resolver depends on the classification: a Spec clarification goes to the owning planning command (`/spec`, `/feature` or `/epic`); an architecture issue goes to `/architect`; a human decision goes to the developer, whose answer is persisted by the command that owns the artifact.

**Agent overlap resolved.**
- `planner` is primary for every planning command.
- `planning-worker` is used only for explicit model override (v0.1) and for `RECONCILE_ONLY`.
- `architect` (Opus) is escalation-only.
- `builder` implements.
- `debugger` handles `/fix` and `/diagnose`.
- The adversary variants are selected by user or approved escalation.
- No agent owns an artifact that its command does not own.

**v0.1 commands left behaviourally unchanged:** `/prd`, `/architect`, `/fix`, `/waive` and `/adversarial-check` (apart from the RECONCILE_ONLY source label). The other retained commands are extended minimally, as listed in §8.1.

### 8.6 `/status` 🆕 (read-only; the only aggregate view; computed with `kilo_graph` `order`, `integrity` and `owed`, §6.5)

`/status [ID]` prints the following sections and never writes:

- **Canonical order:** a topological order over `parent_id` + `depends_on`. Ties go to Enabler/foundation work first (§12), then ID order. It is advisory only (tenets 3–4).
- **Ready / Waiting / Blocked / Active / Complete** lists, derived from states and OPEN BLK/ESC records.
- **Open REC packages and obligations**, and **Specs COMPLETE under a waiver**.
- **Artifact counts 🆕 (§6.1 observability tripwire):** total Epics, Features, Specs and records (REC/ESC/BLK), each broken down by state. This is the standing count that grounds SQLite reconsideration in measured scale rather than assumption, and it never triggers a threshold or diagnostic by itself.
- **Integrity scan:**
  - duplicate IDs and ID mismatches;
  - dangling references;
  - **open `PENDING:` entries grouped by owner**, flagging any owner that is RETIRED or missing, and any owner that has passed its gate without a recorded action;
  - cycles;
  - Case A and Case B lifecycle contradictions;
  - invalid transitions detected from Git diffs of `state`;
  - Project `resume_state` inconsistency.

  This answers the Point 07.4 "project lifecycle-integrity scan" question. The scan runs only on demand; there is no background monitor.
- **Final token:** `STATUS_REPORTED` (plus the integrity diagnostic list when applicable).

## 10. Grooming gates (Point 08) 🆕 fully specified

### 10.1 Gate principle

An artifact is ready when the next stage can proceed **without inventing material intent**. The test is the Point 04.5 invariance test: any unknown whose every reasonable answer leaves the decomposition or implementation correct is non-blocking. A gate is evaluated when requested and re-evaluated after a material change (§2.5).

### 10.2 Common gate items (all levels)

- [ ] Front matter is valid and `depends_on` / `governed_by` have been audited.
- [ ] Effective governance is resolved, and every exemption is authorized.
- [ ] Every dependency is consumable (§4.4) or listed as `PENDING:` with a named owner. A `PENDING:` entry whose contract is *undecided* blocks the gate.
- [ ] **Owed contracts (owner side):** every `PENDING:<this-id>:*` entry held by another artifact has a recorded action — provide, route, or reject (§2.3).
- [ ] No blocking cycle exists.
- [ ] No OPEN ESC or BLK references the artifact with a blocking scope.
- [ ] No OPEN REC obligation affects the artifact.
- [ ] Non-blocking unknowns are listed under `## Open Questions` with an owner.
- [ ] Deferred decisions are listed under `## Deferred Decisions` with (a) the owning later stage or artifact and (b) why deferring is safe under the invariance test.
- [ ] The parent is in the required state (§8.3).

### 10.3 Level-specific items

**Epic → `READY_FOR_FEATURE_DECOMPOSITION`.**
- One-sentence Human-Evaluable Outcome and its Observable Surface.
- In-scope boundaries and Non-Goals.
- Traced PRD FRs.
- Locked assumptions and constraints (cost, security, operations).
- Acceptance Intent: how the developer will judge the outcome.
- Verification Intent: E2E journeys (happy path plus at least one negative path), each written as a stable Epic acceptance criterion `AC-n` (§2.3). The Human-Evaluable Outcome is `AC-0`.
- An advisory **Candidate Capability Map** (a list, not artifacts).
- Foundation and enabler prerequisites identified (§12).

**Feature → `READY_FOR_SPEC`.**
- Human-Evaluable Capability and its Observable Surface.
- Scope boundaries, Integration/Contract boundaries and Non-Goals.
- Feature acceptance criteria as `AC-n`, each observable through the surface. The Human-Evaluable Capability is `AC-0`.
- Verification Intent (integration, and E2E where required by §11.2).
- An advisory **Candidate Slice List**.
- Contracts this Feature provides, named as headings so they can be anchored.

**Spec → `READY_FOR_IMPLEMENTATION`.**
- The v0.1 content sections (Identity … Definition of Done).
- Every acceptance criterion carries an `AC-n` ID and is objectively verifiable.
- Testing Requirements that name seams and include negative and boundary tests.
- TDD applicability and Verification Requirements.
- Provided and consumed contracts are explicit.
- Size is within 5–15k tokens, or the reason for `SPEC_CONTEXT_PRESSURE` is recorded.
- There are no open behavioural 04.2 ambiguities.

### 10.4 Questioning discipline (avoids over-questioning)

1. Ask only about a gate item that neither authority nor the repository settles.
2. Research facts before asking (bounded, as in §5.10). Ask the developer only for *decisions*.
3. Batch related questions into one decision frontier per round.
4. Stop as soon as the gate passes. There are no "nice to know" rounds.
5. Use `/grill` only when a cluster of coupled ambiguities needs interrogation.
6. Never re-ask a persisted answer.

### 10.5 What blocks progression

Progression is blocked by: a failing common or level item; a blocking unknown; an undecided pending contract; a blocking cycle; an unauthorized exemption; parent drift that has not been reconciled; or an OPEN blocking ESC, BLK or REC. Everything else proceeds, with the unknown recorded.

### 10.6 Research

Research is needed when a gate item depends on an external fact that is absent from authority. It is performed inside the owning command and persisted in the artifact body with its sources. If it cannot be obtained and no safe bounded assumption exists, the result is `*_BLOCKED`.

## 11. Verification & testing (Point 09) 🆕 fully specified

### 11.1 Evidence model (✅)

- Verification results are factual (`DONE` / `NOT_DONE`) and kept separate from the delivery gate.
- Reports are immutable.
- Freshness uses Contract v1 (canonical manifest `MATCH`) at every level.
- Applicability lives in a sidecar, per claim.
- A failed check never creates a successful association.
- 🆕 **Sidecar rule.** A sidecar is written for every run whose freshness is `MATCH`, whatever the overall result.
  - Claims whose required checks all passed get `(artifact_id, AC-n) → APPLICABLE`.
  - Claims with a failed or uncovered check get **no entry**.
  - A `NOT_DONE` run can therefore still prove its passing claims. This is the claim-level model from Point 01 / 05.11.
  - Runs with `MISMATCH` or `UNRECONSTRUCTABLE` get no sidecar.

**Gate vocabulary (single contract) 🆕.** Three distinct values; only the effective gate is used as a guard:

| Term | Values | Written by | Where |
|---|---|---|---|
| **Verification result** | `DONE` \| `NOT_DONE` | `/verify` | the report (immutable) |
| **Report gate** | `CLEAR` \| `BLOCKED` | `/verify` | the report (immutable). `CLEAR` requires `DONE` and pre/post `MATCH`. |
| **Effective delivery gate** | `CLEAR` \| `CLEAR_WITH_EXCEPTION` \| `BLOCKED` | *derived, never stored* | computed when a guard is evaluated |

The effective gate for a target is computed from its **latest** report, as follows:
- **`CLEAR`:** the report gate is `CLEAR` and Contract v1 freshness is still `MATCH` for the current working tree.
- **`CLEAR_WITH_EXCEPTION`:** the report is `NOT_DONE`, and a `/waive` waiver exists that is valid and unexpired *now* and is tied to that exact report, manifest and failure set, and freshness is still `MATCH`. This matches v0.1 `/waive` semantics.
- **`BLOCKED`:** anything else.

`CLEAR_WITH_EXCEPTION` never appears inside a verification report. Every guard in this spec (§2.4, §11.4) refers to the **effective delivery gate**. Waiver expiry after an artifact reaches COMPLETE never reopens it (§2.4). `/status` lists completed artifacts whose waiver has since expired.

### 11.2 Test obligations by level

**Suite tiers 🆕.** Tests are grouped by *what they need to run*, not by what they are called. `/project-init` records one command per tier in the project `AGENTS.md`. A tier that doesn't exist yet is recorded as `none`.

| Tier | Contains | Needs |
|---|---|---|
| `fast` | unit, contract, and in-process integration tests (in-memory or fake adapters) | only the code |
| `integration` | cross-Spec, cross-process tests against real adapters (DB container, real HTTP between components) | a composed local environment |
| `e2e` | user or consumer journeys through the Observable Surface | the whole system, running locally or deployed |

**What each `/verify` level runs:**

| Level | Required evidence | Runs |
|---|---|---|
| Spec (`/verify SPEC-###`) | every Spec `AC-n` | **(1)** the tests named in the Spec's Testing Requirements, *whatever their tier*. A Spec that owns an adapter or contract may require specific `integration` tests, and only those run. **(2)** the full `fast` tier as regression. It does **not** run the full `integration` or `e2e` tiers. A negative or boundary test is required for every AC with error, validation or boundary behaviour. |
| Feature (`/verify FEATURE-###`) | every Feature `AC-n` through the Observable Surface | the full `fast` + full `integration` tiers. At least one integration test must exercise the child Specs together across their real contracts, and at least one negative path per external boundary. Add `e2e` tests only when the capability crosses process, network or browser boundaries that `integration` can't cover. |
| Epic (`/verify EPIC-###`) | every Epic journey `AC-n` (the Verification Intent journeys) | full `fast` + `integration` + `e2e`. The E2E journeys cover the happy path plus at least one negative path. |
| Human acceptance (Feature, Epic) | claim `AC-0` (the Human-Evaluable Capability or Outcome) | an `ACCEPT-<ID>-###` record: what was observed, on which build (Contract v1 manifest), and the verdict. It is recorded by the `complete` action. If `ACCEPTED` and the build still matches, its sidecar marks `(ID, AC-0) → APPLICABLE`. |

Security checks follow v0.1 `/verify` Stage 4 at every level. Running the full `integration` and `e2e` tiers only at Feature and Epic level keeps Spec loops cheap.

**STANDARD projects:** there are no Feature or Epic levels, so `/verify` keeps the v0.1 behaviour and runs every applicable configured check. This preserves backward compatibility.

### 11.3 Failure routing

- **Spec `NOT_DONE`:** the v0.1 loops apply (`/fix`, `/diagnose → /fix`, `/waive`).
- **Feature or Epic `NOT_DONE`:**
  - A defect inside an accepted Spec's claim goes to `/fix FEATURE-###` or `/fix EPIC-###` (a corrective change bounded by accepted authority). Then re-run `/verify` at the failing level. A COMPLETE Spec does not reopen.
  - Behaviour that was never specified becomes a new Spec under the ACTIVE Feature (`/spec`).
  - A contradiction in authority goes to `/shouldreconcile`.
  - An unclear cause goes to `/diagnose` first.
- **Waiver at Feature or Epic level:** allowed under v0.1 `/waive` rules. `/status` lists every completion that relied on a waiver.

### 11.4 Completion guards

- **Spec:** see §2.4 (`/review` `APPROVE` path).
- **Feature (`/feature <ID> complete`):**
  - the hard floor holds;
  - the **effective delivery gate** (§11.1) of the latest `/verify FEATURE` run is `CLEAR` or `CLEAR_WITH_EXCEPTION`;
  - every Feature `AC-n` either has an `APPLICABLE` association, or (only under `CLEAR_WITH_EXCEPTION`) falls inside the waiver's failure set. These waived claims are printed in the output and listed by `/status`;
  - no OPEN REC obligation (including `REVERIFY`) or blocking ESC/BLK references the Feature or its Specs;
  - no owed contract (`PENDING:<FEATURE-id or child-id>:*`) is left without a recorded action (§2.3);
  - the developer records `ACCEPTED` in `ACCEPT-FEATURE-###-###`, making `(FEATURE-###, AC-0)` `APPLICABLE`. `AC-0` can never be covered by a waiver.
- **Epic (`/epic <ID> complete`):** the same guard, with Features and E2E evidence in place of Specs and integration evidence.
- **Consumer rule (§4.4):** an artifact cannot complete while the provider integration evidence it depends on is not `APPLICABLE`.

### 11.5 After reconciliation

The ✅ Point 01 / 05.11 rules apply (§3.6). A `REVERIFY` obligation closes on fresh `APPLICABLE` evidence at the level of the affected claim.

## 12. Platform / Enabler / cross-cutting work (Point 10) 🆕

- **No new artifact types, states or dependency kinds.**
- **Cross-cutting *policy*** is an ADR or PRD clause applied through Governed by, with exemptions (§4.2). It is *authority*, not work.
- **Shared *infrastructure or capability*** is an ordinary Feature (or a Spec for small bootstrap work, e.g. v0.1 `SPEC-000 — Project Bootstrap and CI`) marked in its body with `Kind: ENABLER`. Examples: CI/CD, auth foundation, observability, persistence baseline. Its human-evaluable surface is technical: a pipeline run, a deployed health endpoint, a trace or log visible in the chosen tool, or a login round-trip.
- **Front-loading (tenet 7).** The first Epic of a LARGE project is a **Foundation/Walking-Skeleton Epic**. It delivers the minimal deployed vertical slice together with the enablers the architecture requires (CI, CD, config, logging/tracing, authn/authz baseline, test foundations), so every later slice can be deployed and verified independently.
- **Guarding against premature infrastructure.** An Enabler Feature passes its gate only if at least one of the following holds:
  - (a) an accepted ADR requires it; or
  - (b) at least one existing Feature or Spec `depends_on` its contract, or will do so via a `PENDING:` entry.
  
  Otherwise it is speculative and is not groomed. A reusable helper stays implementation-local until real cross-scope reliance exists (Point 04.3 non-trigger).
- **Dependencies, verification and completion** are identical to ordinary Features. Consumers depend on the enabler's *contract* (§4.4), not on its completion, for implementation.

## 13. Ideation (Point 11) 🆕 completes 07.4 locks

### 13.1 Artifact

- The discovery record **is the body of `docs/project/PROJECT-001.md`**. This avoids a separate discovery type and gives a deterministic resume target, because there is exactly one Project.
- Front matter follows §2.2 (`state: DISCOVERY`).
- **Body sections:**
  - Problem & Outcome
  - Users/Actors
  - Success Measures
  - Scope / Non-Goals
  - Core Journeys
  - Binding Constraints (budget, platform, compliance, timeline)
  - Confirmed Decisions (each with an ID `D-n`)
  - Decision Frontier (open questions, marked blocking or non-blocking)
  - Assumptions (provisional, with confirm/refute evidence and dependents)
  - Research Log (question, status `NOT_STARTED` / `IN_PROGRESS` / `DONE`, sources, supported partial conclusions, remaining steps)
  - Developer-Reserved Decisions
- The v0.1 STANDARD `/grill` `DISC-###` brief is unchanged and unrelated.

### 13.2 Results (✅)

**`IDEATION_CONTINUE`**
- Valid progress has been persisted, discovery is not yet ready, and nothing blocks it.
- *Discriminator:* could ideation still progress on at least one independent part of the frontier? If yes, `CONTINUE`; if every remaining part needs a developer choice, `HUMAN_DECISION_REQUIRED`. Related decisions may be presented together as one frontier.

**`IDEATION_READY_FOR_PRD`**
- Nothing is left that `/prd` would have to invent.
- Non-blocking unknowns, architecture-owned questions and bounded assumptions may remain.
- Performs Project DISCOVERY → PLANNING. It does not imply PRD approval.

**`IDEATION_BLOCKED`**
- Evidence is required, and no *safe bounded assumption* exists.
- *Evidence vs decision:* "competitor pricing" is evidence; "our pricing" is a human decision.
- Kilo is conservative about assumptions that touch legality, security, irreversible architecture, major cost or core product promises.
- Writes a `BLK-###`.

### 13.3 Resume (✅, simplified 🆕)

A bare `/ideate` behaves as follows:
- **No Project:** start fresh.
- **Project in DISCOVERY:** resume it. It must be visible (the frontier is printed). Kilo first revalidates OPEN BLK/ESC records; unresolved ones are reported instead of resumed.
- **Project past DISCOVERY:** refuse to reopen ideation. Later product change goes through `/prd` refinement or `/shouldreconcile`.

Kilo compares the current artifact against the last persisted frontier:
- unchanged → continue;
- editorially changed → refresh;
- materially changed → recompute;
- uncertain → `HUMAN_DECISION_REQUIRED`.

### 13.4 Contradiction detection

Each new answer is checked against the Confirmed Decisions and Binding Constraints.

- **Before `IDEATION_READY_FOR_PRD`:** a contradiction is presented as a `HUMAN_DECISION_REQUIRED` choice (keep / replace / refine). Replacing an ideation decision is ordinary editing, because nothing downstream is accepted yet.
- **After the PRD exists:** the change goes through `/shouldreconcile`.

### 13.5 PRD handoff

`/prd` in LARGE loads `PROJECT-001` in full (§5). Each `D-n` maps to PRD FRs, constraints or non-goals, and the PRD's related-documents list references `PROJECT-001`.

### 14.3 Handoff packet

`.kilo/handoffs/HO-###.md` is transient; the owning command persists whatever matters.

```yaml
---
id: HO-007
origin_command: /adversarial-check
target: ADR-012
mode: ADVERSARIAL | REVIEW | DIAGNOSE | ARCHITECTURE_ESCALATION
read_only: true
response_schema: kilo-handoff-result-v1
result_path: .kilo/handoffs/HO-007.result.json
---
## Task            (one bounded question)
## Mandatory sources (references only — resolve them yourself from the repo, Point 03)
## Excluded context (e.g., author reasoning)
## Constraints     (no edits; no commands except read-only git)
## Required response (schema below)
```

The result is `{handoff_id, status: COMPLETED|FAILED|INSUFFICIENT_CONTEXT, verdict_token, findings:[{id, severity, claim, evidence_refs, recommendation}], model, usage}`.

The originating command validates the schema and reconciles the findings as *evidence, not authority* (v0.1 adversarial rule). If needed, it applies `RECONCILE_ONLY` (`ADVERSARIAL_FINDINGS`).

**Context ceiling applies here too 🆕.** §5's "one context policy applies to all commands" governs the handoff, even though the packet itself carries only references. The 40k pressure threshold and 100k hard ceiling (§5.8) apply to the **effective context the delegated agent resolves from `Mandatory sources`**, not to the size of `HO-###.md`.

Enforcement happens **during resolution, not after spend**: the delegated agent estimates content as it resolves each `Mandatory sources` reference (§5.12's characters ÷ 3.5 estimate) and stops resolving before crossing 100k, returning `INSUFFICIENT_CONTEXT` with the ceiling diagnostic rather than continuing to load and only reporting it once the model has already consumed the oversized context. The originating command then validates that this happened correctly (the result's `usage` should be consistent with a bounded resolution) — validation is a check on enforcement, not the enforcement mechanism itself.

### 14.4 Failure and guardrails

- **Unavailable, quota or rate-limit:** fail clearly with the provider error. Offer re-running with GPT (Sol) as an explicit user choice; there is never a silent fallback. The workflow never depends on Anthropic availability.
- **Malformed result:** `INSUFFICIENT_CONTEXT` or a schema failure is treated as no result, and one retry is offered.
- **Spend:** a hard monthly spend cap is set in the Anthropic console (not in Kilo infrastructure). Each paid invocation prints its model and usage in the command output.
- **Non-goals (✅):** no provider framework, universal routing, marketplace, auto-benchmarking or agent-to-agent communication.
