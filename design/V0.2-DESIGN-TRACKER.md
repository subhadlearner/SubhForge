# Kilo Stable v0.2.0 — Design & Brainstorming Tracker

> **Superseded by [`V0.2.1-DESIGN-TRACKER.md`](V0.2.1-DESIGN-TRACKER.md)** (consolidated specification). This file is kept as the historical reasoning record.

## Purpose

This document tracks the design work required before implementing **Kilo Stable v0.2.0**.

v0.2.0 is an evolution of the existing Stable v0.1.0 workflow. It is **not intended to become a universal AI development platform**.

The primary objective is:

> Build an opinionated, reliable and cost-conscious Kilo + VS Code workflow that helps me successfully execute my own serious personal software projects from initial idea through implementation and verification.

Expected projects include applications such as:

- MFHistory
- Arthabeacon
- subhbrain
- future personal greenfield projects of similar or greater complexity

The workflow should particularly improve support for **large projects that may run for weeks or months**, where context loss, requirement drift, incomplete decisions and uncontrolled AI behaviour become increasingly problematic.

---

# Scope Rule

Every proposed capability must pass the following test:

> **Does this materially help me design, build, verify or resume my own projects?**

If the answer is unclear, the capability should not be added.

Prefer:

- Kilo-native capabilities
- simple solutions
- explicit workflows
- Markdown/Git where sufficient
- deterministic behaviour where practical
- human-controlled decisions
- measurable improvements

Avoid:

- infrastructure for hypothetical future users
- unnecessary provider abstraction
- generic plugin frameworks
- architecture designed primarily for extensibility
- solving problems we have not encountered or reasonably expect
- building a platform instead of improving the development workflow

# Kilo v0.2 Personal Workflow Tenets

These tenets govern v0.2 design choices and should be applied before adding automation or complexity.

1. **Personal workflow first.** Kilo is Subhadeep's own AI-assisted development workflow, not a generic software-delivery platform. Prefer simple, explicit, human-controlled behaviour over automation that is not necessary for Subhadeep's workflow.

2. **Reconciliation is a first-class priority.** `/shouldreconcile` and `/reconcile` are among the most important LARGE-workflow capabilities because software design changes frequently due to new requirements, technology changes, architecture evolution and external constraints. These commands must be designed carefully to locate the exact accepted-authority delta, determine affected artifacts, manage dependencies, and create/route required new work such as Epics, Features and Specs without rewriting unrelated work.

3. **Correct decomposition matters more than automated scheduling.** Epic, Feature and Spec authoring must follow Kilo's agreed boundaries rather than arbitrary size splitting. Specs should remain small enough to fit the defined context limits. Features and Epics must represent coherent human-evaluable product outcomes/capabilities through an appropriate observable surface. Subhadeep will review generated artifacts before choosing execution order.

4. **Canonical delivery ordering is advisory, not autonomous.** Kilo should produce a dependency-aware canonical ordering/list of Epics, Features and Specs for Subhadeep to review and follow. Kilo must not automatically start or sequence implementation work merely because an artifact is next in that list.

5. **Spec-first execution is the minimum required v0.2 delivery path.** The first implementation target that must work reliably is an explicit command such as `/implement SPEC-001`, followed by the familiar delivery loop such as `/verify`, `/diagnose` and/or `/fix`, `/review`, then the normal human-controlled PR workflow. Direct `/implement FEATURE-*` or `/implement EPIC-*` is desirable only if it can be added cleanly; it must not delay or destabilize reliable Spec-level implementation.

6. **Humans choose what to implement and when.** Dependency metadata informs Subhadeep; it does not replace his judgment. If a requested Spec depends on another incomplete Spec, Kilo should surface that dependency clearly and let Subhadeep decide how to proceed rather than silently scheduling or executing other work.

7. **Foundations and cost-control concerns are front-loaded.** Authentication, authorization, logging, tracing/observability, metrics, CI, CD/deployment, security, configuration, persistence, testing foundations, reusable abstractions and reusable architecture should be addressed early so each later vertical slice can be deployed and independently verified by Subhadeep. This includes cost-aware choices and avoiding repeated infrastructure/setup work across later Specs.

8. **Prefer the existing v0.1 delivery machinery.** STANDARD v0.1.0 behaviour is the baseline. Reuse it unchanged where possible and extend it minimally where LARGE workflow genuinely requires more capability. Do not re-engineer stable v0.1 commands or delivery loops without a demonstrated need.

9. **Artifact handoffs can be refined through use.** Commands and responsibilities should be clear and deterministic, but v0.2 does not need to eliminate every conceivable handoff imperfection before implementation. Real workflow use and smoke testing may reveal integration edges that can be hardened iteratively.

10. **Spend complexity where it reduces real project risk.** Prefer design effort on authority, reconciliation, dependency correctness, decomposition quality, resumability, verification and cost-control foundations. Defer autonomous scheduling, backlog orchestration and other convenience automation that Subhadeep can easily control manually.

Core principle:

> **Kilo should make Subhadeep's decisions safer, clearer and cheaper to execute — not try to replace Subhadeep as the project manager.**

### Command-on-demand operating rule

Kilo does **nothing autonomously unless Subhadeep explicitly asks it to act**. Control resides with Subhadeep.

The intended operating model is:

1. **Artifact creation on request.** When asked, Kilo creates/grooms Epics, Features and Specs using the agreed boundaries, context limits, dependencies, authority and human-verifiability rules. It does not create work items arbitrarily.
2. **Canonical implementation order on request.** Kilo produces a dependency-aware recommended ordering/list of Epics, Features and Specs for Subhadeep to review and follow. The list is advisory; Kilo does not automatically execute it.
3. **Strong change-management on request.** `/shouldreconcile` and `/reconcile` are core Kilo responsibilities and must precisely identify authority changes, affected artifacts, dependencies, reconciliation obligations and required new work.
4. **Implementation on explicit request.** `/implement SPEC-*` is the required reliable v0.2 path. Direct Feature/Epic implementation may be added if it can cleanly manage its child/dependency sequence when explicitly invoked; otherwise it is deferred to a later phase. Kilo never starts implementation merely because an artifact is next in the canonical order.
5. **Delivery commands on explicit request.** Verification, diagnosis, fixing and review remain Kilo responsibilities when Subhadeep invokes `/verify`, `/diagnose`, `/fix`, `/review` or the applicable workflow command.
6. **No automation for automation's sake.** Do not add autonomous scheduling, background orchestration, self-starting workflows or complex coordination machinery merely because it is technically possible.
7. **Simple harness end state.** Kilo should be a controlled personal coding harness that performs the requested job well, surfaces dependencies/risks clearly, and then returns control to Subhadeep.

Additional boundary:

> **A dependency is information and a constraint, not permission for Kilo to take the next action by itself. Explicit user invocation remains the execution trigger.**

A top-level design item remains unchecked until all important questions underneath it have been answered.

Once there are no material unresolved questions, mark it complete.

The decisions should then be incorporated into the relevant v0.2 specification/documentation.

Completed decisions should not be repeatedly reopened unless later work reveals:

- a contradiction
- an implementation limitation
- new evidence
- or a genuine workflow problem

# Standing Safety Principle

When Kilo cannot confidently classify an authority owner, dependency, impact, reconciliation conflict, lifecycle transition or other workflow-significant ambiguity, it must **not guess**.

It must stop the affected decision path and return:

> **HUMAN_DECISION_REQUIRED**

The response must identify the ambiguity and the concrete choices or missing information needed from the developer. This principle applies across v0.2 and should be reused rather than redefining a different safety rule in each workflow area.

# Recommended Design Order

## [x] 01 — Authority & Reconciliation

### Why this matters

Large projects evolve.

A requirement, architecture decision, external dependency or earlier assumption may change after downstream artifacts have already been created.

Without explicit rules, an AI agent may silently rewrite completed work, ignore the impact of the change, or unnecessarily regenerate large parts of the project.

v0.2 needs a controlled mechanism for handling such changes while keeping the developer in authority.

### Already agreed

- [x] Completed artifacts are immutable during normal downstream work.
- [x] Reconciliation must be explicitly initiated by the human.
- [x] /shouldreconcile evaluates a proposed change before reconciliation occurs.
- [x] /shouldreconcile returns one of:
  - SHOULDRECONCILE
  - NORECONCILENEEDED
- [x] /reconcile executes reconciliation only after the human chooses to proceed.
- [x] Normal implementation changes that can safely be handled by implementation + verification should not automatically trigger reconciliation.
- [x] /reconcile must not reconstruct the project dependency structure from semantic search. Artifact hierarchy and explicit persisted relationships are the source of truth used to calculate reconciliation candidates deterministically.
- [x] Semantic reasoning is used only where semantics are genuinely required: locating the authority root when it is not mechanically obvious, and deciding whether a deterministically discovered candidate is actually affected by the authority delta.
- [x] If the authority root or an impact/conflict classification cannot be made confidently, reconciliation stops that decision path with HUMAN_DECISION_REQUIRED rather than guessing.
- [x] Dependency metadata is maintained by the artifact authoring/grooming workflow; it is not manual bookkeeping left to the developer.
- [x] Readiness gates perform a lightweight local dependency audit using the artifact plus its declared parent, dependencies and immediately relevant authority/context. Broader semantic inspection is used only when the local audit detects uncertainty or possible missing coupling.
- [x] Dependency completeness is best-effort rather than mathematically guaranteed. An undeclared dependency discovered later is recorded as DEPENDENCY_GAP and the metadata is repaired.
- [x] Overlapping reconciliations are allowed. Obligations affecting the same effective work are merged, superseded or escalated; they are not blindly duplicated or used to block the entire project.

### Locked design — exact /reconcile algorithm

Given a human-approved change that has already been classified as SHOULDRECONCILE:

1. **Accept explicit invocation only.** /reconcile never starts automatically.
2. **Locate the authority root(s).** Find the earliest/highest authoritative artifact whose accepted decision must change. Search may identify candidates, but authority ownership is determined from artifact semantics and authority rules. If ownership is ambiguous, return HUMAN_DECISION_REQUIRED and make no speculative authority change.
3. **Create the authority delta.** Record the old accepted decision and the new accepted decision that reconciliation is applying.
4. **Reconcile the root minimally.** Modify only the parts made incorrect by the new decision; unrelated accepted content remains unchanged.
5. **Build the candidate impact graph deterministically.** Read persisted parent/child and explicit dependency metadata and calculate downstream/reverse dependents in memory. Filesystem/directory traversal and repository-wide semantic discovery are not the dependency mechanism.
6. **Classify each candidate semantically.** For every deterministically discovered dependent, ask whether it can remain exactly as written and still be truthful under the authority delta. Unaffected candidates remain unchanged; affected candidates are reconciled; ambiguous cases return HUMAN_DECISION_REQUIRED.
7. **Propagate only through effective change.** Build the complete candidate closure from persisted relationships once, then classify candidates against the effective authority delta. Pass a changed semantic contract along its dependent paths; an unchanged artifact contributes no new delta on that path. Other incoming paths can still affect the same candidate. The detailed propagation and stopping rules appear below.
8. **Record future work changes.** If reconciliation makes planned work obsolete, retain its history and mark it for the appropriate reconciliation retirement state rather than deleting it. If reconciliation requires a new Feature/Spec or other work item, record a required-work obligation; /reconcile does not fully groom or implement that new work.
9. **Assess verification impact.** Reassess prior test and acceptance evidence per claim under the evidence invalidation rules below.
10. **Run a consistency safety scan.** Search for stale authority terms/references and suspicious undeclared coupling after deterministic traversal. This is a backstop, not the primary dependency-discovery mechanism. A newly discovered undeclared dependency is reported as DEPENDENCY_GAP and repaired rather than silently ignored.
11. **Persist a reconciliation work package.** Store a durable reconciliation record containing the authority delta, artifacts checked, artifacts changed, retired work, new required work, invalidated evidence, dependency gaps, unresolved decisions and outstanding delivery obligations.
12. **Return to normal delivery workflow.** Reconciliation restores planning/authority truth and creates mandatory obligations, but it does not force immediate implementation. Unrelated work may continue. Work that depends on an unresolved reconciliation obligation must not be treated as valid/complete until the obligation is resolved through the normal authoring/grooming → /implement → /verify → /review workflow.

The reconciliation work package remains open until its mandatory obligations are resolved. Reconciliation therefore creates **eventual delivery obligations, not mandatory immediate execution**.

### Locked design — RECONCILE_ONLY semantics

**RECONCILE_ONLY is an execution mode for the artifact-owning authoring/grooming agent inside an explicit /reconcile run.** It is not a separate user command, a synonym for /reconcile, or a way for normal downstream work to edit completed authority. /shouldreconcile remains a classifier and does not enter this mode.

- **Entry contract:** /reconcile supplies the accepted authority delta, the reconciliation work-package ID, the specific existing artifact and its role (authority root or dependent), relevant current authority and dependency context, and the reason that artifact was selected. The mode cannot self-start or expand its own scope to another artifact. If the accepted new decision is missing or ambiguous, return HUMAN_DECISION_REQUIRED before changing authority.
- **Permitted change:** Read the artifact as it currently exists, then make the smallest semantic edit needed to bring it into agreement with the accepted delta. Preserve unrelated accepted decisions, stable artifact identity, and a traceable old-to-new delta in Git and the work package. Update relationships and references that become incorrect as part of that edit. A completed artifact can be revised here because the human explicitly initiated reconciliation; normal immutability still applies outside this mode.
- **No effect is a valid result:** If the candidate remains truthful exactly as written, report UNCHANGED with the reason and leave it untouched. A dependency alone does not justify rewriting it. A purely editorial cleanup is outside the reconciliation scope.
- **Unresolved cases:** If an artifact needs a new product/architecture choice, has conflicting authority, or its actual impact is uncertain, return HUMAN_DECISION_REQUIRED with the exact decision and options. Do not invent a decision or mark the artifact reconciled. /reconcile records the blocked branch and can continue independent branches.
- **New or obsolete work:** Report work made obsolete for historical retirement and create only a required-work obligation for genuinely new work. Do not fully author/groom a new Epic, Feature or Spec in this mode; the normal workflow owns that later. Do not implement code, change tests, claim fresh verification, or mark delivery complete.
- **Output contract:** Return the artifact ID; CHANGED, UNCHANGED, or HUMAN_DECISION_REQUIRED; the reason; exact semantic delta or unchanged rationale; relationship/reference corrections; potential downstream contracts affected; newly discovered dependency gaps; and any retirement, new-work, or verification-review obligations. /reconcile owns graph traversal, propagation, work-package persistence, and handoff to normal delivery.
- **Resume and overlap:** On resumption, re-read current artifacts and the open work package before editing. If another reconciliation already made the same effective change, merge/supersede the obligation and report UNCHANGED. If accepted deltas conflict or the current artifact no longer matches the assumed baseline, return HUMAN_DECISION_REQUIRED for that path. Never replay a stale patch blindly.

This mode restores the truth of existing planning artifacts and records obligations. It does not certify that code or prior evidence still satisfies the revised authority; the dispositions, propagation boundaries and evidence rules below govern that assessment.

### Locked design — impacted-artifact disposition

Track the result for each existing candidate **in the reconciliation work package**, separately from its normal artifact lifecycle state. This is a per-reconciliation assessment, not a second global lifecycle state machine.

| Disposition | Meaning |
| --- | --- |
| `UNCHANGED` | Checked against the accepted authority delta and remains truthful as written; no artifact edit. |
| `REVISED` | Existing artifact was minimally updated under RECONCILE_ONLY; record the effective semantic delta. This does not mean code or verification obligations are complete. |
| `DECISION_REQUIRED` | Impact, authority, or the required revision cannot be settled confidently; preserve the artifact and record the exact human decision needed. The affected path remains blocked while independent work may continue. |
| `RETIRE_REQUIRED` | Existing planned work has become obsolete; retain its history and record the obligation to move it to the eventual retirement lifecycle state. Do not delete it. |

`NEW_WORK_REQUIRED` is a work-package obligation, not the disposition of a nonexistent artifact. Normal artifact lifecycle and retirement transitions will be specified under Point 05.

The RECONCILE_ONLY agent's `CHANGED` result is recorded as `REVISED` in the work package; its `HUMAN_DECISION_REQUIRED` result is recorded as `DECISION_REQUIRED`. A disposition describes the current result of this reconciliation assessment, not whether delivery has been implemented or freshly verified.

### Locked design — previous verification evidence after reconciliation

A passing test run or human acceptance remains a historical observation. Its **applicability to a current claim** is what reconciliation reassesses. Evidence becomes inapplicable the moment the accepted claim it was used to prove changes, even if implementation and tests have not yet changed. /reconcile does not execute tests or claim new verification.

- Assess applicability per **claim-to-evidence association**, not per whole test run. One integration or E2E run may support several Spec or Feature claims. If only SPEC-A's claim changes, its association becomes invalid for the revised claim; the same run may still support SPEC-B's unchanged claim, provided the test behavior, relevant implementation, environment and assumptions still support B. Preserve the run and its history. A shared changed premise or changed assertion may affect both associations; assess them rather than assuming B is safe.
- A revised requirement, contract, architecture assumption, acceptance criterion or governing authority invalidates previous evidence for the affected claim. A new expected behavior requires the appropriate tests/acceptance checks to be updated and run through normal delivery. A purely editorial revision that leaves the claim and its premises unchanged does not invalidate evidence.
- For changed shared behavior, evaluate the evidence associations of actual dependents. Require targeted Spec checks and relevant Feature integration/E2E or human acceptance where the affected claims need them; do not automatically discard an entire suite's results or demand a full project rerun. Ordinary implementation changes classified NORECONCILENEEDED still use the normal verification process.
- If a candidate artifact is UNCHANGED and its claim, tested behavior and relevant premises remain valid, retain its evidence association as applicable. If applicability cannot be established confidently, record the precise uncertainty and return HUMAN_DECISION_REQUIRED for the affected path; do not silently count that evidence as current.
- In the reconciliation work package record affected claim(s), prior evidence reference(s), applicability decision and reason, and the required reverification scope. Treat reverification as a mandatory delivery obligation, not as an impacted-artifact disposition or a second artifact lifecycle state. Do not mark affected acceptance as currently verified/complete while its required evidence is outstanding; the exact lifecycle representation belongs to Point 05.
- Reverification obligations follow the existing reconciliation overlap rule. Match obligations for the same effective claim and verification target; merge compatible outstanding work with links to every originating REC record. If a later accepted delta changes that target, supersede the obsolete target/obligation with the latest one while retaining its history. If accepted deltas conflict or the required target is uncertain, escalate under HUMAN_DECISION_REQUIRED rather than opening competing obligations. Close the effective obligation only when fresh applicable evidence is produced through the normal /implement → /verify → /review path.

The exact evidence metadata and Feature verification criteria are deferred to Points 05 and 09; they must preserve these claim-level applicability and overlap semantics.

### Locked design — propagation through dependents and stopping

- From the approved authority root(s), /reconcile computes the bounded downstream candidate closure **once** using the persisted hierarchy and explicit reverse dependencies. Candidate discovery is deterministic; semantic search does not construct or recursively expand the graph. Classify the candidates for effective impact, preserving unchanged artifacts and independent paths.
- The accepted authority delta is the input to root assessment. A `REVISED` artifact passes only its effective semantic/contract delta to dependent candidates. `UNCHANGED` passes no new delta along that path; a candidate reached independently by another changed path is still assessed. Combine compatible incoming effects on one candidate and record one disposition/obligation for the effective work; conflicting effects require HUMAN_DECISION_REQUIRED.
- `RETIRE_REQUIRED` preserves the obsolete work's history and records its retirement obligation; evaluate existing dependents whose premise changes. `DECISION_REQUIRED` suspends the affected path and records the precise human decision as an open obligation. Continue independent paths. Do not guess past a blocked decision or count it as resolved.
- `NEW_WORK_REQUIRED` is a delivery obligation handed to normal authoring/grooming. It is not a newly authored graph node for this /reconcile run and does not recursively expand reconciliation. Reverification obligations likewise pass to normal delivery.
- Once candidate assessment reaches `UNCHANGED`, `REVISED` with all relevant existing dependent paths assessed, `RETIRE_REQUIRED` with its dependent impact assessed, or a recorded blocked `DECISION_REQUIRED` path, perform **one bounded consistency safety scan** for stale references or undeclared coupling. A discovered `DEPENDENCY_GAP` is recorded and its persisted metadata repaired; assess any newly identified impact before declaring the work package assessment complete. This is a bounded correction, not a repeated repository-wide discovery loop. If its impact or repair cannot be settled, record HUMAN_DECISION_REQUIRED for that path.
- /reconcile may finish when the accepted authority updates and all known candidate/effective-change paths have been assessed or explicitly blocked, the bounded safety scan and any discovered gap assessment have been handled, and the reconciliation work package durably records every remaining human decision and delivery obligation. It does **not** wait for implementation, new-work grooming, retirement execution, or reverification. The work package stays open until mandatory obligations are resolved; affected work cannot be claimed complete while its obligations remain.

## [x] 02 — Dependency & Impact Model

### Why this matters

Reconciliation and context selection cannot work reliably unless Kilo understands how project artifacts depend on one another.

The normal hierarchy is:

Epic → Feature → Spec → Implementation → Tests

But dependencies may also exist sideways, for example:

- SPEC-A depends on SPEC-B.
- FEATURE-A depends on a Platform Feature.
- SPEC-C is governed by an Architecture Decision.

### Established constraints from Point 01

- Dependency relationships required for reconciliation must be available deterministically from persisted artifact relationships/metadata; /reconcile must not reconstruct the graph from semantic search.
- The dependency graph may be calculated in memory from authoritative artifact metadata; a separately maintained duplicate graph is not required by Point 01.
- Semantic inspection remains a bounded safety/impact mechanism, not the primary dependency-discovery mechanism.
- Dependency metadata must be maintained during authoring/grooming and receive a lightweight local audit at readiness gates.
- Silent dependency gaps remain an accepted residual risk; when discovered they must be surfaced as DEPENDENCY_GAP and repaired.

### Locked design — dependency relationships (Point 02.1)

- **Contains:** The structural parent/child relationship (for example, Epic → Feature → Spec). Derive it deterministically from the artifact's persisted ID/location convention; authors do not maintain a separate `contains` field. Point 05 defines the exact identity/location format. This relationship is available to reconciliation as a persisted structural fact, not guessed from semantic search.
- **Governed by:** An artifact is constrained by an accepted authority decision, whether an ADR, a PRD clause, an Epic policy or another authoritative decision. This is not ADR-specific. The governing decision must be identifiable from authoritative metadata; Point 05 defines its exact reference shape.
- **Depends on:** An artifact relies on another artifact's decision, behavior or contract remaining true. This can cross parent/Feature boundaries; the precise cross-Feature audit rule remains open below.

These are the only relationship meanings required at this level. A link makes an artifact a **candidate** for impact assessment, not automatically an impacted artifact. Point 01's effective-delta and semantic classification rules still apply. Test/evidence associations are assessed per claim under Point 01's evidence rules; they are not an additional dependency type here.

### Locked design — cross-cutting concern coverage (Point 02.6)

- A cross-cutting concern is represented by an accepted authority decision (for example an ADR, PRD clause or Epic policy). It does not create a new dependency type.
- Use the existing **Governed by** relationship to declare applicability. Persist it at the highest artifact scope where the policy applies uniformly. Descendants inherit that governing context through the derived Contains hierarchy.
- If applicability begins only at a narrower scope, declare Governed by at that narrower Feature or Spec rather than widening scope merely to reduce metadata.
- Inherited governance is derived coverage, not another persisted edge. Kilo may report that a descendant is governed through an ancestor while preserving the ancestor's Governed by edge as the authoritative fact.
- Do not maintain a mirrored authority-side `governs` list. Reverse lookup derives affected scopes from authoritative Governed by references and structural containment.
- **Explicit exemption is supported as a governance-coverage override, not a fourth dependency relationship.** An artifact may declare `Exempted from <authority-ref>` when an inherited authority deliberately does not apply at that scope. The exemption suppresses inheritance for that authority only; all other inherited authorities remain in force.
- Exemption is explicit and positive metadata. Absence of Governed by or absence of enforcement must never be interpreted as an exemption.
- **An exemption cannot self-authorize.** Every `Exempted from <authority-ref>` declaration must carry an `Authorized by <decision-ref>` reference to an accepted decision with sufficient authority to permit that override. `Authorized by` is authorization metadata for the exemption, not a new dependency type.
- **Authorization must explicitly address the override.** The authorizing decision must explicitly reference either the governing authority being overridden or the specific scope/artifact receiving the exemption. Merely pointing to an unrelated accepted decision at a qualifying authority tier is invalid.
- If no accepted decision explicitly authorizes the exemption, or the authorization's applicability is ambiguous, the artifact cannot treat the exemption as effective and readiness must raise HUMAN_DECISION_REQUIRED rather than silently accepting it.
- Changes to either the governing authority or the authorizing decision make the exemption's effective coverage subject to reconciliation through the normal authority/dependency rules.
- A narrower descendant may re-enter the authority's coverage only through an explicit direct Governed by declaration for that authority; do not infer re-entry automatically below an exemption.
- Readiness grooming resolves effective governing context from direct Governed by references, inherited governing context, and explicit exemptions. Missing or contradictory coverage is surfaced as DEPENDENCY_GAP; unresolved ambiguity follows HUMAN_DECISION_REQUIRED.
- Authority changes enter reconciliation through authoritative Governed by edges. Structural descendants in effective coverage become candidates through Contains; exempted subtrees are excluded for that authority unless a descendant explicitly re-enters coverage. Candidate status still does not imply effective impact; Point 01 semantic classification applies.
- Point 02.6 owns only deterministic policy applicability/coverage. Point 10 owns how any resulting Platform, Enabler, shared-infrastructure or ordinary Feature work is packaged and scheduled.

This preserves the Point 02.1 relationship model while making cross-cutting exceptions first-class and deterministic.

### Locked design — upstream dependency discovery (Point 02.3)

- **At authoring/grooming:** Starting from the artifact's derived parent and accepted authority, identify decisions, behavior and contracts that the artifact actually relies on. The authoring workflow records the relevant Governed by and Depends on references on the dependent artifact. This is the bounded semantic identification pass; it does not maintain a mirrored reverse list.
- **At readiness:** Audit the artifact locally against its parent, declared dependencies and immediately relevant authority/context. Inspect more broadly only when that audit reveals uncertainty or possible missing coupling. Do not repeatedly run repository-wide semantic discovery at every lookup.
- **At lookup:** Derive the structural parent from persisted ID/location and follow declared Governed by/Depends on references upstream as needed. A missing relationship is not inferred from code, prose search or file proximity to manufacture a resolved graph edge. Point 01's bounded safety scan can discover a DEPENDENCY_GAP; repair its authoritative metadata and reassess affected work.
- **Target not yet authored:** Record a pending dependency describing the required contract, expected owner if known, and work needed to establish it. Do not put a nonexistent target ID in a resolved-looking Depends on reference. If an existing accepted authority already settles the contract, reference that authority; link the eventual target when it exists. If the necessary contract remains undecided, the dependent artifact cannot pass readiness.
- **Make the blocker actionable:** An undecided contract in a pending dependency creates or links to a tracked grooming obligation in the expected owner's scope, using the existing required-work handoff pattern. Avoid duplicate obligations for the same effective work. If the owner or decision cannot be identified confidently, use the standing HUMAN_DECISION_REQUIRED rule and keep that path blocked. When the target and contract exist, replace the pending entry with the real reference and repeat the local readiness audit.

Point 05 defines the exact pending-reference, obligation and lifecycle representation. The cross-Feature audit boundary and cross-cutting policy coverage remain open under their own Point 02 items.

### Locked design — cross-Feature dependencies (Point 02.5)

- A cross-Feature dependency is **not a separate dependency type**. It is an ordinary `Depends on` relationship whose target happens to belong to another Feature or Epic. The same dependency semantics, readiness audit, reverse lookup and reconciliation rules apply across boundaries.
- **Declare the dependency at the lowest artifact that genuinely owns the reliance.** If one Spec relies on another Feature's Spec-level contract, persist Spec → Spec. Persist Feature → Feature only when the consumer Feature as a whole genuinely relies on the provider Feature's capability or contract.
- **Do not auto-promote or duplicate derived relationships.** Repeated Spec-level dependencies do not create a separately persisted Feature-level dependency, and transitive closure is not persisted merely for convenience. Higher-level Feature/Epic dependency views are derived from authoritative edges when needed.
- **Multiplicity does not change ownership level.** Ten independent Spec-level dependencies on another Feature remain ten authoritative Spec-level dependencies if each reliance genuinely belongs to those Specs. A Feature-level dependency exists only when there is a real Feature-level invariant or contract owned at that level.
- **Derived roll-up is informational, not authoritative.** Kilo may report that Feature A depends on Feature B through multiple lower-level edges for grooming, context or impact summaries, but reconciliation traverses the underlying authoritative edges rather than treating the roll-up as another dependency.
- **A later-discovered Feature-level invariant does not collapse existing lower-level edges.** Add the genuine Feature-level dependency alongside the existing Spec-level edges as its own authoritative fact. Existing Spec-level edges remain unchanged unless someone deliberately re-scopes their ownership; never merge or delete them merely because a higher-level contract was discovered.
- **Provider implementation is not automatically a grooming prerequisite.** A consumer may proceed once the contract it relies on satisfies the lifecycle/readiness condition required for safe consumption; **Point 05 must define the exact state vocabulary and lifecycle condition for that contract.** Point 02 establishes only the dependency semantics and must not invent an independent “accepted/stable” state.
- If the required target or contract does not yet satisfy that Point-05-defined condition, use Point 02.3's pending-dependency and tracked grooming-obligation rules. The consumer cannot pass its relevant readiness gate while the required contract remains undecided.
- Dependency ordering does not automatically equal implementation ordering. A consumer may be implemented against a sufficiently established contract before the provider is complete, but it cannot be claimed fully integrated/verified/complete while required provider capability or integration evidence remains outstanding. Points 05 and 09 define the exact lifecycle/completion representation.
- Provider changes propagate through the actual declared cross-Feature edge using Point 01's deterministic reverse lookup and semantic impact classification. Crossing a Feature or Epic boundary does not itself make a candidate impacted.
- **Dependency cycles are readiness blockers when they prevent either side from establishing a usable contract independently.** Kilo must not invent execution ordering to hide the cycle. First check whether the contract belongs under an existing shared/higher authority or whether decomposition/ownership is wrong; if the correct resolution cannot be determined confidently, return HUMAN_DECISION_REQUIRED.
- **Cycle detection is an ongoing invariant, not a one-time grooming check.** Re-run the relevant cycle check whenever a new or changed dependency edge is persisted, including during later grooming, reconciliation metadata repair, or dependency-gap repair. A previously READY artifact may therefore require readiness re-evaluation if a later edge introduces a blocking cycle; Point 05 defines the exact lifecycle transition/state effect.

This keeps cross-Feature coupling explicit without creating a second dependency model or a duplicated Feature-level graph.

### Locked design — meaningful impact for dependency traversal (Point 02.7)

- **Point 02.7 owns propagation candidacy, not the reconciliation decision.** It answers whether an effective semantic delta on the source side of a relationship touches the premise represented by that relationship strongly enough that the dependent/covered artifact must be reconsidered as a candidate. Point 01's `/shouldreconcile` remains solely responsible for deciding whether the requested change warrants reconciliation.
- **Universal premise test:** a change propagates across a relationship only when the effective semantic delta changes a premise represented by that relationship. "Artifact changed" is not equivalent to "dependency premise changed."
- **Depends on:** propagate when the provider's behavior, contract, invariant or decision actually relied upon by the consumer changes. Internal refactoring, logging, formatting, implementation-detail changes or other non-observable changes do not propagate when the relied-upon premise remains unchanged.
- **Governed by:** apply the same semantic-delta rule to authority documents. Propagate only when the enforceable constraint changes — what the governed scope is required, permitted or forbidden to do, or the applicability of that constraint. Typographical fixes, rationale clarification, examples, section reordering or wording cleanup that do not change the effective rule do not propagate.
- **Contains:** containment alone does not mean every descendant is impacted whenever an ancestor changes. Contains provides the structural path for effects such as inherited governance, decomposition/retirement or other structural deltas; propagation still requires that the effective delta changes a premise relevant to that descendant.
- **Governance overrides:** `Exempted from` / `Authorized by` remain governance-coverage metadata rather than dependency types. Reconsider coverage when the governing rule, exemption, authorizing decision or their applicability changes in a way that may alter the effective governing context.
- **Safe ambiguity default:** when Kilo cannot determine confidently whether the semantic delta touches the represented premise, propagate the artifact as a candidate rather than silently suppressing it. This conservative step does not itself mean the artifact is impacted or that reconciliation is required; subsequent semantic classification and `/shouldreconcile` retain those decisions. If the ambiguity itself requires an authority decision to resolve, use the standing HUMAN_DECISION_REQUIRED rule.
- A propagated candidate may still classify as unchanged after inspection. Candidate propagation is therefore intentionally broader than effective impact.
- Point 05 owns the exact lifecycle/state consequences of material versus non-semantic artifact changes. Point 02.7 defines only the dependency-traversal meaning of "meaningful impact."

**Concrete anchor:** if Spec B depends on Spec A's `CreateOrder(request) -> OrderId` contract, renaming a private class, adding tracing or optimizing persistence does not propagate when observable behavior is unchanged. Changing the request schema, response semantics, accepted-input invariant or removing behavior B relies on does propagate B as a candidate. The same distinction applies to authority artifacts: "must support OAuth2" → "must support OAuth2 with PKCE" propagates; reorganizing the ADR or clarifying its rationale without changing the enforceable rule does not.

### Determine

- [x] Which dependency types actually matter — Contains, Governed by, and Depends on, as defined above.
- [x] How dependencies are represented — hierarchy derived deterministically from persisted artifact ID/location plus declared dependency metadata; derive the graph in memory rather than maintaining a duplicate graph file. Exact field schema belongs to Point 05.
- [x] How upstream dependencies are discovered — authoring/grooming identification, local readiness audit and persisted-reference lookup, with pending targets linked to tracked grooming obligations as defined above.
- [x] How downstream impact is discovered — one-time deterministic reverse lookup and candidate closure over persisted relationships; semantic classification follows candidate discovery.
- [x] How cross-feature dependencies work.
- [x] How cross-cutting concerns are represented.
- [x] What constitutes a meaningful impact.
- [x] Which dependencies must be persisted — the structural ID/location must make hierarchy derivable, and explicit Governed by/Depends on relationships needed for candidate discovery must be persisted in authoritative artifact metadata. No separate authored Contains field or duplicate graph is required. Other safe-inference boundaries remain open below.
- [x] Which dependencies can simply be inferred when needed — safe inference is limited to deterministic, lossless derivation from authoritative persisted facts. Kilo may derive structural ancestry/descendants from artifact identity/location; inherited and effective governance from direct Governed by, containment, exemptions and explicit re-entry; reverse dependents from declared Depends on/Governed by references; transitive closures for reconciliation/context assembly; and informational higher-level roll-ups from underlying authoritative edges. Derived relationships are computed when needed and are not persisted as duplicate authoritative edges.
- [x] Kilo must not infer semantic Depends on or Governed by relationships from code, prose similarity, naming, file proximity, call patterns or architectural intuition; must not infer exemptions or authorization; must not promote lower-level dependencies into authoritative higher-level dependencies; and must not turn pending dependencies into resolved references without an accepted target/contract. If semantic inspection reveals a missing relationship, record DEPENDENCY_GAP, repair authoritative metadata and recompute derived views. If the correct relationship cannot be established confidently, use HUMAN_DECISION_REQUIRED.
- [x] Structural changes are deltas, not harmless inference updates. If an artifact's persisted identity/location changes in a way that changes its derived Contains relationship (for example, reparenting a Spec to another Feature or a Feature to another Epic), treat that structural change as an effective dependency-context delta. Recompute inherited/effective governance, ancestry-dependent context and derived roll-ups, then propagate candidates wherever those effective premises change. The move does not require a persisted Contains edge, but it must not be treated as a purely mechanical rename/move with no impact assessment.
- [x] Persistence rule: **Persist meaning; derive mechanics — but when the authoritative facts from which mechanics are derived change, reassess the semantic consequences of the derived relationships.**
- [x] How dependency information participates in reconciliation — Point 01's deterministic candidate traversal, effective-delta propagation, bounded safety scan and DEPENDENCY_GAP repair.

### Expected outcome validation

Point 02 was acceptance-checked end-to-end against three representative change paths:

1. **Ordinary contract dependency:** `SPEC-CHECKOUT` explicitly Depends on `SPEC-ORDER-CREATE`'s `CreateOrder(request) -> OrderId` contract. A material request/response/invariant change makes Checkout a deterministic downstream candidate; internal refactoring, tracing or persistence changes that preserve the relied-upon premise do not. Cross-Feature roll-ups may be derived for reporting but do not create duplicate authoritative Feature-level edges. Candidate status still does not mean rewrite or reconciliation disposition; Point 01 performs semantic classification.

2. **Structural/derived relationship change:** reparenting an artifact changes its derived Contains relationship even if artifact content does not change. Kilo recomputes ancestry, effective governance and derived roll-ups and propagates candidates only where those effective premises change. This validates that deterministic structural edits cannot silently alter semantic context without impact assessment.

3. **Governance/exemption/authorization chain:** `FEATURE-A` is Governed by `ADR-007`; `SPEC-CHECKOUT` inherits that governance but declares `Exempted from: ADR-007` with `Authorized by: ADR-009`, where ADR-009 explicitly permits the override. Effective coverage therefore excludes SPEC-CHECKOUT. If ADR-009 later revokes that authorization, the authorization premise changes, the exemption becomes ineffective, ADR-007 coverage is recomputed as active, and affected artifacts become candidates under the normal premise test. An exemption without valid explicit authorization does not suppress inherited governance; unrelated authority wording changes do not alter coverage; ambiguity uses HUMAN_DECISION_REQUIRED. A change to ADR-007 itself correctly does not propagate into a subtree that remains validly exempt from ADR-007, because that subtree is not effectively governed by it.

Together these checks exercise ordinary dependency traversal, structural derived-context change, and the full Governed by → Exempted from → Authorized by chain while preserving the core distinction:

> **candidate ≠ effective impact ≠ required rewrite/reconciliation disposition**

Enough dependency information now exists for Kilo to answer:

> **If this changes, what actually needs reconsideration?**

without attempting to construct a universal software dependency graph.

## [x] 03 — Context Freshness & Context Management

### Why this matters

Large-project AI workflows eventually fail if every agent receives either too little context, causing incorrect decisions, or too much context, increasing token consumption and distracting the model with irrelevant information.

v0.2 needs deliberate context management.

### Locked design — stage context requirements (Point 03.1)

Each workflow stage starts from a **minimum-sufficient context contract**: its direct authority chain, its immediate working artifact(s), and only the dependency/governing context materially relevant to the task. Broader project context is discovered on demand rather than preloaded.

| Workflow stage | Mandatory starting context | Loaded only when relevant |
| --- | --- | --- |
| **Ideation** | Project identity, existing/resumed Ideation artifact, previously answered and unresolved questions | Prior research, existing-product/code context when evolving an existing system rather than starting greenfield |
| **PRD authoring** | Completed Ideation artifact in full | Relevant research/evidence referenced by Ideation; existing PRD only during reconciliation |
| **Architecture** | **PRD in full**, existing accepted ADR index/summary | Full specific ADRs, technical research, existing code/repository facts needed for an architectural decision |
| **Epic grooming** | Relevant PRD sections, applicable architecture/ADRs, Epic artifact | Cross-cutting authorities and dependencies affecting that Epic |
| **Feature grooming** | Parent Epic, relevant PRD requirements, applicable architecture/governance, Feature artifact | Other Features/contracts on which the Feature depends |
| **Spec grooming** | Parent Feature, directly relevant Epic/PRD requirements, applicable ADR/governance, Spec artifact, declared dependencies/pending dependencies | Full dependency artifacts when their contracts cannot be understood from bounded references/contract summaries |
| **Implementation** | Current Spec in full, directly applicable authority/contracts, implementation workspace/code relevant to the Spec | Related source files, dependency Specs/contracts, ADR details, tests and prior implementation notes discovered as needed |
| **Verification** | Current Spec/Feature acceptance claims, implementation under test, relevant test/evidence context | Dependency/provider evidence, affected ADR/PRD clauses and broader regression context when required |
| **Review** | Artifact/work being reviewed, governing requirements, relevant verification evidence | Parent/adjacent artifacts where consistency must be checked |
| **/shouldreconcile** | Proposed change, artifact/decision it appears to affect, enough authority context to classify whether accepted truth changes | Dependency information only where needed to determine whether this is an authority-level change rather than ordinary implementation work |
| **/reconcile** | Accepted change, authority root, current reconciliation work package, authoritative artifact/dependency metadata required for deterministic candidate discovery | Full candidate artifacts as each candidate is semantically assessed; bounded consistency-scan context |
| **Resume / CONTINUE** | Current authoritative artifact, durable workflow checkpoint/state, unresolved decisions/obligations | Prior conversation only when it contains information not yet persisted; that condition is a workflow defect rather than normal context |

The following rules are locked for stage-level context assembly:

1. **Stage-scoped contracts.** Each workflow stage has a defined mandatory starting set and an on-demand expansion set.
2. **Working artifact in full.** The artifact currently being authored, reconciled or verified is not reduced to a summary.
3. **Authority/dependency context is relevance-scoped.** Load the governing decision or relied-upon contract rather than automatically loading the complete source artifact.
4. **PRD → Architecture asymmetry.** Architecture always receives the full PRD because system-wide requirement interactions can be hidden by aggressive slicing. Downstream Epic, Feature, Spec and implementation stages remain bounded.
5. **Broader context is pull-based.** Additional context is discovered only when the starting context exposes a genuine need; unrelated project knowledge is not preloaded.
6. **Persisted project truth beats conversational memory.** A stage must be reconstructable from repository/workflow state alone after a fresh session, including weeks or months later. Chat history may assist conversational continuity but is not authoritative project context.

Structural ancestry does not by itself justify loading every ancestor artifact. Point 02's Contains, Governed by and Depends on relationships identify where relevant context may come from, but context assembly still selects only the authority decisions, contracts and artifact content necessary for the current stage.

This point deliberately does **not** yet define snippet/reference representation, freshness markers, stale-context detection, context ceilings, retrieval mechanics or token-budget rules; those remain under the later Point 03 questions.

### Locked design — agent context requirements (Point 03.2)

An agent's context is the context contract of the workflow stage it is executing (per Point 03.1), plus the minimum role-specific context required to exercise that agent's authority.

The following rules are locked:

1. **Stage context + role overlay.** The workflow stage defines the base context contract; the agent receives only the additional role-specific context required to exercise its authority. Point 03.2 does not duplicate complete stage-context contracts per agent.
2. **Delegation is bounded, not inherited.** Agents do not inherit the caller's full context. Delegation assembles a deliberate, bounded context packet rather than copying the parent's conversational or working context.
3. **Fresh-review agents deliberately receive less.** Adversarial/fresh-review agents receive the reviewable artifact plus its governing contract, with factual evidence retrieved on demand. They do not receive the author's reasoning trail or preferred conclusion.
4. **Context follows authority, not model identity.** Model variants performing the same logical role use the same context contract. Switching model/provider does not change what project truth the role is entitled or required to receive.
5. **Durable reconstruction is mandatory.** All mandatory agent context must be reconstructable from durable project/repository state. Prior chat history may assist conversational continuity but must never be the only source of required project truth.

#### Illustrative current-agent mapping — non-normative

The current working agents can be understood under these rules as follows: Planner and Planning Worker consume the applicable planning-stage context plus their delegated workflow/mode state; Builder consumes implementation-stage context plus relevant workspace state; Debugger consumes the exact failure/reproduction evidence plus affected contracts and implicated code/tests/configuration; adversarial agents consume the smallest artifact + governing contract; reviewers consume the current change, governing requirements and verification evidence; smoke orchestration/execution agents consume only the smoke state and delegated workflow context required for their responsibilities.

This mapping is **illustrative only** and does not establish the final v0.2 agent roster, names or ownership boundaries. Those are reserved for **Point 07 — Commands & Agents**. Any final agent defined there must conform to the context rules above.

The existing `planning-worker.md` RECONCILE_ONLY wording discrepancy is noted for Point 07 and is deliberately not resolved under Context Management.

### Locked design — mandatory versus optional context (Point 03.3)

Context classifications are **conceptual reasoning labels only**, not persisted artifact metadata or schema fields. No classification machinery is added unless later design work under Points 05 or 07 demonstrates a concrete need for it.

Use these context classes when assembling or reasoning about a stage/agent request:

- **MANDATORY_START** — required before the stage or agent can begin meaningful work.
- **MANDATORY_ON_DEMAND** — not required initially, but becomes mandatory once work in progress establishes its relevance; retrieve it before the affected decision and never guess around it.
- **OPTIONAL** — safely omittable without changing correctness, authority or valid completion; omission may reduce speed, convenience or explanatory richness only.
- **EXCLUDED** — deliberately withheld by the role contract because receiving it would compromise the role's purpose. Exclusion is a deliberate design choice, not another form of optional context.

The following rules are locked:

1. **Correctness test.** If omitting context could cause violation of accepted requirements, authority, dependency contracts, current workflow state or acceptance criteria, that context is mandatory.
2. **Mandatory does not mean preload.** MANDATORY_ON_DEMAND exists specifically so correctness does not require preloading every potentially relevant artifact or dependency.
3. **Relevance promotes context.** When the current work exposes a material dependency, governing decision, unresolved obligation, external contract or factual prerequisite, the necessary source becomes mandatory for that decision path.
4. **No guessing past missing mandatory context.** If mandatory context cannot be retrieved, stop the affected decision path. If the issue is genuinely ambiguous rather than merely unavailable, use the standing HUMAN_DECISION_REQUIRED principle.
5. **Optional context cannot secretly carry authority.** If material initially treated as optional reveals an authoritative fact, retrieve the relevant authoritative source and treat it as mandatory before relying on that fact.
6. **Optional means safely omittable.** Removing optional context must not change what the agent is authorized to decide, whether its result is valid, or whether completion can legitimately be claimed.
7. **Chat history remains non-mandatory.** Required project truth must be reconstructable from durable repository/workflow state. Prior conversation may help continuity but must never be the only source of mandatory context.

Core rule:

> **Context is mandatory when correctness, authority, or valid completion depends on it. Mandatory context may be required at stage entry (MANDATORY_START) or become mandatory once the work in progress establishes its relevance (MANDATORY_ON_DEMAND). Context is OPTIONAL only when it can be safely omitted without changing the validity or authority of the result. Role contracts may additionally EXCLUDE context that would compromise the role's purpose.**

### Locked design — context freshness establishment (Point 03.4)

Context freshness is established by resolving every mandatory context item from its current authoritative source when the task context is assembled — not by how recently that text happened to be generated. Freshness is tied to current source content, including uncommitted working-tree state, rather than conversation age, cached summaries, or Git commit time alone. Each agent invocation works from a bounded fresh snapshot assembled at start; mandatory context discovered later (`MANDATORY_ON_DEMAND`) is freshly resolved at the moment it becomes relevant, never pulled from an earlier cached copy. Delegation always re-establishes freshness independently — a caller passes task intent, identifiers, scope and workflow mode, never its own already-expanded context as if it were authoritative.

The following rules are locked:

1. **Assembled, not inherited.** Every invocation reconstructs mandatory context from current repository/workflow state according to Points 03.1–03.3. It never assumes that prior conversation context, an earlier agent invocation, a cached summary or a previous execution still represents current project truth.
2. **Resolve at assembly time.** For each `MANDATORY_START` item, determine its authoritative source, resolve its current location/reference, read its current content or required portion, and record which source revision supplied it. Apply the same rule to `MANDATORY_ON_DEMAND` context when relevance is established.
3. **Working tree, not just commits.** Freshness identity is conceptually the artifact/reference plus a fingerprint of its current content, including uncommitted working-tree changes, rather than merely a Git commit SHA. Exact hash/fingerprint mechanics are deferred to implementation design and are not decided here.
4. **Bounded snapshot per invocation.** Once assembled, the initial packet is the current-project-truth snapshot for that invocation. Kilo does not continuously re-read every source while the agent is reasoning. Newly required `MANDATORY_ON_DEMAND` context joins the snapshot when retrieved. Changes that occur after assembly and how they are detected belong to Point 03.5.
5. **Summaries/references do not self-certify freshness.** A summary, compact contract or stored reference may be used as context representation where later rules allow it, but when it is mandatory its freshness must be established against the current authoritative source rather than trusted because the representation was generated previously.
6. **Delegation re-resolves independently.** A delegated agent receives task intent, identifiers, scope and workflow mode, then assembles its own stage + role context from current authoritative state. The caller's already-expanded context is not inherited as authoritative truth. This prevents stale context from cascading through agent chains, including future cross-model handoffs.

Core rule:

> **Freshness means current authoritative source truth was resolved for this invocation, not that the text happens to be recent.**

### Locked design — stale information detection (Point 03.5)

Context becomes stale when an authoritative source the current reasoning depends on no longer matches the source revision resolved into the invocation — not by elapsed time. Detect this through targeted source-fingerprint revalidation at meaningful workflow boundaries; refresh only the affected context; reassess only the reasoning that depended on the changed source.

The following rules are locked:

1. **No continuous polling.** Checks happen at workflow boundaries, not continuously while an agent is reasoning.
2. **Mandatory context carries resolved-source identity.** Conceptually record artifact/reference + source location + content fingerprint for mandatory context. Exact hashing/fingerprint mechanics remain deferred to implementation, per Point 03.4.
3. **Revalidate at meaningful boundaries.** Re-check relevant mandatory-source fingerprints before finalizing a stage result; when `MANDATORY_ON_DEMAND` context is pulled into an active invocation; when resuming after interruption/checkpoint; and when the workflow observes out-of-band repository/worktree changes.
4. **Changed fingerprint requires re-read.** Once the authoritative source no longer matches the resolved source identity, do not continue relying on the old copy, summary, contract extract or cached representation. Re-read the authoritative source.
5. **Use targeted invalidation.** A stale source does not invalidate the entire context packet automatically. Refresh that source and revisit only reasoning or outputs that actually depended on it.
6. **Semantic change, not byte change, determines impact.** A content fingerprint change triggers refresh, but the refreshed source may prove semantically unchanged for the current task (for example spelling or formatting cleanup). In that case existing reasoning may remain valid. A changed governing decision or contract requires the affected reasoning to be reassessed.
7. **An agent's own expected edits are not external staleness.** Deliberate writes to the invocation's active output/implementation targets are tracked as part of that work, not treated as an authority/source changing underneath it.
8. **Derived representations inherit source freshness.** A summary, compact contract or extract derived from source fingerprint A becomes stale when the authoritative source becomes fingerprint B until it is validated or regenerated against the current source. Points 03.6/03.7 decide when such representations are allowed.
9. **Do not guess through genuine conflict.** After refresh: if the work remains valid, continue; if affected reasoning can be deterministically recomputed, redo that path; if the changed authority creates genuine ambiguity or conflicting accepted truth, use the standing `HUMAN_DECISION_REQUIRED` principle.

Explicitly excluded from v0.2 stale detection: filesystem watchers, background refresh, TTLs, context-age rules, periodic rescanning and a separate stale-context database.

Core rule:

> **Context becomes stale when an authoritative source on which the current reasoning depends no longer matches the source revision resolved into the invocation. Detect this through targeted source-fingerprint revalidation at meaningful workflow boundaries, refresh only affected context, and reassess only reasoning dependent on the changed source.**

### Locked design — when full artifacts are needed (Point 03.6)

Load an artifact in full only when the task requires understanding, modifying, validating, or judging the artifact as a whole, or when its relevant semantics cannot be safely isolated. Otherwise, consume only the relevant authoritative portion or contract.

“Mandatory” under Point 03.3 determines **whether** context is required; it never determines representation size. Mandatory context may therefore be satisfied by a bounded authoritative portion when that portion safely carries everything needed for correctness, authority and valid completion.

The following rules are locked:

1. **Active working artifact is always full.** Preserve Point 03.1: the artifact currently being authored, groomed, implemented against, reconciled, verified as the primary object, or reviewed as the primary object is loaded in full.
2. **Architecture still receives the full PRD.** Preserve the deliberate Point 03.1 asymmetry because system-wide requirement interactions may be hidden by aggressive PRD slicing.
3. **Reconciliation candidate assessment requires the full candidate artifact.** /reconcile must judge whether the candidate remains truthful as written under the accepted authority delta; a preselected snippet could hide a contradictory premise elsewhere in the same artifact.
4. **Full dependency/authority artifacts are required only when their relevant semantics cannot be safely bounded.** A clean, self-contained contract such as `CreateOrder(request) -> OrderId` may be consumed as bounded authoritative context. If the contract is ambiguous, qualified elsewhere, distributed across sections, or cannot be interpreted safely without surrounding decisions, expand that source and, if necessary, load it in full as `MANDATORY_ON_DEMAND`.
5. **Whole-artifact-consistency tasks require the full artifact.** Examples include readiness review of that artifact, internal contradiction checks, post-reconciliation coherence assessment, and checking whether all of that artifact's acceptance requirements are satisfied.
6. **A relationship alone never justifies full loading.** `Contains`, `Depends on`, `Governed by` and ancestry identify candidate context sources; the current task determines how much of each source is required.
7. **Escalate representation before scope.** When bounded context proves insufficient, expand that source progressively — relevant section/contract → broader surrounding section → full artifact. Do not respond by indiscriminately loading the parent Epic, full PRD, ADR set or sibling Specs.
8. **“Full artifact” means that artifact only.** Loading a Feature in full does not automatically load its child Specs, parent Epic or referenced ADRs in full. Every additional artifact is independently evaluated under the context rules.

Core rule:

> **Need the artifact itself as the object of reasoning? Load it in full. Need only a particular accepted decision or contract from it? Use bounded authoritative context. If bounded context proves insufficient, progressively expand that source, eventually to the full artifact if required.**

### Locked design — when references are sufficient (Point 03.7)

A reference may remain unresolved when the current operation only needs the identity, location, existence, relationship, or routing information of the referenced source. Once correctness of a semantic decision depends on what the referenced source actually says, Kilo must resolve the reference and read the minimum sufficient authoritative content under Points 03.3–03.6.

The following rules are locked:

1. **References suffice for deterministic mechanics.** Artifact IDs, paths and relationship references are enough for locating artifacts, `Contains`/`Depends on`/`Governed by` traversal, candidate identification, reconciliation closure and routing. No semantic content is required merely to establish these mechanics.
2. **References are not semantic context.** A reference such as `Governed by: ADR-007` identifies where authority lives; it does not communicate what ADR-007 requires.
3. **Mandatory semantic context must eventually be dereferenced.** A reference may represent a `MANDATORY_START` or `MANDATORY_ON_DEMAND` source during assembly/discovery, but before reasoning relies on its contents Kilo must retrieve the bounded authoritative portion required for correctness, or the full artifact where Point 03.6 requires it.
4. **Do not dereference irrelevant references.** Resolve only the references whose contents materially affect the current task. The existence of additional relationships does not justify loading their source content.
5. **A resolved bounded contract is not a bare reference.** `Depends on: SPEC-ORDER-CREATE` is only a locator/relationship. Once the dependency contract matters, the current authoritative contract — for example `CreateOrder(request) -> OrderId` — must be resolved before use.
6. **Delegation prefers references over copied context.** Pass task intent, identifiers, scope and workflow state; the receiving agent resolves its own mandatory context fresh from authoritative state, preserving Points 03.2 and 03.4.
7. **Freshness metadata does not replace content.** A source fingerprint can identify which revision a reference resolves to, but it does not communicate the decision or contract contained by that source.
8. **References are sufficient only when absence of the referenced content cannot change the result.** Practical test: *could reading the referenced source change this valid result?* If no, the reference is sufficient. If yes or uncertain, resolve it as mandatory context before completing that decision path.

Persisted "reference summaries" and context-cache artifacts are explicitly not introduced here; those concerns remain for Point 03.8 and the Point 06 persistence POC.

Relationship between Points 03.6 and 03.7:

> **03.7 decides whether to open the source at all; 03.6 decides how much of it to open once needed.**

Core rule:

> **A reference is sufficient for locating or relating project truth. It is not sufficient when the agent must understand that truth to make the current decision.**

### Locked design — how duplicated context is avoided (Point 03.8)

Deduplicate by provenance, not by semantic similarity. Keep one authoritative source for each decision/contract; reference it elsewhere; resolve each required source only once at its minimum sufficient scope within an invocation; upgrade a bounded representation to full rather than holding both. No persisted convenience copies or generated summaries of authoritative project truth — re-read authoritative sources rather than maintain synchronized semantic duplicates. Disposable indexes/caches (Point 06) may accelerate lookup, but are never authoritative and must be safely rebuildable.

The following rules are locked:

1. **One authoritative home per decision/contract.** Other artifacts point to it via ID/relationship and do not copy its text merely for context convenience.
2. **No persisted context-summary convenience copies.** Do not introduce `context-summary.md`, cached ADR summaries, duplicated PRD excerpts inside Features, or equivalent durable generated summaries of authoritative project truth. This ban is fully general; there are no semantic-summary exceptions.
3. **Dependency metadata identifies, never duplicates.** For example, use `Depends on: SPEC-ORDER-CREATE#CreateOrderContract` rather than copying that dependency contract into metadata. Point 03.7 determines when the referenced contract must be dereferenced.
4. **Deduplicate within one context assembly.** Maintain an invocation-local resolved-source set conceptually keyed by source identity + current fingerprint + resolved scope. If the same source portion is reached through multiple relationships, include its content once while preserving every relationship that led to it.
5. **Broader representation subsumes narrower representation from the same source.** If a bounded portion is already loaded and the full artifact later becomes necessary, upgrade/replace the bounded representation rather than keeping both. Do not add a snippet when the full source is already present.
6. **Do not semantically deduplicate different authoritative artifacts.** Similar-looking PRD, ADR, Epic, Feature or Spec text is not assumed to be equivalent or interchangeable. Provenance determines duplication, not textual or semantic resemblance.
7. **Child artifacts may contain legitimate derived truth.** A Feature's scoped requirements or a Spec's acceptance contract are new authoritative statements at that level when they intentionally refine/decompose upstream truth. They are not treated as duplicate context merely because they trace to a PRD or parent artifact.
8. **Delegation still avoids context forwarding.** Preserve Points 03.2 and 03.4: pass task intent, identifiers, scope and workflow state rather than the caller's expanded context packet. The receiving invocation reconstructs its own minimum-sufficient fresh context.
9. **Cross-invocation caching is disposable acceleration only.** Any cache/index considered under Point 06 must remain non-authoritative, safely rebuildable and incapable of changing the logical context rules. Kilo prefers re-reading authoritative content over maintaining synchronized semantic duplicates.

Core rule:

> **Persist authoritative project truth once, reference it elsewhere, and deduplicate loaded context by provenance within each invocation. Re-reading tokens is preferable to synchronization bugs from durable semantic copies.**

### Locked design — reasonable context ceilings (Point 03.9)

Kilo should normally operate within **20–40k tokens of deliberately assembled project context**. Crossing 40k is allowed when minimum-sufficient correctness requires it and should surface context pressure where the working unit itself appears too broad. **100k tokens is the hard ceiling for one Kilo reasoning unit.** Mandatory context must never be silently discarded to fit the ceiling; if minimum-sufficient context exceeds it, the reasoning scope must be reduced before work continues. Model context-window capacity (200k, 1M, etc.) does not redefine these limits — it is safety headroom, not a budget increase.

| Kilo-managed context | Meaning | Behaviour |
| --- | --- | --- |
| ≤ 40k | Normal | Preferred operating range. |
| >40k–≤100k | Context pressure | Allowed when correctness genuinely requires it. |
| >100k | Ceiling exceeded | Must not proceed as one context packet; scope reduction is required before continuing. |

`SPEC_CONTEXT_PRESSURE` is a diagnostic signal rather than a failure. It fires when either:

1. the Spec artifact materially exceeds the existing **5–15k token guidance**, or
2. grooming, executing or verifying that Spec pushes Kilo-managed working context beyond **40k** because of the Spec's breadth or dependency surface.

Below 100k, work may continue with the pressure surfaced. Above 100k, Kilo must not continue the same reasoning unit by truncating required truth, silently dropping mandatory sources or assuming the model's larger provider window makes the task safe.

Additional boundaries:

- **Count only Kilo-intentionally-assembled context.** The ceiling covers project artifacts, authoritative excerpts, source/code, tests, evidence, dependency contracts, retrieved supporting material and active workflow state. It does not attempt to count system prompts, tool-protocol overhead or model bookkeeping that Kilo does not control.
- **The ceiling is not a fill target.** Kilo deliberately leaves headroom for reasoning, tool interaction and output.
- **Use one common policy.** Do not create separate numeric ceilings for commands or agents. Stage- and role-context rules determine what each workflow needs; some stages may naturally consume more context than others.
- **Do not decide the >100k reduction mechanism here.** Point 03.9 defines the ceiling and required stop condition only. How a large reasoning scope is reduced or assembled is owned by the later context-assembly/grooming design.

Core rule:

> **20–40k is the normal working band; >40k is pressure, not failure; 100k is the hard ceiling for one Kilo-managed reasoning unit. Required truth is never silently discarded to fit the budget.**

### Locked design — large-project context assembly (Point 03.10)

For LARGE projects, context is assembled **task-outward rather than project-inward**. Start with invocation identity and the active working artifact, add the minimum-sufficient portions of its direct authority chain and explicit dependency context, then add the relevant execution surface, and expand only when reasoning establishes a concrete need. Project size alone never justifies loading broader context. Build the source skeleton deterministically from authoritative metadata first, then spend semantic retrieval only on sources whose contents can affect the current result. Existing freshness (03.4/03.5), reference/full-artifact (03.6/03.7), deduplication (03.8), and 40k/100k ceiling (03.9) rules apply throughout.

Assembly layers:

1. **Invocation identity.** Include workflow mode, command/stage, active Project/Epic/Feature/Spec identifiers, current task/intent, and resume/reconciliation state when applicable. Keep this tiny and deterministic.
2. **Active working artifact.** Load it in full under Point 03.6. Existing exceptions and stage rules remain unchanged.
3. **Direct authority chain.** Walk upward only as far as needed. Each ancestor contributes the minimum-sufficient authoritative portion rather than being loaded in full by default. Preserve the Architecture-stage full-PRD exception.
4. **Explicit dependency context.** Resolve declared `Depends on`, `Governed by`, effective inherited governance and relevant pending dependencies mechanically first. Dereference semantic content only when required under Point 03.7. Do not perform repository-wide dependency search.
5. **Execution surface.** For implementation, verification and debugging, discover the source files, interfaces/contracts, tests, configuration and deployment/infrastructure definitions relevant to the active work from the active Spec and repository facts. Do not preload whole directories or subsystems.
6. **On-demand expansion.** Add further context only when reasoning establishes a genuine missing premise. Newly retrieved context joins the same invocation snapshot and follows the existing freshness and deduplication rules.

Context assembly has two phases:

- **Phase A — deterministic skeleton.** Establish the active artifact, parent chain, declared dependencies, governing authorities, workflow state and known implementation/test references from authoritative persisted facts. This phase should not require LLM judgment merely to discover that these sources exist.
- **Phase B — semantic minimum-sufficient resolution.** Decide which referenced sources actually need content, and how much, under Points 03.3–03.7. Semantic retrieval is spent only where source contents can affect the current result.

Explicit anti-patterns:

- no load-all-project-docs-first behaviour
- no full ancestor chain by default
- no all-ADR preload
- no sibling Feature/Spec preload merely because they share a parent
- no repository-wide semantic retrieval before every invocation
- no conversation-history replay as project context
- no generated mega-summary as substitute authority
- no transitive dependency-of-dependency loading unless current reasoning actually reaches that premise

Project size should therefore have little direct relationship to invocation size. A project with many Epics, Features, Specs and years of history should still allow a well-scoped Spec to operate primarily from its own artifact, relevant authority, dependency contracts and execution surface.

Interaction with Point 03.9:

- stop growing the packet once minimum-sufficient context has been reached
- crossing 40k surfaces context pressure but may continue when additional context is genuinely mandatory
- if minimum-sufficient assembly would exceed 100k, return `CONTEXT_CEILING_EXCEEDED` rather than silently truncating required truth

The ceiling report should identify the major contributors and approximate sizes so that later grooming/scope-reduction design has actionable evidence. Point 03.10 does not define how that scope is decomposed or reduced.

Core rule:

> **For LARGE projects, assemble context task-outward: establish the source skeleton deterministically, resolve only the minimum semantic content that can affect the current result, and expand only when a concrete missing premise appears. Project size alone never justifies broader loading.**

### Locked design — agent discovery of additional context (Point 03.11)

Agents discover additional context through a **reason-bound expansion loop**. When current context leaves a concrete premise unresolved, first follow deterministic authoritative references and repository relationships; if the required information is known but its location is not, perform a bounded targeted search. Search results are candidate locators, not context — confirm relevance, resolve the current authoritative source, and load only the minimum-sufficient portion. Further expansion occurs only when newly read material establishes another concrete missing premise. Discovery may expose a `DEPENDENCY_GAP` but must never invent authoritative relationships. Stop when the premise is resolved, further context cannot affect the result, expansion becomes speculative, the context ceiling is reached, or genuine authority ambiguity requires `HUMAN_DECISION_REQUIRED`.

Rules:

1. **State the missing premise first.** Do not begin with open-ended repository exploration. Express the unresolved question specifically enough that additional context has a clear purpose.
2. **Prefer deterministic discovery before search.** Use known artifact/reference IDs, declared dependencies/governance, the direct authority chain, known implementation/test references, imports/callers/interfaces/configuration references, and exact path/name/symbol lookup where applicable.
3. **Use bounded search only when the source location is unknown, not when the information need itself is vague.** Search should answer a concrete question such as where an interface is implemented, where a retry policy is tested, or which accepted requirement defines a particular behavior.
4. **Treat search results as candidate locators, not context.** Confirm candidate relevance, resolve the current authoritative source, load only the minimum-sufficient portion under Points 03.6/03.7, and exclude irrelevant candidates from the active packet.
5. **Chain expansion only when each step earns the next.** A path such as Spec → interface → implementation → configuration is valid when each newly read source demonstrates why the next source matters. Do not recursively explore merely because links exist.
6. **Discovery reveals gaps; it never manufactures project truth.** If code or prose reveals a genuine undeclared semantic dependency, raise `DEPENDENCY_GAP` and repair it through the existing Point 02 process. Do not silently create authoritative `Depends on`/`Governed by` relationships from implementation discovery.
7. **Apply freshness automatically to every newly discovered source.** Resolve its current authoritative source and fingerprint before use; do not rely on remembered or cached content.
8. **Delegated agents discover independently.** The parent passes task intent, scope, identifiers and workflow state rather than an anticipatory expanded packet. The delegated invocation applies the same bounded discovery rules from fresh authoritative state.
9. **Use no arbitrary discovery-count limit.** Do not cap discovery by a fixed number of searches/files. The semantic requirement that every expansion has a concrete reason, plus the 40k/100k context policy, provides the guardrail.
10. **Stop expansion when:** the missing premise is sufficiently resolved; additional material cannot change the current decision; the next step would be speculative; the 100k ceiling would be crossed; deterministic/bounded discovery genuinely cannot locate the required information; or sources conflict/authority becomes unclear. In the last case, use the standing `HUMAN_DECISION_REQUIRED` rule where the ambiguity is workflow-significant.

Core rule:

> **Additional context must be earned by a concrete unresolved premise. Follow deterministic references first, use targeted search only to locate known-needed information, treat results as locators rather than context, and stop expanding as soon as the decision no longer depends on more material.**

### Locked design — token cost interaction (Point 03.12)

Token cost is optimized only **after correctness requirements are satisfied**. Mandatory fresh context is never omitted, replaced by stale summaries, or weakened merely to reduce cost. Kilo minimizes total work-unit cost through minimum-sufficient task-outward assembly, bounded authoritative reads, deterministic lookup, provenance deduplication, reason-bound expansion, appropriate task scope, and economical model selection where capability permits. Optimize total tokens required to reach a correct result, not merely the size of the initial packet. Provider-specific budgets and routing thresholds are deferred to the model-integration/cost design in Point 14.

Rules:

1. **Correctness determines context; cost influences efficiency and model choice only.**
2. **Optimize in this order:** remove irrelevant context; prefer bounded authoritative portions over full artifacts where Point 03.6 permits; deduplicate within-invocation reads; prefer deterministic lookup before semantic discovery; keep work appropriately scoped near the 20–40k normal band; choose a cheaper model when frontier capability is unnecessary; then accept the cost of the minimum-sufficient packet.
3. **Never drop mandatory context for cost.** Do not substitute a stale summary merely because rereading current authority costs more tokens.
4. **Measure cost across the whole invocation/work unit, not just the initial packet.** A smaller starting packet that triggers repeated vague searches may cost more than a larger but well-justified initial packet.
5. **Do not optimize through durable semantic summaries.** Preserve Point 03.8. Disposable Point-06 indexes/caches may reduce lookup cost but cannot replace authoritative semantic content.
6. **Separate invocations rebuild their own bounded packets.** Repeated work under one Feature must not drag the entire previous Feature/session context forward by default.
7. **Model choice may weigh cost but cannot redefine mandatory context.** If a cheaper model cannot reliably handle the minimum-sufficient task/context, use a more capable model or legitimately reduce task scope rather than starving the model of required truth.
8. **Large provider windows do not relax Point 03 discipline.** A larger or more expensive model is not permission to preload unnecessary project context.
9. **Do not define provider-specific monetary or routing thresholds here.** Rupee/dollar caps, token-triggered model switching and provider pricing rules belong to Point 14.
10. **Require lightweight observability for later POC/smoke work.** Capture assembled input tokens, peak context size, expansion count, tokens introduced by expansion, measurable duplicate-context avoidance where practical, and approximate model/API cost where available. Points 06 and 12 determine implementation and validation details.

Core rule:

> **Cost is a tie-breaker among already-correct options. Kilo should minimize total tokens required to reach a correct result, but never by weakening freshness, authority, mandatory context or reasoning validity.**

## [x] 04 — Escalation Model

### Why this matters

AI agents will encounter ambiguities and unexpected implementation problems.

Not every issue should interrupt the developer, but an implementation agent must also not silently make a product or architectural decision simply because it needs to continue coding.

### Locked design — implementation-agent autonomy

An implementation agent may independently resolve a choice only when the choice is clearly an implementation detail within already accepted authority.

All of the following must hold:

- mandatory governing context has been assembled and established as fresh under Point 03;
- the choice is directly consistent with, or genuinely unaddressed by, accepted PRD, architecture/ADRs, Epic, Feature and Spec authority relevant to the task;
- it does not alter required behaviour, acceptance criteria, product semantics or an already accepted decision;
- it does not create, remove or materially change a contract relied upon outside the current implementation scope;
- it does not establish a project-level, cross-cutting or architectural policy;
- changing the decision later would not require migration, compatibility handling, coordinated downstream changes or reinterpretation of accepted authority;
- normal verification can prove the implementation satisfies an already-defined behaviour rather than choosing what that behaviour should mean;
- if classifying the choice as autonomous requires material interpretation, assumptions, debate or a constructed argument, the choice is not autonomous and must be escalated.

Persisted formats, externally consumed API/event/message shapes, deployment/configuration contracts, shared external-facing abstractions and security-related semantics are **presumptively non-local** and therefore cannot be treated as autonomous implementation decisions without an already accepted governing decision.

Tests may independently implement verification of stated behaviour. A test must not resolve ambiguity in governing behaviour by choosing the expected result itself; such ambiguity requires escalation.

Within these boundaries, the agent should choose a reasonable implementation and continue rather than asking the developer to approve routine coding details. The agent does not need to prove its chosen implementation is globally optimal; it needs to establish that the choice is clearly within its implementation authority.

If only part of the implementation encounters a non-autonomous decision, that unresolved portion must remain explicitly blocked. The exact rules for continuing independent safe work, pausing and resuming are defined by the later Point 04 workflow-pause/resume decisions.

Typical autonomous choices include local naming, private helper decomposition, internal code organization, equivalent language/framework idioms, implementation algorithms where required behaviour is already fixed, implementation-local refactoring, test fixtures/mocks, and local performance improvements that preserve accepted behaviour and architecture.

A reusable abstraction may be created autonomously only while it remains implementation-local. Declaring that abstraction to be a shared/project-wide pattern is not an implementation-local decision.

A useful boundary test is:

> **Would any accepted artifact, external consumer, sibling Feature or future implementation legitimately need to know which implementation option was chosen?**

If no, the choice is normally an implementation detail. If yes, it is not autonomous under this rule and must follow the appropriate escalation path defined by the remainder of Point 04.

### Locked design — specification clarification

`SPECIFICATION_CLARIFICATION_REQUIRED` is the initial classification when implementation or verification cannot determine an intended **material observable behaviour** from the accepted Spec and its governing authority.

**Dividing line from 04.1:** Silence is autonomous only when all reasonable choices are implementation-equivalent from the perspective of accepted behaviour and relevant consumers. If reasonable choices produce materially different observable behaviour, the silence requires specification clarification.

Typical triggers:

- required observable behaviour is missing for a case implementation must handle;
- multiple reasonable interpretations would produce materially different results;
- acceptance criteria are insufficient to determine correctness;
- requirements within the Spec contradict each other;
- the Spec conflicts with governing Feature/Epic/PRD authority and the intended contract cannot be determined confidently;
- material state transitions, validation semantics, error behaviour, ordering, retry/idempotency semantics, defaults or boundary behaviour are undefined;
- verification would have to invent the expected result;
- implementation discovers an assumption on which the required behaviour depends but which accepted authority never actually settled.

**De minimis / materiality rule:** A reasonable implementation choice remains autonomous when all of the following hold — no accepted authority constrains the choice; no external consumer, sibling Feature or accepted contract materially relies on which option is chosen; the choice does not establish a shared/project-level convention; changing it later is cheap and local, requiring no migration, compatibility handling or coordinated downstream change; verification of the actual required behaviour does not depend on that specific choice.

**Classification is provisional, not the resolution.** `SPECIFICATION_CLARIFICATION_REQUIRED` means the implementation agent has established the behavioural contract is insufficiently clear to continue that portion safely — it does not mean the agent has determined who resolves it. Triage routes to: Spec clarification (higher authority already determines intent; Spec just needs to state it) / Architecture escalation (choosing requires an architectural decision) / Human-product decision (authority genuinely leaves it open). The implementation agent identifies the ambiguity; it does not choose among the unresolved options.

**Boundary test:** Could two reasonable implementations make materially different promises to a user, consumer, verifier or downstream artifact because this decision was left unstated? If yes → `SPECIFICATION_CLARIFICATION_REQUIRED`. If no, and 04.1 conditions hold → implementation may decide.

### Locked design — architecture issue

An issue is an **architecture issue** when resolving it would establish, change, or materially reinterpret a technical decision that defines a durable system-level constraint, contract, boundary, or pattern beyond the current implementation scope.

The key distinction is:

> **Architecture is not “important technical work.” It is a technical decision whose consequences extend beyond the local implementation and materially constrain how other parts of the system are or will be built.**

Typical architecture issues include:

- introducing or changing a primary persistence strategy or datastore model;
- establishing service/module/process boundaries;
- defining cross-cutting authentication, authorization or security mechanisms;
- introducing a shared integration pattern for external services;
- establishing durable API, event, message or persisted-data contracts;
- deciding consistency, transaction, concurrency or distributed-state strategy;
- changing deployment topology, runtime boundaries or infrastructure architecture;
- establishing project-wide observability, configuration or resilience patterns;
- introducing a framework, platform, shared abstraction or technical pattern that downstream Features are expected to rely upon;
- reversing an earlier architectural choice where migration, compatibility handling or coordinated downstream work would be required.

#### Existing architecture authority is not a new architecture issue

If an accepted ADR or other architecture authority already determines the choice, applying that decision is **not** a new architecture issue.

The implementation agent should follow the existing architecture under 04.1 where the required implementation is clear.

If the existing architecture decision is ambiguous in how it applies to the current Spec, the issue may first classify under `SPECIFICATION_CLARIFICATION_REQUIRED`.

If implementation would need to contradict, extend, reinterpret or replace the accepted architecture decision, then it becomes an architecture escalation.

```text
Architecture topic encountered
        │
        ├─ Existing ADR/architecture clearly answers it
        │      → apply accepted authority
        │
        ├─ Existing authority exists but application is behaviourally unclear
        │      → 04.2 clarification
        │
        └─ Choice requires new/change/reinterpretation of architecture
               → 04.3 architecture issue
```

The overlap is intentional: an ambiguity can initially enter through 04.2 and then triage to architecture when resolving the behavioural uncertainty requires establishing or changing project-wide technical authority.

#### Foundational decisions count even before dependents exist

Architecture does not require multiple existing Features or Specs.

A decision is still architectural when it establishes a foundation that **future reasonable Features/Specs would be expected to inherit or work within**, even if the project currently contains only one implementation scope.

For example, choosing the project's primary datastore, authentication model, deployment topology or service boundary for the first Feature can be architectural because the decision deliberately creates a system-wide constraint for later work.

The counterfactual test is:

> **Would future Features, Specs or implementations reasonably be constrained by this decision if the project grows according to its accepted direction?**

If yes, that is evidence of architectural scope.

#### Non-trigger / materiality rule

Potential reuse alone does **not** make something architectural.

A helper, class, library wrapper, validator, module or abstraction remains implementation-local merely because another Feature *could* reuse it later.

It becomes architectural only when either:

- actual or deliberately intended cross-scope reliance exists; or
- the decision establishes a system-wide technical constraint whose later reversal would require migration, compatibility handling, coordinated downstream changes or reinterpretation of accepted artifacts.

This mirrors the 04.1 boundary:

> **Could this remain a private implementation choice without any accepted artifact, external consumer, sibling/future Feature or project-wide convention needing to know about it?**

If yes, it remains implementation-local.

#### Boundary test

> **Does this decision establish or change a durable technical constraint that current or reasonably foreseeable future implementation scopes must work within, or whose reversal would require coordinated system-level change?**

If yes → architecture issue.

If no → remain under 04.1 unless 04.2 behavioural ambiguity applies.

This gives Point 04 a continuous ladder:

```text
Local technical choice
→ 04.1 implementation autonomy

Required behaviour unclear
→ 04.2 SPECIFICATION_CLARIFICATION_REQUIRED

Required behaviour understood, but resolving it needs a new/change to
a durable system-level technical constraint
→ 04.3 architecture issue
```

### Locked design — what requires human approval (Point 04.4)

Human approval is required when continuing would require Kilo to choose a material project direction that is not already determined by accepted authority and where choosing among reasonable options depends on the developer's priorities, risk tolerance, scope intent, willingness to accept a consequential trade-off, or an explicitly developer-reserved decision.

Architecture and implementation workflows may independently resolve decisions that are genuinely technical and already bounded by accepted project authority.

**Conservative classification rule:** The same conservative-escalation bias from 04.1 applies. If classifying a decision as purely technical requires material argument, interpretation, or an assumption about the developer's unstated priorities, it is not purely technical and must be escalated as `HUMAN_DECISION_REQUIRED`.

**Cumulative-effect rule:** Materiality is assessed against the effective combined consequence of related decisions, not only each in isolation. Several individually minor choices must not be used to incrementally create a materially different cost, lock-in, operational, security, privacy, migration, or risk posture without human approval. The aggregation mechanism is deferred to Points 05/06.

**Developer-reserved decisions:** A decision explicitly reserved for the developer remains human-owned even if an agent later considers one option technically obvious. Durable representation of such reservations is deferred to Point 05's artifact/state metadata design.

**Triggers:** product/scope intent; unsettled material trade-offs; changing accepted authority; material scope creation/removal/deferral; materially different cost/risk/lock-in commitments; authority conflict/ownership ambiguity; explicitly developer-reserved decisions.

**Non-trigger:** Human approval is not required merely because a decision is architectural, important, difficult, or has multiple technically valid solutions.

**Decision-presentation rule:** `HUMAN_DECISION_REQUIRED` must present a bounded decision, not merely report uncertainty. Kilo must state the exact unresolved choice, why existing authority cannot resolve it, the reasonable options, the material consequences/trade-offs of each, and any recommendation or technical preference that can be made without substituting for the developer's judgment. It must ask the developer to choose between concrete alternatives rather than returning a vague "please advise."

Example shape:

```text
HUMAN_DECISION_REQUIRED
Decision: Choose deployment model for X.
Why human-owned: Accepted authority does not establish the preferred
  trade-off between recurring cost and operational burden.
Option A — Managed service: higher recurring cost, lower operational burden, lower maintenance complexity.
Option B — Self-hosted: lower recurring cost, higher operational burden, more maintenance responsibility.
Technical assessment: Both satisfy accepted requirements.
Human decision required: Choose A or B.
```

The resulting authority boundary is:

```text
Can accepted authority + technical reasoning determine it?
→ workflow decides

Does determining it require assumptions about what the developer values,
is willing to pay/operate/risk, or wants the product to become?
→ HUMAN_DECISION_REQUIRED
```

### Locked design — what constitutes a blocking ambiguity (Point 04.5)

Blocking is not a separate escalation category. It is a property of an unresolved 04.2, 04.3, or 04.4 escalation that determines whether dependent work may safely continue while that escalation remains unresolved.

An ambiguity is blocking when continuing the affected work would require Kilo to choose, assume, or encode an unresolved answer that can materially affect the correctness, observable behaviour, contract, architecture, accepted authority, verification result, or developer-owned project direction of that work.

Blocking applies at the narrowest dependency scope whose validity depends on that answer. Independent work that can remain correct regardless of every reasonable resolution consistent with accepted authority may continue. The block widens only where dependency requires it.

An unresolved question is not blocking merely because it is difficult, important, architectural, or currently unknown. If normal bounded discovery can resolve it, or if the current work is invariant under every reasonable resolution consistent with accepted authority, work may continue.

Easy reversibility does not authorize guessing. If continuing requires an assumption the agent is not authorized to make, the dependent path remains blocked even if the speculative implementation would be cheap to undo.

Investigation, option analysis, and genuinely resolution-independent preparation may continue; dependent commitment may not.

If a later accepted resolution reveals that work previously classified as independent was actually affected, the consequences are handled under Point 01 reconciliation.

**Scope semantics** (semantic only — not yet lifecycle states; Point 05 owns state vocabulary):

- **Path block** → only dependent reasoning/implementation stops
- **Work-unit/stage block** → the current Spec/Feature/stage cannot satisfy its gate
- **Project-wide block** → a foundational unresolved decision affects all meaningful next work

**Boundary test:**

```text
Would this work remain correct and truthful under every reasonable
resolution consistent with accepted authority?

YES → not blocked
NO  → blocked
```

### Locked design — how agents report escalation (Point 04.6)

Something cannot be safely self-resolved → classify under 04.2/04.3/04.4 → assess blocking under 04.5 → produce one bounded, actionable escalation report → route to the appropriate owner/workflow.

**Uniform-envelope rule:** Every escalation uses the same report structure regardless of classification. Field presence is fixed; required detail varies by classification — `Options` may be a concise list of interpretations for a specification clarification, while a human decision must include the consequence/trade-off detail required by 04.4.

**Report fields (all always present):**

```text
ESCALATION REPORT

Classification
Origin
Unresolved decision
Why escalation is required
Authority consulted
Options / interpretations
Technical assessment
Blocking assessment
Blocked work
Safe continuation
Resolution required
```

**Depth by type:**

- `SPECIFICATION_CLARIFICATION_REQUIRED` → short interpretations may be enough
- Architecture escalation → materially distinct technical options/constraints
- `HUMAN_DECISION_REQUIRED` → full consequences/trade-offs per 04.4

**Safe-continuation field is mandatory.** The report must explicitly state what independent work may continue. If none exists, it must say `None` and explain why — omission is indistinguishable from failing to assess the 04.5 blocking scope.

**Anti-bundling rule:** Report one smallest actionable decision per escalation, except where 04.4 cumulative materiality is itself the trigger; then report one composite escalation containing all contributing decisions, because the materiality exists only in their combined effect.

**Other governing rules (unchanged):**

- Before escalating, the agent must complete bounded discovery and authority checks already required by Points 03/04 — no escalating merely because the answer wasn't immediately visible.
- Once the escalation threshold is reached, the agent must not keep searching to avoid reporting it.
- Reference authoritative sources; do not copy their content into the report (Point 03 discipline).
- Report conclusions and actionable facts, not a reasoning transcript.
- 04.6 does not define persistence, identifiers, pause mechanics, or resume mechanics — those belong to 04.7–04.9 and Point 05.

**Quality test:** Could the receiving owner understand exactly what must be decided, why it belongs to them, what authority was checked, what is blocked, what may continue, and what resolution is required — without re-investigating the originating task? If yes, sufficient. If no, incomplete.

### Locked design — how the workflow pauses (Point 04.7)

A workflow pause is the execution consequence of a blocking ambiguity under 04.5. It is not a separate escalation type or an automatic project-wide stop.

Kilo pauses the narrowest work scope whose correctness depends on the unresolved decision. Independent work that remains correct under every reasonable resolution consistent with accepted authority may continue.

**Safe-continuation is a standing test, not a snapshot:** Safe-continuation status is not fixed at the time of the original escalation report. Any subsequently identified work may be assessed against the same 04.5 correctness test.

Paused work must not proceed through assumptions, temporary decisions, placeholder contracts, weakened verification, or premature completion. Investigation and genuinely resolution-independent preparation may continue.

A blocked dependency prevents any readiness/completion gate whose validity depends on that dependency from passing. **Gate-deferral exception:** A gate may pass with an unresolved dependency only if the developer has explicitly excluded that dependency from the gate's completion criteria through a 04.4 decision; otherwise it remains blocked.

Pause scope widens only when dependency requires it, never merely because time passes. **If it widens:** update the existing escalation record with the newly dependent work and revised blocking scope rather than creating a duplicate escalation.

If no safe continuation remains in the current invocation, the agent stops cleanly with the outstanding escalation rather than inventing speculative work.

Exact persisted lifecycle/state representation remains deferred to Point 05; 04.7 defines execution semantics only.

**Operational test:**

```text
Does this next action depend on the unresolved answer?

NO  → assess against 04.5; continue if truly invariant
YES → paused
```

### Locked design — how the workflow resumes (Point 04.8)

Workflow resume is a fresh continuation from current authoritative project state after the blocking escalation has been genuinely resolved; it is not a replay of the paused invocation or its old context.

An escalation is considered resolved for resume purposes only when its answer has become durable accepted authority through the mechanism defined by 04.9. Informal, provisional, suggested, or chat-only answers do not release dependent work — including the developer's own chat response, which supplies decision content but not authority until recorded.

Resolution does not automatically restart execution. The developer explicitly resumes the originating workflow through `/continue` or the eventual equivalent command.

Before resuming, Kilo reconstructs minimum-sufficient context from current authoritative state, applies Point 03 freshness rules, re-reads the accepted resolution and relevant changed sources, and reassesses the affected dependency/blocking scope.

Only work whose blocking premise has actually been resolved is released. Other unresolved escalations remain independently blocking.

Previously completed resolution-independent work is preserved when still valid; it is not repeated merely because the workflow resumes. If the accepted resolution reveals that supposedly independent work was actually affected, handle that impact through Point 01 reconciliation rather than silently rewriting it during resume. **If that reconciliation affects work on which the paused path depends, the paused work must remain blocked until reconciliation completes — resuming against unreconciled state is not permitted.**

Control returns to the workflow that originally owned the blocked work. The resolving workflow establishes the accepted decision; it does not take over unrelated downstream execution.

If current authority, repository state, another unresolved escalation, or required reconciliation still prevents safe continuation, the affected path remains paused or produces the appropriate new escalation instead of blindly resuming.

**Operational test:**

```text
Has the resolution been recorded as durable accepted authority?
NO  → remain paused.

YES
 ↓
Has the developer explicitly resumed the owning workflow?
NO  → remain paused.

YES
 ↓
Does current authoritative state show this path is safe to continue?
NO  → remain paused / reconcile / escalate as appropriate.
YES → resume from current state.
```

### Locked design — how resolved escalations become durable project knowledge (Point 04.9)

A resolved escalation becomes durable project knowledge by promoting its accepted resolution into the authoritative artifact that semantically owns the decision. The escalation record itself is historical provenance and routing state; it is not a competing source of project authority.

Decision ownership and decision-maker are separate concerns. A human-owned decision may ultimately belong in a PRD, ADR, Epic, Feature, Spec, or other accepted authority depending on what the decision governs.

An escalation is not resolved for 04.8 resume purposes until the accepted decision has been durably recorded in its authoritative home. Chat responses, provisional conclusions, and the escalation report itself do not satisfy this requirement.

Every legitimately resolved `SPECIFICATION_CLARIFICATION_REQUIRED` requires an update to its owning authoritative artifact, however minimal. If no artifact change is actually necessary, the original issue was not a genuine 04.2 escalation and should have been resolved under 04.1.

If recording the resolution materially changes completed accepted authority, Point 01 reconciliation applies. 04.9 does not bypass completed-artifact immutability. The escalation remains unresolved for dependent resume until the required authority/reconciliation work is complete.

The escalation history retains the original issue, classification, origin/blocking context, a concise historical resolution summary, references to the authoritative resolution, and any reconciliation or scope consequences required to understand why the escalation closed. Exact schema/state fields are deferred to Point 05.

Escalation records persist indefinitely as historical provenance but are not part of default context assembly. They are discoverable on demand under Point 03's minimum-sufficient-context rules; retrieval/indexing mechanics remain deferred to Point 06.

A resolution summary is historical context only. Future workflows resolve current truth from the referenced authoritative artifact, not from the escalation record.

Where one resolution affects multiple authoritative artifacts, normal dependency and reconciliation mechanisms update those artifacts. The escalation record references the resulting authority chain; it does not duplicate that authority.

Rejected options may remain in escalation history as provenance, but they never become accepted project truth.

**Test:**

```text
If the escalation record disappeared tomorrow,
could Kilo still discover the accepted project decision
from normal authoritative artifacts?

YES → durable knowledge is correct.
NO  → the escalation record has accidentally become authority.
```

04.2  Required behaviour unclear           → SPECIFICATION_CLARIFICATION_REQUIRED
04.3  Durable system-level constraint      → architecture issue
04.4  Developer priorities/trade-off       → HUMAN_DECISION_REQUIRED
04.5  Blocking (property, not a category)  → does dependent work require the answer?
04.6  Escalation report                    → fixed envelope, variable depth

### Already agreed — 05.2 Epic states

  RECONCILING, DECISION_REQUIRED, VERIFYING/VERIFIED, IMPLEMENTING,

- [x] Post-completion bug fixes / small operational corrections do not

  new work constitutes a new bounded product/technical outcome.
- [x] Transition metadata/fields deferred to later 05.x items.

- [x] GROOMING intentionally omitted at Spec level. Epic/Feature need
  explicit grooming to resolve ambiguity before decomposition; a Spec

- [x] Meanings:
  - DRAFT — Spec exists but not yet safe to implement (details,

- [x] Titles/slugs are never encoded in the ID (no FEATURE-PORTFOLIO-

### Already agreed — 05.7 Lifecycle transition mechanics

- [x] No second transition-history schema. Git is the transition
  history; artifact metadata holds only current state (+ Project's
  resume_state).
- [x] Initial states on creation (LARGE workflow only — does not force
  STANDARD/v0.1 projects through /ideate, a separate compatibility
  constraint): Project→DISCOVERY, Epic→DRAFT, Feature→DRAFT, Spec→DRAFT.
  No NEW/CREATED/UNINITIALIZED state.
- [x] A transition is valid only when: current state allows target
  state + trigger/guard satisfied + persistence succeeds. Guard content
  (readiness/completion criteria) remains owned by Points 08/09; only
  the mechanism is locked here.
- [x] State transition + directly related metadata update is atomic
  (logical atomicity via Markdown/Git, not a DB transaction) —
  e.g. state:PAUSED and resume_state can never diverge; a child-
  triggered parent transition (e.g. Epic READY→ACTIVE on first Feature)
  cannot be left half-applied.
- [x] Every successful transition updates updated_at (per 05.5's rule).
  No state_changed_at / started_at / completed_at / retired_at fields.
- [x] No generic previous_state / last_state / state_history[] field on
  any artifact. Only Project has resume_state, because only Project's
  PAUSED overlays multiple possible prior positions.
- [x] Illegal transitions fail closed with a deterministic
  INVALID_LIFECYCLE_TRANSITION error (current/requested/allowed/reason),
  not HUMAN_DECISION_REQUIRED — an explicitly forbidden transition is a
  validation failure, not an ambiguity.
- [x] Canonical allowed-transition tables locked (consolidating 05.1–05.4):
  - Project: DISCOVERY→{PLANNING,PAUSED,RETIRED};
    PLANNING→{ACTIVE,PAUSED,RETIRED};
    ACTIVE→{MAINTENANCE,COMPLETE,PAUSED,RETIRED};
    MAINTENANCE→{ACTIVE,COMPLETE,PAUSED,RETIRED};
    PAUSED→{resume_state,RETIRED}; COMPLETE→{RETIRED}; RETIRED→{}.
  - Epic/Feature (same shape): DRAFT→{GROOMING,RETIRED};
    GROOMING→{READY_FOR_*,RETIRED}; READY_FOR_*→{ACTIVE,RETIRED};
    ACTIVE→{COMPLETE,RETIRED}; COMPLETE→{RETIRED}; RETIRED→{}.
  - Spec: DRAFT→{READY_FOR_IMPLEMENTATION,RETIRED};
    READY_FOR_IMPLEMENTATION→{ACTIVE,RETIRED};
    ACTIVE→{COMPLETE,RETIRED}; COMPLETE→{RETIRED}; RETIRED→{}.
- [x] No backwards transitions outside explicit reconciliation, except
  the two deliberate Project cases (MAINTENANCE→ACTIVE, PAUSED→resume_
  state). GROOMING→DRAFT is explicitly disallowed — stay in GROOMING
  while unresolved, or RETIRE if the artifact shouldn't exist. Prevents
  state from becoming an informal undo mechanism.
- [x] Child-triggered parent transitions fire only after the child is
  successfully persisted into durable project history (same boundary
  as 05.6's ID-consumption rule) — not on in-memory instantiation or

- [x] Retirement is always explicit/human-controlled, never inferred
  from age, inactivity, or absence of children. Reconciliation's
  RETIRE_REQUIRED obligation must be resolved through the normal owning
  workflow — /reconcile does not silently mutate lifecycle state itself.
- [x] No state_history log of any kind. Current state is authoritative
  truth; "when/why did this change" is answered by Git history or the
  relevant reconciliation/escalation record, not duplicated metadata.
- [x] No new common metadata fields introduced by this section. Only
  persisted transition-specific field remains Project.resume_state
  (05.5). Everything else is table + guard + atomic update + updated_at

### Already agreed — 05.8 Material artifact change
 Definition: a change is material when it alters what an artifact means, requires, promises, constrains, depends on, or must prove — such that a previously valid readiness, dependency, implementation, acceptance, or verification assumption may no longer hold.
 Material: requirement/behavioural/interface-contract changes, acceptance criteria, scope, parent_id, depends_on[], governed_by[], authoritative assumptions. This is the same boundary 05.5 already uses for updated_at — 05.8 doesn't introduce a new rule, it names the existing one.
 Non-material (editorial): spelling, grammar, formatting, line-wrap, heading style, wording cleanup that preserves meaning. No updated_at bump (05.5), no re-evaluation.
 Title rename: non-semantic for materiality (no re-evaluation) but still authoritative metadata, so it still bumps updated_at — this exact case is already locked in 05.5; 05.8 just confirms it fits the general rule.
 Effect on a mutable artifact: a material change reruns that artifact's local dependency audit and its applicable readiness/completion guard (Points 02/08/09). Declared dependents (Point 02) are re-evaluated; no repo-wide scan.
 Material ≠ reconciliation: ordinary grooming/authoring changes stay ordinary. Section 01's /shouldreconcile → /reconcile applies only when the change touches already-accepted authority or a COMPLETE/immutable artifact.
 Material change to a READY_FOR_* artifact: does not demote it — backward transitions stay disallowed per 05.7. Instead, reliance on the prior readiness evaluation is invalidated until the same gate reruns. Pass → stays READY_FOR_*. Fail → downstream decomposition/execution is blocked until resolved. This is a workflow block, not a lifecycle transition — no INVALID_LIFECYCLE_TRANSITION, no state change, no new field.
 Material change to a COMPLETE artifact: governed entirely by Section 01's existing immutability/reconciliation rule; never applied as normal editing.
 Genuine ambiguity: default to HUMAN_DECISION_REQUIRED (Point 04) rather than treating an uncertain edit as harmless.
 Three concepts stay separate: updated_at changed ≠ material change ≠ reconciliation required.
 No new persisted state, field, or metadata introduced — consistent with 05.5/05.7's "mechanism only" scope.

### Already agreed — 05.9 Completion semantics

- [x] Completion is never inferred automatically from child state alone. A lifecycle transition to COMPLETE must satisfy the artifact's applicable completion criteria and be explicitly performed through the transition mechanics defined in 05.7.

- [x] **Epic/Feature hard floor:** a parent Epic or Feature cannot become COMPLETE while it has any non-RETIRED child that is not itself COMPLETE. RETIRED children do not block completion — RETIRED represents closed historical work, not unfinished live work.
  - Feature → COMPLETE requires every child Spec to be COMPLETE or RETIRED.
  - Epic → COMPLETE requires every child Feature to be COMPLETE or RETIRED.

- [x] **Project is intentionally different.** Project completion is a human-controlled project/portfolio outcome judgment and is not derived from Epic completion counts. There is no requirement that every historical or planned Epic be COMPLETE or RETIRED before Project → COMPLETE. Project lifecycle semantics remain those defined in 05.1.

- [x] The child-completion floor is necessary but not sufficient. Satisfying it alone never causes or justifies COMPLETE. Each artifact must also satisfy its own level-specific completion criteria:
  - **Spec:** agreed behaviour is implemented AND required Spec-level verification evidence exists and is applicable (05.4; exact evidence defined by Point 09).
  - **Feature:** all child Specs satisfy the hard floor AND required integrated Feature-level verification/acceptance succeeds (05.3; exact criteria defined by Point 09).
  - **Epic:** all child Features satisfy the hard floor AND the Epic-level completion criteria demonstrate that the intended Epic outcome was delivered. Exact acceptance/verification requirements remain owned by the appropriate later design points.
  - **Project:** explicit human-controlled determination that the intended Project scope/outcome has reached COMPLETE under the Project lifecycle rules.

- [x] The hard floor is evaluated when COMPLETE is requested. It is not persisted as `children_complete`, continuously watched, or used to auto-promote the parent when the final child completes. No automatic lifecycle transition is introduced.

- [x] A live child preventing its parent from reaching COMPLETE is a normal unmet completion precondition. It does not create a new lifecycle state, escalation type, or error category; the parent simply remains in its current state until the criterion is satisfied or the child is legitimately retired.

- [x] COMPLETE does not reopen to ACTIVE for Epic, Feature, or Spec, consistent with 05.2–05.4. Meaningful later work becomes a new artifact. Project retains its separately defined ACTIVE ↔ MAINTENANCE behaviour before Project completion; Project COMPLETE itself does not reopen.

- [x] Child-state evaluation is derived deterministically by reverse lookup of artifacts whose `parent_id` references the parent. No persisted child list, `children_complete` flag, completion counter, or additional common metadata is introduced.

### Already agreed — 05.10 Reconciliation-related states

- [x] Project/Epic/Feature/Spec gain **no** reconciliation-specific lifecycle states. No RECONCILING, no BLOCKED, no DECISION_REQUIRED as an artifact state. This is a direct extension of the exclusions already locked in 05.1–05.4 — reconciliation dispositions remain orthogonal overlays, not lifecycle states.

- [x] **Reconciliation package lifecycle** (the `/reconcile` work unit itself, not the artifacts it touches): `ASSESSING → OPEN → CLOSED`, with a direct `ASSESSING → CLOSED` shortcut when assessment finds no outstanding mandatory obligations.
  - **ASSESSING** — `/reconcile` has started; candidate discovery/classification is not yet fully finished. Covers interrupted/resumable reconciliation.
  - **OPEN** — assessment is complete, but at least one mandatory obligation remains unresolved.
  - **CLOSED** — assessment is complete and no mandatory obligation remains `OPEN`; every mandatory obligation is therefore `RESOLVED` or `SUPERSEDED`.
  - No CANCELLED, FAILED, or RECONCILING-adjacent state for the package. A package can be ASSESSING while one obligation is independently blocked — that condition is carried on the obligation, not the package.

- [x] **Per-artifact reconciliation disposition** (set per affected artifact by a given package, not a lifecycle state): `UNCHANGED | REVISED | DECISION_REQUIRED | RETIRE_REQUIRED` — as already locked in Section 01. These never write into an artifact's `state` field.

- [x] **Obligation status vocabulary:** `OPEN | RESOLVED | SUPERSEDED`. No CANCELLED — an obligation superseded by a later accepted delta is SUPERSEDED, preserving its history rather than erasing it.
  - Example: DECISION_REQUIRED obligation, OPEN → human resolves → RESOLVED.
  - Example: NEW_WORK_REQUIRED obligation, OPEN → later reconciliation replaces the required work → SUPERSEDED.
  - Example: reverification obligation → RESOLVED once applicable fresh evidence exists (ties to Point 09/05.11 evidence; evidence semantics are not redefined here).

- [x] **Reference direction settled (resolves 05.5's deferred item):** reconciliation records reference artifacts; artifacts never reference reconciliation records. No `open_reconciliation_ids[]` or similar field on Project/Epic/Feature/Spec.
  - "Does SPEC-014 have an open reconciliation obligation?" is answered by reverse lookup over reconciliation packages/obligations referencing SPEC-014, not by reading a field on SPEC-014 itself.
  - If Point 06 adopts SQLite, it may index this lookup for speed, but Markdown/Git remains authoritative; the reference direction does not change.

- [x] Three concepts stay permanently distinct and are never collapsed into one field:
  1. artifact lifecycle state (05.1–05.4),
  2. per-reconciliation artifact disposition,
  3. reconciliation-package lifecycle.

- [x] An artifact's lifecycle state is untouched by reconciliation mechanics themselves:
  - a COMPLETE Spec remains COMPLETE while its accepted claim is revised under RECONCILE_ONLY;
  - RETIRE_REQUIRED records an obligation to retire through the normal owning workflow and does not immediately set the artifact to RETIRED;
  - DECISION_REQUIRED blocks only the affected reconciliation path and does not become an artifact lifecycle state;
  - REVISED means the artifact's accepted content changed under reconciliation, not that delivery or verification is complete.

- [x] Reconciliation-package closure is derived from assessment completion plus obligation status; no mirrored `reconciliation_status` or `open_reconciliation_ids[]` field is added to Project/Epic/Feature/Spec metadata.

### Already agreed — 05.11 Verification-related states

- [x] Verification is not an artifact lifecycle state. No VERIFYING, VERIFIED, FAILED, or STALE value is added to Project/Epic/Feature/Spec — consistent with the exclusions already locked in 05.1–05.4.

- [x] Verification truth lives in a claim↔evidence association status vocabulary: `APPLICABLE | INAPPLICABLE | SUPERSEDED`.
  - **APPLICABLE** — this evidence currently supports this claim.
  - **INAPPLICABLE** — evidence is preserved historically but no longer proves the current claim (for example, after a requirement change during reconciliation).
  - **SUPERSEDED** — newer evidence intentionally replaces this association for the same effective claim/scope.
  - No FAILED value here: a failed run is still evidence, but it never establishes a successful claim association in the first place. Failure handling (how a failed run returns to implementation) belongs to Point 09, not 05.11.
  - No separate STALE value: INAPPLICABLE already covers "historically true, currently not proof of this claim" without implying the evidence itself was ever wrong.

- [x] Evidence execution result (did the test/check/acceptance pass or fail) and evidence applicability (can this evidence currently support this claim) are explicitly separate concepts. Evidence can be historically PASSED yet currently INAPPLICABLE; failure semantics stay with Point 09.

- [x] Artifact-level "is this verified?" is always derived, never persisted. No `verification_status` field exists on any artifact — already excluded from the base schema in 05.5; 05.11 confirms it stays derived rather than reopening it. Kilo answers the question by checking whether every claim required by the applicable Point-09 completion rules has current APPLICABLE evidence and no outstanding mandatory reverification obligation.

- [x] **Reference direction settled** (resolves the second half of 05.5's deferred item, matching 05.10's reconciliation direction): evidence records reference artifacts/claims; artifacts never maintain `verification_evidence_ids[]` or any equivalent field.
  - "What evidence proves SPEC-014?" is answered by reverse lookup over evidence associations referencing SPEC-014, not by reading a field on SPEC-014.
  - Point 06 may index this lookup later; Markdown/Git remains authoritative and the reference direction does not change.

- [x] Reconciliation interaction is fully covered by Section 01 plus 05.10's obligation mechanics and is not reopened here:
  - reconciliation never deletes old evidence;
  - applicability is reassessed per claim association, not per test run, so changing one claim does not invalidate unrelated claims from the same run;
  - an affected association becomes INAPPLICABLE;
  - the reconciliation package records an OPEN reverification obligation (05.10);
  - fresh APPLICABLE evidence resolves that obligation;
  - unrelated evidence remains APPLICABLE throughout.

- [x] 05.11 defines applicability only, not the verification engine. What counts as a "claim," when evidence is required, and how failed verification is handled remain Point 09's scope and are not pre-empted here.

- [x] No new common artifact metadata field is introduced by this section. Verification status remains derived from authoritative evidence associations and outstanding obligations; evidence history stays in evidence records rather than being duplicated onto Project/Epic/Feature/Spec metadata.

### Already agreed — 05.12 Physical representation & storage layout

- [x] **Artifact files:** one Markdown file per artifact, filename = stable ID (`SPEC-014.md`), never title/slug-derived. Title rename never renames the file (consistent with 05.6's immutable-ID rule).
- [x] Flat top-level YAML front matter — no nested `metadata:` wrapper. Canonical field order (to minimize diff noise): `id → type → title → state → created_at → updated_at → parent_id → resume_state (Project only) → depends_on → governed_by`.
- [x] Timestamps: ISO-8601/RFC3339 with timezone. Empty `depends_on`/`governed_by` remain explicit `[]`, never omitted (matches 05.5). Authoritative semantic content lives in the Markdown body, not front matter.
- [x] This resolves 05.5's deferred "physical representation... whether wrapped in a `metadata:` key" item.
- [x] **Reconciliation packages:** one Markdown file per package under `docs/workflow/reconciliation/REC-###.md`. No per-obligation file and no global obligation registry. Obligations are embedded in the package body/front matter (e.g. `OBL-001 NEW_WORK_REQUIRED OPEN`), namespaced as `REC-001/OBL-003` for stable cross-reference (e.g. `superseded_by: REC-004/OBL-002`). Package `state` (05.10's ASSESSING/OPEN/CLOSED) lives in the package's own front matter.
- [x] **Verification factual evidence:** unchanged from the existing `/verify` model — `docs/verification/VERIFY-<SPEC-ID>-###.md`, immutable, history-preserving; a new report is always added, an existing verdict is never rewritten.
- [x] **Verification applicability:** a separate mutable sidecar per evidence report, `docs/verification/applicability/VERIFY-<SPEC-ID>-###.md`, holding current `claim_ref → status (APPLICABLE | INAPPLICABLE | SUPERSEDED)` per 05.11, with `reason` / `superseded_by` where applicable. This is the only place 05.11's mutable claim↔evidence state is persisted — never inside the immutable report itself, which would otherwise contradict `/verify`'s no-rewrite rule.
- [x] Both reconciliation and evidence records reference artifacts/claims by ID; artifacts never reference them back — consistent with the reference direction already locked in 05.10/05.11.
- [x] **Boundary:** 05.12 locks these storage *patterns* only. The complete repository directory tree, and where Project/Epic/Feature/Spec collections physically sit within it, remains Point 13's responsibility.

### Expected outcome

A state model that lets Kilo reliably answer:

- What is currently being worked on?
- What is ready?
- What is blocked?
- What is complete?
- What requires reconciliation?
- What has already been verified?

without requiring an LLM to reinterpret every document from scratch.

## [ ] 06 — Lightweight SQLite Workflow State & Context Index

### Why this matters

Several v0.2 requirements may require persistent machine-readable state:

- resumable workflows
- artifact lookup
- dependency lookup
- reconciliation
- context assembly
- progress tracking

Repeatedly asking an LLM to read many Markdown files merely to reconstruct this information may waste tokens and introduce nondeterminism.

SQLite may provide a lightweight local solution.

**However, SQLite must earn its place through measurable value.**

### Determine

- [x] Which state genuinely benefits from SQLite.

### Locked design — which state genuinely benefits from SQLite (Point 06.1)

SQLite, if adopted, is primarily a **rebuildable machine-readable index over authoritative Markdown/Git state**.

Its strongest justified candidate uses are:

- artifact discovery and ID → file lookup;
- structural hierarchy and reverse child lookup;
- dependency and governance reverse lookup;
- reconciliation-package / obligation lookup by referenced artifact;
- verification evidence / applicability lookup by referenced artifact or claim;
- efficient querying of already-authoritative lifecycle metadata where useful.

Existing authoritative lifecycle metadata, including Project `resume_state`, may be indexed or mirrored for efficient querying but remains owned by Markdown/Git. `resume_state` retains only its Section 05 meaning: the Project lifecycle state to return to after `PAUSED`; it is not a generic workflow cursor.

SQLite must not become authoritative for requirements, architecture decisions, artifact identity, lifecycle ownership, reconciliation semantics, verification history, or other accepted project truth.

Point 06.1 deliberately does **not** define database tables/columns, minimum relationship representation, operational workflow checkpoints, command-resume state, disagreement handling, or rebuild mechanics. Those remain owned by their dedicated Point 06 items.

The governing boundary is:

> **SQLite may help Kilo find authoritative truth cheaply; it does not become the authority that defines that truth.**
- [x] What must remain authoritative in Markdown/Git.

### Locked design — what must remain authoritative in Markdown/Git (Point 06.2)

Markdown/Git is the authoritative store for all durable accepted project truth. This includes:

- artifact identity and authoritative metadata;
- lifecycle state;
- structural, dependency and governance declarations;
- Project `resume_state`;
- authoritative artifact semantic content, including requirements, scope, contracts, acceptance criteria and architecture/product decisions;
- reconciliation records, dispositions and obligations;
- verification evidence and applicability records;
- any durable escalation resolution or developer-owned decision that becomes accepted project authority under its owning workflow.

Git remains the authoritative history/provenance mechanism for changes to that truth.

SQLite, if adopted, may index or mirror this information but must never be its sole authoritative store.

SQLite may own only reconstructable operational convenience state whose loss cannot erase an accepted decision, requirement, lifecycle fact, dependency declaration, reconciliation obligation, verification fact, or other durable project truth, and cannot force the developer to remember or re-decide settled information.

The recovery invariant is:

> **Delete the SQLite database. Kilo must still be able to reconstruct all accepted project truth from Markdown + Git without asking the developer to remember or re-decide anything.**

Loss of SQLite may cause temporary operational inconvenience — for example, recalculating a lookup, rediscovering the next workflow step, or restarting/reconstructing a non-authoritative execution checkpoint — but it must never make the project semantically incomplete.

This point defines the authority boundary only. Exact operational checkpoint/resume persistence remains owned by the later dedicated Point 06 items.
- [x] Artifact ID → file path mapping.

### Locked design — Artifact ID → file path mapping (Point 06.3)

Artifact ID → file path is **derived, rebuildable locator information**, never authoritative identity.

Given a canonical Project/Epic/Feature/Spec ID, Kilo resolves it to exactly one repository-relative artifact file.

Lookup semantics:

1. Validate the requested ID against the canonical Section 05 artifact-ID rules.
2. If a valid SQLite index exists, use its ID → repository-relative path mapping as the fast path.
3. A fast-path hit still performs a cheap authoritative identity check:
   - the mapped file must exist;
   - read only enough front matter to confirm the canonical `id` and `type`;
   - do not load the full Markdown body merely to validate identity.
4. If SQLite is absent, stale, invalid, or misses the ID, fall back to deterministic filesystem/Markdown discovery within the bounded canonical artifact locations defined by Point 13.
5. Fallback lookup validates only the requested ID and its exact candidates; it does not perform a repository-wide integrity scan.
6. Exactly one valid artifact match returns its repository-relative path.
7. Zero valid matches return `ARTIFACT_NOT_FOUND`.
8. Multiple artifacts claiming the same canonical ID return `DUPLICATE_ARTIFACT_ID`.
9. Filename/front-matter identity disagreement returns `ARTIFACT_IDENTITY_MISMATCH`.
10. Kilo never resolves any of these integrity failures through semantic guessing.

File moves change only the derived locator. Artifact identity and references remain unchanged.

SQLite mapping is fully rebuildable from Markdown/filesystem state. A stale SQLite path is a cache/index staleness condition, not evidence that the artifact is authoritative at that location.

Index build/rebuild performs **repository-wide structural validation for the indexed artifact set** before publishing a new valid index. It must detect at least duplicate artifact IDs and filename/front-matter identity mismatches. If any such corruption is found:

- the new index is not published as valid;
- no arbitrary winner is indexed;
- any existing index must not be treated as freshly valid;
- Kilo may continue using deterministic Markdown/filesystem lookup;
- the authoritative repository corruption must be repaired before a successful rebuild can publish a valid index.

The index therefore has an all-or-nothing validity guarantee: it either represents an artifact set that passed structural integrity checks at build time, or it is not considered valid.

An unavailable or invalid SQLite index disables the optimization, not Kilo itself.

Point 06.3 applies only to the four Section 05 artifact identity classes: `PROJECT-*`, `EPIC-*`, `FEATURE-*`, and `SPEC-*`. It does not expand into locating reconciliation records, verification records, ADRs, source files, tests, or other record types.

This point deliberately does **not** define when rebuild/reindex runs. Trigger policy belongs to the later Point 06 Recovery/Rebuild-Reindex items. Exact artifact directories remain Point 13's responsibility.
- [x] Minimum relationships required.

### Locked design — minimum relationships required (Point 06.4)

If SQLite is adopted, its minimum relationship index consists only of **direct relationships already authoritative in Markdown/Git and required for deterministic lookup**.

Minimum indexed relationship families:

- artifact `parent_id` → artifact;
- artifact `depends_on` → referenceable project source, preserving Point 02's semantic meaning of reliance on a decision, contract or behaviour rather than constraining the edge by target type;
- artifact `governed_by` → accepted authority source;
- any direct persisted governance-coverage relationships defined by the authoritative dependency model;
- reconciliation package / obligation → referenced artifact;
- verification evidence / applicability → `(artifact_id, claim_ref)` association.

For verification lookup, `claim_ref` is queryable as part of the artifact-scoped composite identity `(artifact_id, claim_ref)`. It is not promoted into a separate global Claim entity.

The following remain **derived views**, not separately authoritative relationships:

- `Contains` / children, derived from `parent_id`;
- reverse dependents;
- reverse governance;
- transitive dependency or governance closure;
- higher-level Feature/Epic roll-ups;
- effective governance;
- other mechanically derived ancestry/descendant views.

SQLite may maintain reverse indexes or equivalent query structures for efficiency, but those are indexes over authoritative direct relationships, not new semantic project edges.

Point 06.4 does not introduce or redefine dependency/governance schema. It consumes the relationship semantics and authoritative representation already established by Points 02/05. SQLite must not infer or invent relationships from code, prose similarity, naming, file proximity, call patterns or other semantic guesses.

Core rule:

> **Index direct authoritative relationships; derive reverse, structural and transitive views mechanically.**
- [x] Workflow checkpoint requirements.

### Locked design — workflow checkpoint requirements (Point 06.5)

Workflow checkpoints are **minimal, replaceable operational continuation markers** for interruptible multi-step workflows.

A checkpoint answers only:

> **Where can this workflow safely continue from?**

It does not carry accepted project truth.

Checkpoint rules:

- A checkpoint is advanced only after the preceding safe workflow boundary and any authoritative writes belonging to that boundary have persisted successfully.
- A checkpoint may identify the workflow/command, owning Project/Epic/Feature/Spec or work-package reference, execution mode, last safely completed boundary, next logical action, and references to unresolved durable records relevant to continuation.
- A checkpoint must reference durable project truth rather than copy accepted semantic content into operational state.
- If execution stops between safe checkpoints, Kilo resumes from the previous completed boundary and may repeat unfinished operational work rather than assume it completed.
- Kilo does not serialize mid-reasoning state, chain of thought, half-completed tool sequences, expanded context packets, source snapshots, or permanent execution logs into checkpoints.
- Checkpoints are current continuation state, not workflow history. Git and authoritative workflow records remain the historical record.
- Continuation always reconstructs fresh minimum-sufficient context from current authoritative state under Point 03; a checkpoint is never a replay packet.
- A checkpoint is a continuation hint, never proof that current project state still permits continuation. Authoritative state always wins.

Checkpoint state is intentionally the first class of state that may live **only in SQLite with no Markdown mirror**, because it is non-authoritative operational convenience state permitted by Point 06.2.

If SQLite is deleted or unavailable, checkpoint state may be lost. Kilo must recover by inspecting current authoritative Markdown/Git state and restarting from the latest safe boundary it can deterministically establish. Recovery may repeat unfinished or recently attempted operational work, but it must not lose accepted project truth or require the developer to remember or re-decide anything.

Point 06.5 defines the checkpoint mechanism only. **Point 07 determines which commands actually use checkpoints and defines their command-specific safe continuation boundaries.** A command whose Point-07 contract does not require checkpoints restarts/recomputes rather than participating in checkpoint persistence.

Checkpoints must never be the sole store for:

- accepted answers or decisions;
- requirements, contracts or semantic artifact content;
- draft semantic content that exists nowhere else;
- lifecycle/reconciliation/evidence truth;
- model conversation history or chain of thought;
- partial tool execution state;
- source-code snapshots;
- permanent execution history.

Core rule:

> **A checkpoint is a bookmark, not authority: persist project truth first, then advance the operational continuation marker. Losing the marker may cause repetition, never loss of accepted truth.**

Exact resume interpretation and stale-checkpoint handling remain owned by the later Point 06 resume/recovery items.
- [x] Resume-state requirements.

### Locked design — resume-state requirements (Point 06.6)

Workflow resume state is a **reconstructed continuation position**, not a stored execution snapshot.

It is distinct from Project `resume_state` defined in Point 05:

- Project `resume_state` is authoritative lifecycle metadata used only when Project is `PAUSED`, identifying the lifecycle state to return to.
- Workflow resume state is operational continuation information used to resume an interrupted command/workflow.
- Workflow resume must never overload or repurpose Project `resume_state`.

Effective workflow resume state is derived from:

1. current authoritative Markdown/Git project/workflow truth;
2. the optional SQLite checkpoint defined by Point 06.5;
3. the owning command's continuation contract defined by Point 07.

On continuation, Kilo must:

- identify the owning workflow/command and active scope/work package;
- reconstruct fresh minimum-sufficient context from current authoritative state under Point 03;
- determine the latest authoritatively proven safe completed boundary;
- validate any SQLite checkpoint against that authoritative state;
- re-evaluate current prerequisites, lifecycle/readiness conditions, unresolved escalations, reconciliation obligations, dependency/authority changes and other blockers relevant to the owning command;
- only then select the next command-defined action.

Core principle:

> **Resume restores position, never permission.**

A checkpoint may accelerate locating the continuation position, but it never proves that continuation from that position remains valid.

Checkpoint cases:

- **Valid/current checkpoint** — checkpoint agrees with authoritative state; continue from that safe boundary after normal prerequisite validation.
- **Missing checkpoint** — reconstruct the latest safe continuation boundary deterministically from authoritative Markdown/Git state.
- **Checkpoint behind authority** — authority wins; advance the derived continuation position to the latest authoritatively established safe boundary.
- **Checkpoint ahead of authority** — this is not ordinary staleness. Under Point 06.5's write-ordering invariant, it indicates checkpoint/authority divergence and must emit a deterministic integrity diagnostic such as `CHECKPOINT_AUTHORITY_DIVERGENCE`.

For a checkpoint-ahead anomaly, Kilo must still recover safely toward authority:

- discard the unsupported checkpoint position;
- reconstruct the latest authoritatively proven safe boundary;
- revalidate current prerequisites;
- continue if otherwise valid.

The integrity diagnostic is non-authoritative and does not itself create a lifecycle state, project-truth record, or `HUMAN_DECISION_REQUIRED` condition. It exists to surface an implementation/integrity defect rather than silently masking it.

No accepted answer, requirement, contract, decision, or other durable project truth may exist solely in workflow resume/checkpoint state. Anything necessary to avoid asking the developer to remember or re-decide settled information must already exist in authoritative durable state.

Workflow resume/checkpoint state may contain only operational continuation information such as:

- workflow/command identity;
- owning scope/work-package reference;
- execution mode where relevant;
- last safe checkpoint/boundary identifier;
- next-action hint.

It must not contain copied semantic authority, cached context packets, reasoning summaries, conversation history, or other shadow project truth.

Point 07 owns command-specific resumability, safe continuation boundaries, durable-state interpretation and next-step semantics. Point 06.6 defines only the universal resume contract.

Core rule:

> **Resume is reconstructed from current authority, optionally accelerated by a checkpoint. Authority may move the continuation position forward or backward; the checkpoint never overrides it.**
- [x] Reconciliation-state requirements.

### Locked design — reconciliation-state requirements (Point 06.7)

Reconciliation state is split between **authoritative reconciliation truth** and **disposable operational execution state**.

Authoritative reconciliation truth remains in Markdown/Git. SQLite may index it for efficient lookup, but must never be its sole owner.

Authoritative reconciliation truth includes at least:

- reconciliation package identity;
- reconciliation package lifecycle `ASSESSING | OPEN | CLOSED`;
- accepted authority delta;
- per-artifact reconciliation dispositions;
- reconciliation obligations and their statuses;
- new-work, retirement, reverification and decision obligations;
- dependency gaps discovered during reconciliation;
- evidence/applicability decisions;
- unresolved decisions;
- references to affected artifacts/claims;
- overlap, merge or supersession relationships between obligations/packages;
- any other durable reconciliation outcome defined by Points 01/05.

If deleting SQLite would make Kilo forget any such fact, the design is invalid.

SQLite may index authoritative reconciliation state to answer deterministic queries such as:

- which OPEN reconciliation packages affect an artifact;
- which OPEN obligations reference a given artifact;
- which reconciliation packages contain DECISION_REQUIRED for an artifact;
- which obligations remain before a package may close.

SQLite may additionally hold **reconstructable operational state** for an in-progress `ASSESSING` reconciliation, including:

- current reconciliation package reference;
- current reconciliation phase;
- deterministic candidate-closure/cache used for traversal;
- current traversal position / next-candidate hint;
- whether the bounded consistency-scan step is next.

Operational reconciliation state follows the same persist-before-advance ordering established by Point 06.5:

1. classify/process the current reconciliation step;
2. persist every durable semantic result produced by that step to the authoritative reconciliation package or other authoritative record;
3. only after persistence succeeds, advance the SQLite operational position.

A candidate is never considered durably assessed merely because SQLite marks it processed.

If SQLite is lost during `ASSESSING`, Kilo must:

1. reload the authoritative reconciliation package;
2. reconstruct current dependency/authority relationships;
3. recompute the deterministic reconciliation mechanics required by the Point-01 algorithm;
4. identify assessment results already persisted authoritatively;
5. continue from the remaining safe work without asking the developer to repeat settled decisions.

Operational reconciliation state must be revalidated against current authoritative state on resume. Cached candidate queues, traversal positions or other SQLite state never define reconciliation scope or override current dependency/authority truth.

Package lifecycle and obligation resolution remain authoritative Markdown/Git facts. SQLite-derived counters, cached `open_obligation_count` values, traversal completion flags or equivalent convenience fields may accelerate checks but can never by themselves transition a package to `OPEN`/`CLOSED` or mark an obligation `RESOLVED`/`SUPERSEDED`.

Overlap, merge and supersession semantics also remain authoritative. SQLite may index such relationships, but it cannot be the only place recording that one obligation or reconciliation package supersedes, merges with or replaces another.

SQLite must never be the sole store of:

- authority delta;
- candidate semantic classification;
- artifact disposition;
- obligation or obligation status;
- human decision;
- dependency-gap finding;
- evidence invalidation/applicability decision;
- overlap/merge/supersession decision;
- package lifecycle;
- reconciliation completion.

**Candidate-closure boundary:** whether the authoritative `REC-###` package additionally records the initially computed candidate closure for audit purposes is a Point 01 reconciliation-algorithm decision, not a Point 06.7 concern. Because candidate closure is deterministically derivable from authoritative reconciliation input plus authoritative dependency relationships, SQLite's operational cache of that closure remains disposable regardless of whether Point 01 later chooses to persist an audit snapshot.

Core rule:

> **Persist reconciliation truth first; use SQLite only to accelerate lookup and remember reconstructable execution position. Losing SQLite may repeat reconciliation mechanics, never erase a reconciliation decision or obligation.**
- [x] Context lookup requirements.

### Locked design — context lookup requirements (Point 06.8)

SQLite may answer **where required context lives and which authoritative sources are mechanically related to the current task**. It must not answer what that context means.

SQLite context lookup may accelerate:

- artifact/reference identity → authoritative source/path lookup;
- parent/ancestor/descendant traversal;
- direct and reverse dependency lookup;
- direct and reverse governance lookup;
- direct persisted governance-coverage relationship lookup;
- reconciliation-package / obligation lookup by referenced artifact;
- verification evidence/applicability lookup by artifact and `(artifact_id, claim_ref)`;
- lookup of already-authoritative lifecycle/workflow metadata where useful;
- construction of Point 03.10's deterministic Phase-A context skeleton from indexed authoritative facts.

A Phase-A skeleton may identify sources such as the active artifact, parent/ancestor chain, declared dependencies, governing authorities, relevant reconciliation/obligation records, verification/evidence records and other durable workflow references required by the owning stage.

Lookup results are **locators and relationship facts, not semantic context**.

Core boundary:

> **SQLite may establish relevance/location mechanically; authoritative-source resolution establishes freshness and meaning.**

Before a workflow relies on what a referenced source actually says, Kilo must resolve the current authoritative source and apply Point 03's freshness, mandatory-context and minimum-sufficient-content rules. A SQLite hit never replaces reading current authoritative semantic content where that content can affect the result.

Context lookup must remain **bounded and composable**. Prefer small deterministic operations such as resolving an artifact, getting its parent/ancestors, finding direct dependencies/governing authority, or locating open reconciliation/evidence references. SQLite must not expose a generic semantic "give me everything relevant to this task" mechanism that silently takes over Point 03's context-selection policy.

Derived relationships may be returned as query results where they are mechanically computable from authoritative indexed edges, but they do not become new authoritative relationships.

SQLite context lookup explicitly does **not** become:

- semantic/full-text relevance search;
- vector similarity or RAG;
- generated relevance ranking;
- code-semantic dependency discovery;
- a durable semantic-summary store;
- a persisted context-packet store;
- a cache of prior model conversations or expanded invocation context.

When deterministic indexed lookup is insufficient, Point 03.11's bounded targeted discovery rules apply.

If SQLite is missing, invalid, stale or incomplete for the requested lookup, Kilo falls back to deterministic Markdown/filesystem/reference discovery. Index failure may increase lookup cost; it must never cause mandatory context to be omitted or weaken correctness.

SQLite may additionally cache source fingerprints **only as a non-authoritative freshness optimization**, using whatever fingerprint definition Point 03's freshness rules ultimately establish. A cached fingerprint may help short-circuit obviously unchanged sources, but it is never itself proof of freshness.

- fingerprint absence means Kilo computes/reads from the authoritative source directly;
- fingerprint mismatch is a stale-cache miss, not a project inconsistency;
- a mismatched source is resolved from current authority before use;
- deleting SQLite must leave freshness checking fully functional, only less optimized.

Point 06.8 does not define the fingerprinting mechanism itself (hash, mtime, size, combination, invalidation trigger, etc.). That remains owned by Point 03's freshness model / later implementation design.

Core rule:

> **Use SQLite to cheaply locate and relate authoritative sources; use the authoritative sources themselves to establish current meaning and freshness.**
- [x] Database location.

### Locked design — database location (Point 06.9)

If SQLite is adopted, Kilo uses exactly **one project-local database per target project repository/workspace**.

The database lives under a stable Kilo-owned directory at the **target project's repository root**, preferably:

`.kilo/index.db`

"Target project repository" means the repository of the application/product being designed and built (for example MFHistory, ArthaBeacon, VidyaBeacon, etc.), **not** the separate Kilo tooling/configuration repository such as `kilo-configuration`.

Location/scope rules:

- one SQLite database per target project repository/workspace;
- never one shared/global database across multiple projects;
- no user-global registry under home/AppData or equivalent;
- no per-artifact, per-Epic, per-Feature, per-Spec or per-command databases;
- the database must live outside authoritative documentation/artifact directories such as `docs/`;
- the location must be stable and known to all Kilo commands/agents;
- deleting the database must be safe and may only cause rebuild/recovery work, never loss of accepted project truth.

The hidden `.kilo/` directory is a Kilo-owned local runtime/index namespace. Its existence does not imply that additional runtime files should be created without a demonstrated need.

The filename `index.db` is preferred over a generic `state.db` because the dominant role locked in Points 06.1–06.8 is a rebuildable index/cache plus limited operational checkpoint state, not an authoritative project-state database.

Point 06.9 defines **location and project scope only**. Whether `.kilo/index.db` is committed, ignored, regenerated on clone, or otherwise treated by Git remains Point 06.10.

Core rule:

> **The SQLite database belongs to the target project checkout, not to Kilo's tooling checkout, and deleting it must cost only reconstruction—not project truth.**
- [x] Repository/Git treatment.

### Locked design — Repository/Git treatment (Point 06.10)

The target project's `.kilo/` directory is **local, disposable Kilo runtime/index state** and must never participate in Git history.

The target project's tracked `.gitignore` must ignore the entire directory:

`.kilo/`

Repository/Git rules:

- neither `.kilo/index.db` nor SQLite companion files such as WAL/SHM/journal files are committed;
- the database is never merged, versioned, reviewed, backed up through Git, or treated as project history;
- a fresh clone does not need to contain `.kilo/`; Kilo creates it on demand if/when the local index is used;
- no `.gitkeep` is required for `.kilo/`;
- Git clone, checkout, branch switch, reset, rebase, merge, pull or other repository operations must never depend on preserving the database;
- SQLite differences between clones, machines, branches or working trees do not constitute project divergence;
- Git remains the history and transport mechanism for authoritative Markdown/project truth.

The ignore rule applies to the **entire `.kilo/` namespace**. If a future Kilo file needs Git history to preserve correctness, accepted truth, shared configuration or durable project knowledge, it must live in an appropriate authoritative location **outside `.kilo/`**. Do not add negated `.gitignore` carve-outs such as `!.kilo/something-important.md` to mix authoritative files into the disposable runtime namespace.

### Git worktree rule

Each physical target-project working tree uses its **own** `.kilo/index.db`.

Git worktrees may share underlying Git repository/object storage, but their checked-out and uncommitted file contents may differ. Since SQLite indexes the current working tree rather than merely a commit SHA, separate worktrees must not share one database.

For example:

`/project-main/.kilo/index.db`

and

`/project-feature-x/.kilo/index.db`

are independent local indexes even when both worktrees belong to the same underlying Git repository.

Git operations may make an existing local index stale. Point 06.10 establishes only that Git state never makes the database authoritative and that the database is not version-controlled. Exact staleness detection, recovery and rebuild/reindex behaviour remain owned by the later Point 06 items.

Core rule:

> **Git stores and transports the project; `.kilo/` stores disposable local acceleration state. If a file needs Git history, it does not belong in `.kilo/`.**
- [x] Recovery behaviour.

### Locked design — recovery behaviour (Point 06.11)

SQLite recovery is always **fail-safe toward authoritative Markdown/Git/filesystem state**.

Core principle:

> **SQLite failure degrades Kilo from fast to reconstruct-from-authority; it must not degrade correctness.**

#### Failure class 1 — database missing

A missing database is a normal recoverable condition, including:

- fresh clone;
- new Git worktree;
- manual deletion of `.kilo/`;
- cleanup of local runtime state.

Kilo falls back to authoritative Markdown/Git/filesystem discovery and reconstructs whatever lookup/resume information is required. If an operational checkpoint was lost, Point 06.6 applies: derive the latest authoritatively proven safe continuation boundary and repeat operational work where necessary.

Missing SQLite may increase cost or repeat work, but is not a project-integrity failure.

#### Failure class 2 — database unreadable, corrupt or incompatible

If `.kilo/index.db` is unreadable, corrupt, schema-incompatible, cannot be opened, or otherwise has uncertain internal integrity, Kilo emits a deterministic operational diagnostic such as `KILO_INDEX_UNAVAILABLE` with an appropriate reason.

For these integrity-level failures, **the entire local database is treated as untrusted**, not merely the records that happened to expose the problem.

Kilo must not attempt partial-trust bookkeeping such as "valid rows", "poisoned rows" or "probably safe tables". It stops using that database and falls back to authoritative state until a new valid index exists.

This matches Point 06.3's all-or-nothing index-validity stance.

A single proven-stale cached entry is different:

- stale path mapping;
- stale fingerprint;
- other isolated cache miss.

Those invalidate/fallback for that lookup only and do not imply whole-database corruption.

Boundary:

> **A stale entry is a wrong cached answer to one lookup; database-integrity uncertainty invalidates the whole local index.**

Exact replacement/rebuild timing remains Point 06.12.

#### Failure class 3 — authoritative persistence succeeds, SQLite write fails

If an authoritative Markdown/Git write succeeds and a subsequent SQLite/index/checkpoint update fails, the authoritative operation remains successful.

Kilo must not roll back, reinterpret or invalidate project truth merely because the disposable acceleration layer failed.

Recovery behaviour:

1. preserve the successful authoritative result;
2. surface local-index degradation where useful;
3. stop relying on the failed/untrusted SQLite operation;
4. continue from authoritative state/fallback behaviour where possible;
5. rebuild/recover the local index later under Point 06.12.

This applies equally to reconciliation: if a disposition/obligation was persisted authoritatively but advancing the SQLite traversal/checkpoint fails, later execution may repeat mechanical work but must recognize the already-durable reconciliation result.

Core invariant:

> **Failure to persist disposable state never invalidates a successfully persisted authoritative operation.**

#### Failure class 4 — interruption before authoritative persistence

If execution stops before a step's durable authoritative result has been persisted, recovery returns to the previous authoritatively proven safe boundary.

The unfinished step may be repeated.

Kilo prefers repeating unfinished operational work over assuming completion that authority cannot prove.

#### Recovery must not require manual SQLite repair

The developer must not be required to open SQLite and repair rows/tables to continue normal project work.

Diagnostics may expose an implementation defect for debugging, but operational recovery is through authoritative fallback/reconstruction whenever authoritative state itself is healthy.

#### When recovery may block

SQLite failure alone never creates `HUMAN_DECISION_REQUIRED`.

If fallback cannot continue, the blocker must come from authoritative project state, for example:

- duplicate artifact IDs;
- contradictory authoritative records;
- missing mandatory authority;
- genuine workflow-significant ambiguity.

Database failure is an operational problem. Authoritative-state ambiguity or corruption is a project-integrity problem and follows the existing standing safety rules.

#### Recovery direction is one-way

Recovery always flows:

`authoritative Markdown/Git/filesystem → SQLite`

never:

`SQLite → repair authoritative Markdown/Git`

Kilo must not rewrite authoritative project state merely to make it match what the old database remembered.

Point 06.11 defines correct fallback behaviour only. **Point 06.12 owns when and how rebuild/reindex occurs**, and the later database-vs-Markdown disagreement item owns explicit disagreement-handling policy.

Core rule:

> **Losing or invalidating SQLite may cost reconstruction and repeated operational work, but never accepted truth, never settled decisions, and never correctness.**
- [x] Rebuild/reindex behaviour.

### Locked design — rebuild/reindex behaviour (Point 06.12)

Kilo distinguishes **targeted refresh/reindex** from **full rebuild**.

Core principle:

> **Use the cheapest repair whose correctness can be established; escalate to full rebuild when the affected index scope cannot be bounded confidently.**

#### Targeted refresh

When Kilo knows exactly which authoritative fact changed and can mechanically determine the affected derived index entries, it should refresh only that bounded scope after the authoritative write succeeds.

Typical cases include:

- artifact identity/path changes;
- lifecycle metadata changes;
- direct dependency/governance relationship changes;
- reconciliation/evidence association changes;
- stale locator/fingerprint discovered during lookup.

A targeted refresh may update the directly affected record plus mechanically derived reverse/index structures required to keep the bounded lookup set internally consistent.

A targeted refresh affecting multiple derived entries must apply as a **single atomic database operation/transaction**.

- all affected rows/views/index entries commit together, or none do;
- if the refresh fails before commit, it is treated as not-yet-applied rather than partially applied;
- partial application of a targeted refresh is never a valid trusted index state;
- the prior index state remains in place pending retry, authoritative fallback or escalation to full rebuild;
- if atomic bounded repair cannot be established confidently, Kilo escalates to full rebuild rather than introducing partial-validity bookkeeping.

This extends the same persist/advance discipline used elsewhere in Point 06 into the index itself.

#### Full rebuild triggers

A full rebuild is required when at least one of the following applies:

- `.kilo/index.db` is absent and Kilo chooses to initialize it;
- Point 06.11 invalidated the whole database because of corruption, unreadability or integrity uncertainty;
- database schema/version is incompatible;
- a failed/interrupted index operation leaves database-wide validity uncertain;
- Kilo cannot determine the affected index scope strongly enough for a correct targeted refresh;
- explicit integrity validation determines that the currently published index cannot be trusted as a whole.

An isolated known stale entry does not by itself require full rebuild; it receives targeted fallback/refresh where correctness can be bounded.

#### Rebuild source of truth

A full rebuild is produced solely from the **current authoritative target-project working-tree state**:

- authoritative Markdown/project records;
- authoritative persisted relationships;
- current filesystem/project structure defined by the relevant points;
- current uncommitted authoritative working-tree changes where applicable.

An old or untrusted SQLite database is never used as a source of project truth for rebuilding the replacement index.

Recovery/rebuild direction remains:

`authoritative Markdown/Git/filesystem → SQLite`

#### Build, validate, publish

A full rebuild must not construct the live `.kilo/index.db` in place.

Conceptually:

1. create a temporary candidate database;
2. scan current authoritative sources;
3. populate the required locator/relationship/workflow indexes;
4. run the repository-wide structural validation required by Point 06.3 and other applicable index invariants;
5. if validation fails, discard the candidate and do not publish it;
6. if validation succeeds, atomically publish/replace it as the valid `.kilo/index.db`.

A failed, incomplete or partially populated rebuild candidate is never exposed as a valid index.

This preserves Point 06.3's all-or-nothing validity guarantee across every full rebuild.

#### Current working tree, not merely Git HEAD

A rebuild indexes the actual physical target-project working tree, including relevant uncommitted authoritative changes.

Git commit SHA may be useful operational metadata, but it is insufficient as the definition of index freshness because different worktrees or uncommitted states may legitimately differ at the same commit.

#### Rebuild frequency

Kilo must not perform a repository-wide rebuild at the start of every command invocation.

Normal operation is:

- authoritative bounded change → targeted atomic refresh;
- isolated stale lookup → targeted authoritative fallback/refresh;
- missing/untrusted/incompatible/global-uncertain index → full rebuild when appropriate.

A missing database may be initialized lazily when indexed capability is first useful. Until then, Point 06.11's deterministic authoritative fallback remains valid.

Rebuild is therefore an initialization/recovery mechanism, not a mandatory command-start ritual.

#### Operational checkpoint treatment

A full rebuild may discard disposable SQLite-only workflow/reconciliation checkpoint state.

Kilo must not copy checkpoint rows from a database that has been declared untrusted merely to preserve execution convenience.

If checkpoint state is lost, Points 06.5/06.6 apply: reconstruct the latest authoritatively proven safe continuation boundary and repeat operational work where necessary.

A normal targeted refresh on an otherwise healthy database preserves unrelated operational checkpoint state.

#### Failed rebuild behaviour

If a rebuild fails because of SQLite/local mechanics, Kilo emits an operational diagnostic and continues through authoritative fallback where possible.

If the rebuild cannot publish because authoritative repository state violates required structural invariants, the repository-integrity problem is surfaced through the applicable existing rules.

Index rebuild failure by itself does not create `HUMAN_DECISION_REQUIRED`.

Point 06.12 does not define the complete semantics for database-vs-Markdown disagreement. It establishes only that rebuild/reindex always takes current authoritative sources as input, never repairs authority from SQLite, and never publishes an index that fails required validity checks. Explicit disagreement precedence/diagnostics remain Point 06.13.

Core rule:

> **Targeted refreshes are bounded and atomic; full rebuilds are authority-derived, privately built, fully validated and atomically published. No partially refreshed or half-built index is ever considered valid.**
- [x] Behaviour when database and Markdown disagree.

### Locked design — behaviour when database and Markdown disagree (Point 06.13)

When SQLite and authoritative Markdown/Git/filesystem state disagree, **authoritative state always wins**.

Core principle:

> **There is one authority and one cache. Disagreement is resolved by trusting authority and repairing or discarding the cache—not by reconciling two peers.**

Kilo must never:

- merge SQLite and Markdown as competing sources of truth;
- choose between them using timestamps, mtimes, Git commit time or last-write-wins logic;
- restore authoritative Markdown from SQLite merely because SQLite appears newer;
- recreate missing authoritative decisions/relationships from SQLite;
- use SQLite to break ties between contradictory authoritative records.

SQLite values are accepted only insofar as they remain consistent with current authoritative state.

#### Case 1 — ordinary stale-cache disagreement

If authoritative state is valid and the disagreement can be bounded to known derived entries, treat it as ordinary cache staleness.

Examples include:

- stale artifact path;
- stale source fingerprint;
- stale indexed dependency/governance relationship;
- stale reconciliation/evidence lookup entry.

Behaviour:

1. use the authoritative value immediately;
2. ignore the stale SQLite value for that lookup;
3. repair the affected index scope using Point 06.12's atomic targeted refresh;
4. continue.

No `HUMAN_DECISION_REQUIRED` is created merely because the cache was stale.

#### Case 2 — SQLite is ahead of what authority can prove

If SQLite claims durable progress/truth that authoritative state does not prove, and Point 06's persist-before-advance rules say such a condition should not normally be reachable, treat it as an integrity anomaly.

Examples include:

- checkpoint claims a later safe boundary than authority proves;
- reconciliation execution state claims an artifact was durably assessed but no authoritative reconciliation result exists;
- other operational state claims completion that should only have been recorded after an authoritative write.

Behaviour:

1. discard the unsupported SQLite claim;
2. fall back to the latest authoritatively proven state;
3. emit an appropriate deterministic integrity diagnostic (for example the existing `CHECKPOINT_AUTHORITY_DIVERGENCE` where applicable);
4. continue if authoritative state itself remains valid and prerequisites allow it.

This anomaly does not by itself create `HUMAN_DECISION_REQUIRED`.

#### Case 3 — apparent disagreement reveals authoritative repository integrity failure

Before treating a mismatch as stale SQLite, Kilo must establish that the authoritative source for that lookup is itself sufficiently well-formed to determine truth.

Examples of authoritative-state integrity failures include:

- duplicate artifact IDs;
- filename/front-matter identity mismatch;
- contradictory authoritative records;
- malformed authoritative metadata;
- genuine workflow-significant authority ambiguity.

In these cases, SQLite is not used to choose a winner.

The applicable repository-integrity diagnostic or standing `HUMAN_DECISION_REQUIRED` rule governs the affected path.

**Authoritative-state integrity problems do not by themselves invalidate the rest of the local SQLite index.** The problem lives in the repository, not in SQLite. Unrelated index entries may remain trusted; only the affected lookup/path is blocked or bypassed pending authoritative repository repair.

Whole-database invalidation remains reserved for SQLite-side integrity uncertainty under Point 06.11 (for example corruption, unreadability or schema/integrity uncertainty).

#### SQLite-only operational state

Some operational checkpoint/resume state intentionally has no Markdown mirror under Points 06.5/06.6.

Such state is still subordinate to authority.

Kilo validates the operational claim against current authoritative state:

- checkpoint behind authority → derive/advance the current continuation position from authority;
- checkpoint ahead of authority → integrity diagnostic and fallback to the latest proven boundary;
- checkpoint cannot be validated safely → discard it and reconstruct continuation from authoritative state.

The absence of a second Markdown copy does not promote SQLite operational state into project authority.

#### Timestamp rule

Timestamps, mtimes, cached fingerprints and Git commit metadata may help detect staleness, but they never determine which side is authoritative.

A newer SQLite row is still cache state. An older authoritative Markdown file is still authority.

Core rule:

> **A cache does not get a vote. Valid authority wins; stale cache is repaired, unsupported cache claims are discarded and diagnosed, and broken authority is repaired as authority rather than being overridden by SQLite.**
- [x] Whether SQLite materially reduces token/context consumption.

### Locked design — SQLite material-value evaluation contract (Point 06.14)

Whether SQLite materially reduces token/context consumption is an **empirical decision**, not an architectural assumption.

The required POC must compare SQLite-assisted Kilo against a **competent Markdown-only deterministic baseline** implementing the same Point-03 minimum-sufficient-context rules.

The Markdown-only baseline must use deterministic filesystem/frontmatter/reference lookup wherever possible. It must not artificially force an LLM to read project documents merely to discover IDs, paths, hierarchy or relationships.

The comparison is therefore:

- Markdown-only deterministic lookup + Point-03 context assembly;
- SQLite-assisted deterministic lookup + the exact same Point-03 context assembly.

It is not:

- broad LLM-driven Markdown discovery versus SQLite.

SQLite may legitimately reduce model-facing discovery/assembly work, but it cannot claim savings for semantic authoritative content that both approaches must correctly read.

#### Required measurements

Across representative LARGE-project workflows, measure at least:

- total Kilo-managed model input tokens across the complete work unit;
- tokens introduced by context-discovery expansions;
- peak context size;
- expansion count;
- measurable duplicate-context avoidance where practical;
- authoritative files opened/read;
- deterministic lookup work;
- lookup/context-assembly latency;
- correctness/completeness of the Phase-A context skeleton;
- workflow-result correctness;
- recovery behaviour;
- implementation and maintenance complexity;
- approximate model/API cost where available.

Primary token accounting counts what actually enters model reasoning. Deterministic local file parsing or SQL work is measured separately and is not counted as model-token consumption.

#### Required workflow scenarios

The POC should exercise representative cases including:

- normal Spec implementation;
- Feature grooming/readiness;
- interrupted workflow resume;
- reconciliation candidate/obligation lookup;
- verification/evidence lookup;
- a localized task inside a materially larger project fixture.

#### Required operating conditions

Measure at least four operating conditions:

1. **Cold** — fresh clone/new worktree/no existing index;
2. **Warm** — healthy established index;
3. **Mutation** — bounded authoritative changes requiring targeted refresh;
4. **Recovery** — deleted, invalid, corrupt/incompatible or otherwise unusable index requiring fallback/reconstruction/rebuild behaviour.

Correctness equivalence is a **hard gate across all four conditions**, not only the steady-state warm path.

A SQLite implementation that is faster or cheaper when healthy but produces an incorrect, incomplete or silently degraded context skeleton/workflow result during cold start, mutation, corruption, fallback or rebuild **fails the correctness gate regardless of warm-path token savings**.

This explicitly validates the fail-safe contracts from Points 06.5–06.13 rather than treating recovery only as a latency benchmark.

#### Materiality gate

Correctness must be equivalent before cost/efficiency benefits are considered.

SQLite is considered materially valuable only if representative LARGE-project POC results show equivalent correctness and at least one substantial benefit:

1. **Model-token/context benefit** — use approximately **20% median reduction** in total model-token/context consumption across representative workflows as the initial materiality heuristic; or
2. **Operational deterministic benefit** — a substantial measured lookup/latency/scaling improvement that materially improves normal Kilo use even if token savings are smaller.

The ~20% figure is a design heuristic, not a scientific constant. One isolated benchmark improvement is insufficient; evaluate representative workflows rather than selecting the best result.

Operational benefit must also be measurable. "Feels cleaner" or "SQLite is more sophisticated" is not evidence.

Any demonstrated benefit must still justify the added schema, targeted-refresh, rebuild, recovery, diagnostics, smoke-test and maintenance complexity.

#### No sunk-cost preference

Points 06.1–06.13 being well-designed does **not** create a sunk-cost argument for adopting SQLite.

If the competent Markdown-only baseline proves sufficiently cheap, deterministic, reliable and maintainable, SQLite must be rejected even after all of Point 06's design work.

Conversely, SQLite may be adopted only when the POC demonstrates that its measurable value exceeds its implementation/maintenance cost.

#### Completion boundary

Point 06.14 locks the **evaluation methodology and decision gate** only.

The final Point-06 outcome — adopt SQLite or remain Markdown-only — remains pending until the required POC is actually executed and evaluated against this contract.

Core rule:

> **SQLite must earn its place empirically. Correctness must hold in cold, warm, mutation and recovery conditions; only then do token, latency and scaling improvements count toward adoption.**

### Required POC

Construct a representative LARGE-project fixture containing:

PRD → Epics → Features → Specs → Architecture decisions → Implementation references → Tests

Then compare Markdown-only context discovery with SQLite-assisted context discovery.

Measure:

- token/context reduction
- retrieval accuracy
- complexity
- maintainability
- failure/recovery behaviour

### Decision gate

SQLite should be adopted only if the POC demonstrates meaningful value.

If Markdown-only state proves sufficiently simple, reliable and inexpensive, SQLite should be rejected.

### Explicit non-goals

v0.2 is **not** building:

- a general-purpose knowledge graph
- a graph database
- a vector database
- a RAG system
- a semantic source-code graph
- a project-management database
- a generic persistence framework

### Expected outcome

Either:

> **Adopt a deliberately small SQLite state/index layer because it demonstrably improves our workflow.**

or:

> **Remain Markdown-only because additional persistence does not justify its complexity.**

Both are valid outcomes.

#### Locked command-family boundaries

- **Discovery vs decomposition:** `/ideate` answers "what are we building?"; `/grill` answers "is this bounded piece clear enough?". `/grill` is a supporting interrogator, never an artifact owner.
- **Outcome-driven decomposition:** Epic → Feature → Spec decomposition is based on independently meaningful outcomes, not merely breaking work into progressively smaller pieces. Each level should be designed so it can later satisfy its appropriate verification boundary. Exact verification obligations remain owned by Point 09.
- **Human-verifiable delivery:** LARGE Epics and Features must be shaped around outcomes that can ultimately be observed and human-evaluated through the product-appropriate surface, such as UI, API, CLI, event/message flow, generated artifact/output, or other externally observable behaviour. This does not imply every Feature needs a UI.
- **Planning ownership funnel:** `/ideate` owns product discovery; `/prd` owns product requirements; `/architect` owns system architecture; `/epic` owns a bounded end-to-end outcome; `/feature` owns a coherent integrated capability; `/spec` owns the implementation-ready behavioural contract; `/implement` owns execution; `/verify` owns factual evidence; `/review` owns qualitative engineering judgment.
- **Separate delivery authorities:** `/implement`, `/verify`, and `/review` remain separate and must not absorb each other's authority. Implementation does not declare completion; verification does not perform subjective review or accept risk; review does not replace missing verification evidence.
- **Diagnosis vs repair:** known failure with understood corrective action routes to `/fix`; uncertain root cause routes through `/diagnose → /fix`.
- **Reconciliation boundary:** `/shouldreconcile` and `/reconcile` are scoped to changes in accepted authority, not generic change management. Ordinary implementation adjustments, bug fixes, refactoring, or changes safely within accepted authority continue through the normal delivery/verification path.
- **Supporting-command rule:** a supporting command may investigate, challenge, clarify, repair, classify, or record evidence, but must never silently acquire ownership of the artifact or decision it supports. Control returns to the owning workflow.

Core rule:

> **One command owns each major lifecycle responsibility; supporting commands assist that owner without silently taking over its authority.**

### Locked design — input contracts for each command

Input contracts define the **minimum authoritative context a command must receive or discover before it is allowed to act**. They define semantic prerequisites and target resolution, not exact CLI syntax.

#### Shared input-contract rules

1. **The user supplies intent, not duplicated repository context.** The developer normally states what they want done and, where necessary, identifies the target artifact/change. Kilo loads existing accepted context itself.
2. **Persisted authority beats conversation memory.** PRDs, architecture, ADRs, Epic/Feature/Spec artifacts, dependency metadata, verification evidence, reconciliation records and other authoritative project state are loaded from persisted project sources. Chat history may help interpret intent but never substitutes for authority.
3. **Target identity must be unambiguous.** Canonical artifact IDs are preferred. Kilo may infer an omitted target only when exactly one eligible target exists in authoritative current workflow context. It must never guess among multiple candidates.
4. **Project mode is discovered, not re-specified each time.** STANDARD versus LARGE comes from project state/configuration.
5. **Commands load the minimum authoritative context required.** Context loading follows Point 03 rather than reading the whole project indiscriminately.
6. **Known information is not re-asked.** Existing authoritative answers, decisions, constraints, dependencies and artifact content are consumed rather than requested again.
7. **Missing authority is not invented.** If a required upstream decision genuinely does not exist, the established blocking/escalation rules apply.
8. **Optional user constraints remain authoritative.** The developer may add new constraints, focus areas, scope restrictions or supported model/adversary choices. Conflicts with accepted authority must be surfaced rather than silently overriding authority.
9. **Supporting commands require a support target.** Commands such as `/grill`, `/adversarial-check`, `/fix` and `/diagnose` operate on bounded work/decision/problem scope rather than roaming the repository looking for work.
10. **Exact CLI syntax is not part of this design point.** Positional arguments, flags and final command-file syntax are deferred to implementation/documentation.

#### Locked input edge cases and resolution rules

- **`/grill` owns question construction.** The user supplies the bounded subject; Kilo determines what remains ambiguous and which clarifying questions are necessary. The developer is not required to pre-build a questionnaire.
- **`/ideate` deliberately accepts minimal starting input.** Its purpose is discovery; requiring a mini-PRD as input would defeat the command.
- **Epic/Feature/Spec context is resolved by Kilo.** The developer identifies intended work/target; Kilo loads parent authority and dependencies rather than requiring pasted PRD/architecture/artifact context.
- **Readiness gates are input preconditions and cannot be bypassed by invocation.** `/feature` requires a parent Epic at `READY_FOR_FEATURE_DECOMPOSITION`; `/spec` requires a parent Feature at `READY_FOR_SPEC`; normal Spec-driven `/implement` requires a target Spec at `READY_FOR_IMPLEMENTATION`.
- **`/shouldreconcile` requires a delta, not merely an artifact.** A bare artifact ID is insufficient unless the proposed change is otherwise unambiguous.
- **`/reconcile` requires explicit human authorization.** A prior `SHOULDRECONCILE` result does not itself authorize reconciliation; the accepted new decision and instruction to proceed must be explicit.
- **`/implement` has two valid input shapes.** Normal delivery is Spec-driven; bounded maintenance/corrective work may proceed directly when it remains within accepted authority and genuinely does not require a new planning artifact. `/fix` remains preferred when repairing known failure evidence.
- **`/verify` Feature/Epic invocation semantics remain deferred to Point 09.** 07.3 locks only that verification requires an explicit target and the authoritative behaviour/acceptance contract applicable to that target.
- **Single-eligible-target inference is the general target-resolution mechanism.** If exactly one eligible target exists, Kilo may resolve an omitted ID from authoritative workflow context; if several candidates exist, Kilo must request/require disambiguation rather than guessing.

`NOT_DONE` is treated as existing verification-result vocabulary, not an artifact lifecycle state.

Core rule:

> **The human provides the intended action and any genuinely new decision or constraint; Kilo resolves and loads existing authoritative context itself. Every command requires explicit prerequisite authority and an unambiguous target, and no command may compensate for missing required inputs by inventing project truth.**

### Locked design — 07.4 Discovery/support output contracts

The Discovery/support family is locked for `/grill` and `/ideate`. This subsection does **not** complete all of Point 07.4; the remaining command families still require scrutiny.

#### Shared discovery/support rules

- Exit results are deterministic and describe what the current command invocation achieved; they do not silently imply downstream artifact readiness unless that command owns the relevant readiness gate.
- The command currently holding control returns its own exit contract. It does not "teleport" control into another command's blocked/result token.
- `HUMAN_DECISION_REQUIRED` is the single shared document-level stop result defined by the Standing Safety Principle. `/grill` and `/ideate` consume that global contract; they do not redefine, alias or specialize it locally.
- Ordinary in-progress questioning/research is not itself a result token. Result tokens fire at a meaningful session/command boundary or genuine inability to proceed.
- Supporting clarification never acquires artifact ownership. The owning workflow remains responsible for authoritative persistence/readiness decisions.
- Implicit resume must be deterministic and visible to the developer.

#### `/grill` result contract

`/grill` may exit with:

- `GRILL_RESOLVED`
- `GRILL_BLOCKED`
- `HUMAN_DECISION_REQUIRED` (shared global token)

##### `GRILL_RESOLVED`

`GRILL_RESOLVED` means the **explicitly bounded clarification scope** contains no unresolved material ambiguity.

It does **not** mean the owning Epic, Feature or Spec is ready.

Locked semantics:

- resolution is scope-local, not artifact-global;
- non-blocking unknowns may remain;
- `/grill` returns resolved decisions, clarified constraints, rejected assumptions and remaining non-blocking concerns to the owning workflow;
- `/grill` performs no readiness transition;
- accepted answers are checkpointed by the **owning command/workflow** as they are confirmed;
- `/grill` does not maintain a competing authoritative clarification artifact;
- control returns to the owning workflow, which re-evaluates the whole artifact.

Canonical flow:

```text
/feature
  ↓
/grill
  ↓
GRILL_RESOLVED
  ↓
/feature re-evaluates the whole Feature
  ↓
FEATURE_READY_FOR_SPEC
```

`/grill` intentionally has no `READY_FOR_*` result because it owns a bounded clarification question, not a lifecycle/readiness gate.

##### `GRILL_BLOCKED`

`GRILL_BLOCKED` means the bounded clarification cannot currently proceed because required **evidence, access or prerequisite authority** is unavailable.

It does not represent:

- an unresolved human choice;
- ordinary unfinished questioning;
- general artifact unreadiness.

Locked classification:

- missing evidence/access/prerequisite context → `GRILL_BLOCKED`;
- genuine developer choice/judgment → `HUMAN_DECISION_REQUIRED`;
- ordinary unanswered questions while grilling → continue grilling; no exit status yet.

If upstream authority is unresolved:

- if the bounded question remains independently answerable, `/grill` may continue and may still return `GRILL_RESOLVED`;
- if the missing authority makes the bounded question itself undefined/unanswerable, return `GRILL_BLOCKED` and identify the upstream owner/next action.

`GRILL_RESOLVED` is a statement about the current bounded scope, not a durability guarantee against future upstream reconciliation.

The blocked output identifies:

- blocking issue;
- responsible owner in descriptive terms using existing ownership concepts where possible;
- why it blocks;
- minimum required action;
- owning workflow to return to afterward;
- final token `GRILL_BLOCKED`.

No new blocker-owner enum is introduced here.

#### `/ideate` result contract

`/ideate` may exit with:

- `IDEATION_CONTINUE`
- `IDEATION_READY_FOR_PRD`
- `IDEATION_BLOCKED`
- `HUMAN_DECISION_REQUIRED` (shared global token)

##### `IDEATION_CONTINUE`

`IDEATION_CONTINUE` means the current ideation session made valid persisted progress, but discovery is not yet ready for PRD and no genuine blocking condition prevents further ideation.

It is a **pause condition**, not a failure.

Before returning `IDEATION_CONTINUE`, persist at minimum:

- confirmed answers/decisions;
- unresolved decision frontier;
- discovered facts/evidence;
- explicit assumptions;
- pending research;
- next unanswered questions;
- research progress where applicable;
- discovery-artifact version/fingerprint/checksum at persist time.

`IDEATION_CONTINUE` is valid only when meaningful ideation work remains that `/ideate` could continue performing without first receiving a blocking human decision.

Discriminator:

- if the user had kept talking, could `/ideate` still make useful progress on at least one independent frontier?
  - yes → `IDEATION_CONTINUE`;
  - no, every currently actionable remaining frontier depends on one or more explicit developer choices → `HUMAN_DECISION_REQUIRED`.

Multiple related human decisions may be presented as one coherent decision frontier rather than forcing repeated stop/start cycles.

`Next Owner: /ideate` (or whatever common routing field Point 07 later standardizes) expresses workflow ownership, not an obligation to continue immediately.

##### `IDEATION_READY_FOR_PRD`

`IDEATION_READY_FOR_PRD` means the persisted discovery artifact contains enough settled product-level understanding for `/prd` to begin without redoing discovery or inventing material product decisions.

Readiness does **not** require every possible unknown to be eliminated.

Allowed to remain:

- explicit non-blocking unknowns;
- implementation questions owned by architecture;
- facts that can safely be researched later;
- low-risk assumptions that are clearly marked and bounded.

Must not remain:

- unresolved material product decisions that `/prd` would have to invent.

The result authorizes the transition:

```text
/ideate → /prd
```

It does not imply PRD approval, architecture readiness, Project ACTIVE state, or implementation readiness.

##### `IDEATION_BLOCKED`

`IDEATION_BLOCKED` means discovery cannot safely proceed because required evidence/access/context is unavailable **and no safe bounded assumption exists**.

Quick discriminator:

- needed thing exists independently and must be fetched/observed → evidence problem;
- needed thing does not exist until an authorized person chooses → decision problem.

Examples:

- "What is the competitor's current pricing model?" → evidence;
- "What should our pricing model be?" → human decision.

Before blocking on missing evidence, `/ideate` should determine whether a safe bounded assumption can be recorded.

If yes:

- record the assumption as provisional;
- record what evidence would confirm/refute it;
- record which later decisions depend on it;
- continue discovery;
- if the session ends, return `IDEATION_CONTINUE`.

If no safe assumption exists, return `IDEATION_BLOCKED`.

Kilo should be conservative about assumptions that cross high-impact boundaries such as legality, security posture, irreversible architecture, major cost exposure or core product promises.

`IDEATION_BLOCKED` should use the same semantic blocked-output shape as `GRILL_BLOCKED`:

- Blocking Issue
- Owner
- Why It Blocks
- Required Action
- Return To / common routing field
- final token `IDEATION_BLOCKED`

##### Research during ideation

Research that Kilo can perform itself is **internal ideation work**, not a status transition.

No separate research-in-progress result exists.

Cases:

- Kilo can continue the research now → continue ideation; no exit token;
- research is obtainable but the session ends before completion → persist progress and return `IDEATION_CONTINUE`;
- required evidence cannot currently be obtained and no safe bounded assumption exists → `IDEATION_BLOCKED`.

Persisted research checkpoint information distinguishes at minimum:

- not started versus in progress;
- research question/obligation;
- sources/evidence already gathered;
- sufficiently supported partial conclusions;
- remaining research steps;
- partial results that must not yet be treated as settled facts.

Research checkpoint status is operational metadata, not artifact lifecycle state.

#### `/ideate` resume behaviour

Resume remains behavior, not a separate slash command.

A bare `/ideate` resolves the intended discovery target deterministically:

- zero eligible resumable discovery artifacts → start fresh ideation;
- exactly one eligible resumable discovery artifact → resume it;
- more than one eligible resumable artifact → require explicit target; never choose "most recently touched" as a tie-breaker.

Automatic resume eligibility:

- last result `IDEATION_CONTINUE` → directly resumable after checkpoint validation;
- last result `IDEATION_BLOCKED` → resume only after the blocker is revalidated as cleared;
- last result `HUMAN_DECISION_REQUIRED` → resume only after the required human decision is supplied/resolved;
- last result `IDEATION_READY_FOR_PRD` → do not silently reopen active ideation.

Before resuming, compare the persisted checkpoint/artifact fingerprint against current authoritative discovery state.

- unchanged → resume normally;
- changed but previous frontier remains applicable → refresh checkpoint and continue;
- materially changed → recompute from current authority;
- if applicability cannot be classified confidently → use the standing `HUMAN_DECISION_REQUIRED` rule rather than guessing.

Implicit resume must be visible to the user. A resumed invocation should identify that it is resuming, the target discovery artifact, the previously persisted unresolved frontier and whether the resume checkpoint was valid. A fresh invocation should visibly identify that it is starting new discovery.

Core rule:

> **Resume is implicit in `/ideate`, but never ambiguous or invisible. Automatic continuation is permitted only for an unambiguously resolved target with valid persisted resume state; blocked or decision-required discovery resumes only after its stopping condition has been demonstrably cleared.**

### Locked design — 07.4 Decomposition output/integrity foundation

The following rules are locked for the LARGE decomposition family `/epic → /feature → /spec`. This subsection establishes shared output, persistence and lifecycle-integrity semantics only; the remaining command-specific result-token scrutiny is still open.

#### Command-result versus lifecycle-state naming

Command results describe what the invocation accomplished. Lifecycle states describe the durable position of the artifact. They are separate namespaces and do not need identical names.

The readiness-result convention is:

- `EPIC_READY` → Epic state `READY_FOR_FEATURE_DECOMPOSITION`
- `FEATURE_READY` → Feature state `READY_FOR_SPEC`
- `SPEC_READY` → Spec state `READY_FOR_IMPLEMENTATION`

This deliberately preserves v0.1's `SPEC_READY` result while applying one consistent v0.2 rule to all three decomposition owners.

Result tokens are exact enum-like identifiers. Consumers must compare the complete documented token and must not infer semantics from suffix grammar such as `*_READY` or `*_BLOCKED`.

#### Healthy continuation results

The healthy-but-unfinished result family is:

- `EPIC_CONTINUE`
- `FEATURE_CONTINUE`
- `SPEC_CONTINUE`

These mean useful progress has been made/persisted, the current invocation/session has ended normally, no stopping condition prevents further safe work, and more authoring/grooming remains before readiness.

This intentionally matches the already locked `IDEATION_CONTINUE` semantics.

#### Waiting versus blocked versus human decision

The decomposition family distinguishes:

- `*_CONTINUE` — useful target-local work remains that can proceed independently of every currently blocking condition.
- `*_WAITING` — target-local productive work is exhausted and readiness is waiting only on a known, normally progressing declared dependency/prerequisite.
- `*_BLOCKED` — an abnormal prerequisite/evidence/access/authority condition prevents safe progress and there is no normal sequencing path that currently resolves it.
- `HUMAN_DECISION_REQUIRED` — the shared global stop result when an authorized developer choice is required before the affected path can proceed.

Known waiting/blocking/decision risks discovered during a `*_CONTINUE` invocation must be surfaced immediately even when they are not the primary final result. The final result describes the primary reason the invocation stops, not the only condition that exists.

`*_WAITING` is a derived command result, not a lifecycle state. Emitting it does not inherently require a state mutation. It relies on authoritative `depends_on[]` / prerequisite metadata already defined by Points 02/05. If the invocation discovers a missing dependency declaration, that authoritative metadata must be persisted before the command may rely on it to emit `*_WAITING`.

v0.2 performs no background WAITING→BLOCKED monitoring. Classification is reevaluated only when an applicable command/audit later examines the artifact.

Result-enumeration tables do not define precedence. The documented discriminator rules define the primary result.

#### Human-evaluable outcome scope

Ready Epic/Feature outputs must surface the human-evaluable delivery boundary they represent.

- `EPIC_READY` — human-evaluable end-to-end outcome required.
- `FEATURE_READY` — human-evaluable integrated capability required.
- `SPEC_READY` — independent human evaluability is not required; the output instead identifies the implementation behavioural slice plus its verification/acceptance expectations.

Exact Feature/Epic verification evidence remains owned by Point 09.

#### Parent lifecycle side effects

Already locked Point-05 triggers remain authoritative:

- first durable Feature under an Epic causes `READY_FOR_FEATURE_DECOMPOSITION → ACTIVE`;
- first durable Spec under a Feature causes `READY_FOR_SPEC → ACTIVE`.

When a command performs one of these parent transitions on the normal path, the output must surface the parent state change.

#### Persistence-before-result

A command may return a semantic workflow result only after every authoritative mutation required to make that result truthful has persisted and every mechanically required lifecycle invariant for that command has been validated.

A result does not itself imply that a write was required.

If a required authoritative mutation for the current invocation cannot be safely established, return:

> `PERSISTENCE_FAILURE`

This includes failure to persist a newly discovered `depends_on[]` relationship that the command needs in order to truthfully classify the current result.

SQLite/checkpoint failure after authoritative persistence succeeds does not become `PERSISTENCE_FAILURE`; Point 06's authoritative-first recovery rules apply.

#### Decomposition-local lifecycle-integrity preflight

The integrity preflight is deliberately local and mechanical. It does not walk the full ancestor chain and does not perform semantic blast-radius reasoning.

- `/feature` validates the mechanically relevant Feature↔immediate-parent-Epic child-triggered invariant.
- `/spec` validates the mechanically relevant Spec↔immediate-parent-Feature child-triggered invariant.
- `/epic` has no analogous Project child-triggered READY→ACTIVE invariant introduced by this rule.

Project remains a real Point-05 artifact type, but this preflight does not introduce any new Project lifecycle trigger.

##### Case A — recoverable forward omission

If a durable child exists but the immediate parent is still in its corresponding `READY_FOR_*` state, the intended parent transition is mechanically provable.

Kilo must:

1. repair the immediate parent forward to `ACTIVE`;
2. persist the required metadata update (including `updated_at`);
3. visibly surface the repair;
4. continue the requested decomposition command only after the repair succeeds.

Example output information:

```text
Lifecycle Integrity Repair:
EPIC-003: READY_FOR_FEATURE_DECOMPOSITION → ACTIVE
Reason: durable child already existed from a prior interrupted execution
```

If that required repair write cannot be established, return `PERSISTENCE_FAILURE`.

The repair is project truth correction, not reconciliation. It does not require a new lifecycle audit-log artifact or a backward transition.

##### Case B — reverse lifecycle contradiction

If the parent is already `ACTIVE` but no durable triggering child exists, Kilo cannot deterministically infer which side is correct.

Normal decomposition stops with:

> `LIFECYCLE_INTEGRITY_FAILURE`

The decomposition command does not diagnose provenance, choose a repair, demote the parent, or invoke reconciliation automatically.

The next owner is `/diagnose`, which establishes why the contradiction exists and then routes the eventual repair according to the evidence:

- mechanically/non-semantically repairable repository problem → integrity repair;
- accepted authority actually needs changing → normal `/shouldreconcile → /reconcile` path;
- developer-owned choice required → `HUMAN_DECISION_REQUIRED`.

Thus `/reconcile` is not the universal escape hatch for lifecycle corruption, and decomposition preflight cannot deadlock the diagnostic workflow that exists to investigate the inconsistency.

##### Case C — invalid authoritative artifact

If a required authoritative artifact is malformed, truncated, structurally invalid or otherwise cannot establish trustworthy authoritative state, normal decomposition stops with:

> `AUTHORITATIVE_ARTIFACT_INVALID`

Existing more-specific repository-integrity diagnostics such as duplicate-ID or identity-mismatch errors remain valid where already defined.

Kilo does not reconstruct missing/truncated semantic content by inference.

#### Failure-token separation

The relevant integrity/operational diagnostics are intentionally distinct:

- `PERSISTENCE_FAILURE` — the current invocation could not establish a required authoritative mutation.
- `LIFECYCLE_INTEGRITY_FAILURE` — individually parseable authoritative artifacts form a mechanically contradictory lifecycle combination that cannot be deterministically repaired.
- `AUTHORITATIVE_ARTIFACT_INVALID` — an authoritative artifact itself cannot be trusted structurally.
- `INVALID_LIFECYCLE_TRANSITION` — already locked by Point 05.7; the requested transition is explicitly illegal under the lifecycle table.

These tokens must not be collapsed because their recovery paths differ.

#### Repair provenance

A successful deterministic lifecycle repair is surfaced in the command output and changes the authoritative artifact plus `updated_at`.

No new generic lifecycle-history or repair-log schema is introduced; Point 05 already establishes that current artifact state is authority and Git is history/provenance.

A Git commit is **not** the authoritative persistence boundary. Current authoritative repository truth includes valid uncommitted working-tree state. Therefore Kilo must not assume that every authoritative repair has already been committed when the command returns.

#### Deliberate v0.2 limitation

The local-preflight design intentionally does not guarantee discovery of stale lifecycle invariants elsewhere in the hierarchy.

For example, a stale Epic child-triggered invariant may remain undetected indefinitely if no later `/feature` invocation operates under that Epic.

v0.2 has no background or repository-wide lifecycle-integrity monitor by virtue of this rule.

Whether v0.2 additionally needs an explicit project lifecycle-integrity scan remains a separate design question and must not be silently inferred from command-local preflight.

### Locked design — 07.4 Epic result contracts

The `/epic` result family is locked as:

- `EPIC_CONTINUE`
- `EPIC_WAITING`
- `EPIC_BLOCKED`
- `EPIC_READY`
- shared global `HUMAN_DECISION_REQUIRED`
- applicable shared integrity/operational diagnostics from the decomposition foundation.

#### `EPIC_CONTINUE`

`EPIC_CONTINUE` means `/epic` made valid progress on the Epic, persisted every authoritative mutation required by the invocation, and more Epic-local grooming remains that can proceed independently of currently blocking dependencies or human decisions.

It is a healthy pause/result, not a failure and not a readiness result.

The Epic remains in its valid mutable lifecycle state, normally `DRAFT` or `GROOMING`.

Before returning `EPIC_CONTINUE`, the resumable continuation package must preserve or reference at least:

- settled Epic decisions;
- unresolved Epic-local grooming frontier;
- declared dependency status relevant to current grooming;
- next meaningful grooming actions;
- current Epic artifact fingerprint/version;
- known waiting, blocking or human-decision conditions already surfaced during the invocation but not currently the primary stop reason.

These non-primary conditions must not exist only in chat/session output.

Where an authoritative source already owns the semantic fact, continuation state references that source rather than duplicating authority:

- dependency truth remains in authoritative `depends_on[]` / related metadata;
- human-decision truth remains in the applicable Point-04 escalation record;
- blocker truth remains in the durable blocker record defined below.

The continuation package records that those conditions are relevant to the active grooming frontier; it does not become a competing source of truth.

A condition may coexist with `EPIC_CONTINUE` only when genuinely useful Epic-local work remains that does not depend on resolving that condition first.

#### `EPIC_WAITING`

`EPIC_WAITING` means Epic-local productive grooming is exhausted for now, but the Epic cannot pass its readiness gate because a known declared dependency/prerequisite is still progressing through a normal resolution path elsewhere.

It is sequencing, not failure.

`EPIC_WAITING` may be emitted only when all of the following hold:

- the dependency/prerequisite is known and authoritatively declared;
- the dependency has an identified owner/workflow path;
- `/epic` freshly resolves enough of that dependency's current authoritative state and applicable blocking/escalation information to establish that the normal path remains viable;
- no currently recorded condition says that dependency/workflow is itself unable to proceed normally;
- no independently actionable Epic-local grooming remains.

The classification therefore cannot be made from the current Epic file alone.

If the dependency cannot be inspected reliably, that absence of evidence is not sufficient to classify `WAITING`; the applicable unavailable, integrity or blocking result applies instead.

`EPIC_WAITING` does not introduce or mutate an Epic lifecycle state. The Epic remains in its current valid mutable state, normally `GROOMING`.

#### `EPIC_BLOCKED`

`EPIC_BLOCKED` means `/epic` cannot safely continue or reach readiness because a required prerequisite, evidence source, access path, authority input or dependency has no currently viable normal resolution path.

It is distinct from both normal sequencing and developer-owned choice:

- known normal sequencing path still exists → `EPIC_WAITING`;
- authorized human choice must create/settle the missing decision → shared `HUMAN_DECISION_REQUIRED`;
- abnormal prerequisite/evidence/access/authority condition prevents safe progress → `EPIC_BLOCKED`.

Every `EPIC_BLOCKED` result must persist or update a durable blocker record. The reason for stopping must never live only in command output/chat.

The durable blocker record must capture at least:

- affected Epic;
- blocking condition/reason;
- missing prerequisite, evidence, access or authority;
- time/discovery provenance;
- responsible workflow/source/owner if known;
- unblock/resolution-check condition;
- current blocker status.

This blocker record is distinct from a Point-04 escalation record:

- blocker record = unavailable prerequisite/evidence/access/authority condition;
- escalation record = unresolved decision/authority choice such as `HUMAN_DECISION_REQUIRED`.

Future `/epic` invocations revalidate the durable blocker condition rather than reconstructing it from conversation history.

The command output follows the common blocked semantic envelope:

- Blocking Issue
- Owner / responsible workflow where known
- Why It Blocks
- Required Action / unblock condition
- routing back to `/epic`
- final token `EPIC_BLOCKED`

#### `EPIC_READY`

`EPIC_READY` means `/epic` has persisted the Epic, the Point-08 Epic readiness gate passes, and the Epic lifecycle state is now:

> `READY_FOR_FEATURE_DECOMPOSITION`

It means only that the Epic is sufficiently settled to decompose safely into Features without inventing material Epic-level intent.

It does **not** mean:

- any Feature already exists;
- the Epic is `ACTIVE`;
- the Epic is `COMPLETE`;
- Epic-level E2E verification has already run;
- every implementation detail is known;
- future reconciliation can never affect the Epic.

The first durable Feature creation remains the Point-05 trigger that transitions the Epic from `READY_FOR_FEATURE_DECOMPOSITION` to `ACTIVE`.

The `EPIC_READY` handoff must surface enough of the Epic contract for `/feature` to decompose without silently reinterpreting prior grooming. At minimum it includes:

- Artifact ID;
- lifecycle State;
- Human-Evaluable Outcome;
- Major Boundaries;
- Non-Goals / Explicitly Excluded Scope;
- Declared Dependencies;
- Locked Assumptions / Constraints relevant to decomposition;
- Verification Intent, noting that Epic-level E2E proof is expected while exact evidence/mechanics remain owned by Point 09;
- Next Owner: `/feature`;
- final token `EPIC_READY`.

The ready output is a compact handoff contract, not a duplicate copy of the Epic artifact. Authoritative details continue to live in the Epic and referenced authority.

### Locked design — 07.4 Feature result contracts

The `/feature` result family is locked as:

- `FEATURE_CONTINUE`
- `FEATURE_WAITING`
- `FEATURE_BLOCKED`
- `FEATURE_READY`
- shared global `HUMAN_DECISION_REQUIRED`
- applicable shared integrity/operational diagnostics from the decomposition foundation.

#### `FEATURE_CONTINUE`

`FEATURE_CONTINUE` means `/feature` made valid progress on the Feature, persisted every authoritative mutation required by the invocation, and more Feature-local grooming remains that can proceed independently of currently blocking dependencies or human decisions.

It is a healthy pause/result, not a failure and not a readiness result.

The Feature remains in its valid mutable lifecycle state, normally `DRAFT` or `GROOMING`.

Before returning `FEATURE_CONTINUE`, the resumable continuation package must preserve or reference at least:

- settled Feature decisions;
- unresolved Feature-local grooming frontier;
- declared dependency status relevant to current grooming;
- next meaningful grooming actions;
- current Feature artifact source identity/fingerprint;
- current parent Epic authoritative source identity/fingerprint resolved using the existing Point-03 freshness mechanism;
- known waiting, blocking or human-decision conditions already surfaced during the invocation but not currently the primary stop reason.

Where authoritative sources already own those facts, continuation state references them rather than duplicating semantic authority.

A condition may coexist with `FEATURE_CONTINUE` only when genuinely useful Feature-local work remains that does not depend on resolving that condition first.

#### Parent-Epic freshness and authority drift

The parent Epic fingerprint/reference is mandatory resume context for `/feature`.

A fingerprint mismatch is only a freshness signal. It is not itself evidence of waiting, blocking, reconciliation or Feature impact.

On mismatch, `/feature` reloads the current Epic from authoritative state and obeys existing Point-03/Point-05/Point-01 authority rules.

Locked behaviour:

- non-semantic parent changes may refresh the Feature checkpoint/context without reopening Feature decisions;
- `/feature` does not silently reinterpret, reopen or rewrite previously settled Feature decisions merely because the parent fingerprint changed;
- `/feature` does not automatically invoke `/shouldreconcile`;
- if current authoritative/reconciliation state already proves that an upstream change has been handled and no outstanding obligation affects this Feature, `/feature` rebuilds fresh context and continues;
- if an accepted parent-authority change remains unreconciled or its reconciliation status cannot be established safely, `/feature` stops with the appropriate blocked/escalation routing and tells the developer that the human-controlled `/shouldreconcile` path is required;
- parent-Epic drift is never classified as ordinary `FEATURE_WAITING`.

When parent-authority revalidation is materially relevant to the current Feature invocation, the command output must visibly surface that revalidation rather than silently mutating context.

No new `FEATURE_PARENT_AUTHORITY_CHANGED` result token is introduced.

#### No Feature-local decision dependency graph

v0.2 tracks dependencies between authoritative artifacts, not between individual settled decisions inside one Feature artifact.

`/feature` does not create or maintain an internal graph such as "decision B depends on decision A".

If an upstream accepted-authority change may affect a Feature, Point-01 reconciliation evaluates the Feature artifact as a candidate:

- can the Feature remain exactly as written and still be truthful under the authority delta? → unaffected;
- no → Feature requires reconciliation/revision;
- uncertain → `HUMAN_DECISION_REQUIRED`.

This deliberately accepts coarser Feature-level impact analysis rather than introducing a second fragile semantic dependency graph inside artifacts.

#### `FEATURE_WAITING`

`FEATURE_WAITING` means Feature-local productive grooming is exhausted for now, but the Feature cannot pass its readiness gate because a known declared non-hierarchical dependency/prerequisite is still progressing through a normal resolution path elsewhere.

It is sequencing, not failure.

`FEATURE_WAITING` may be emitted only when all of the following hold:

- the prerequisite/dependency is known and authoritatively declared;
- it is not merely the parent Epic hierarchy relationship;
- the dependency has an identified owner/workflow path;
- `/feature` freshly resolves enough of that dependency's current authoritative state and applicable blocking/escalation information to establish that its normal path remains viable;
- no currently recorded condition says that dependency/workflow is itself unable to proceed normally;
- no independently actionable Feature-local grooming remains.

A Feature does not normally `WAIT` on its parent Epic. Parent-authority change/drift follows the freshness/reconciliation rules above.

`FEATURE_WAITING` does not introduce or mutate a Feature lifecycle state. The Feature remains in its current valid mutable state, normally `GROOMING`.

#### `FEATURE_BLOCKED`

`FEATURE_BLOCKED` means `/feature` cannot safely continue or reach readiness because a required prerequisite, evidence source, access path, authority input or dependency has no currently viable normal resolution path.

Classification remains two-way for upstream gaps:

- required information/authority exists or should exist but cannot currently be safely obtained/resolved → `FEATURE_BLOCKED`;
- the missing answer must be created by an authorized developer choice → shared `HUMAN_DECISION_REQUIRED`.

There is no third Feature result meaning "the Epic itself needs revisiting". The output may name the affected upstream artifact/authority for routing, but `/feature` keeps its own result vocabulary and does not silently edit upstream authority.

Every `FEATURE_BLOCKED` result must persist or update a durable blocker record under the same common blocker-record semantics already locked for Epic:

- affected Feature;
- blocking condition/reason;
- missing prerequisite, evidence, access or authority;
- discovery/provenance time;
- responsible workflow/source/owner if known;
- unblock/resolution-check condition;
- current blocker status.

Future `/feature` invocations revalidate this durable blocker instead of reconstructing the reason from conversation history.

The output follows the common blocked semantic envelope and routes back to `/feature` after the external/upstream condition is resolved.

#### `FEATURE_READY`

`FEATURE_READY` means `/feature` has persisted the Feature, the Point-08 Feature readiness gate passes, and the Feature lifecycle state is now:

> `READY_FOR_SPEC`

It means only that the Feature is sufficiently settled to decompose safely into implementation-ready Specs without inventing material Feature-level intent.

It does **not** mean:

- any Spec already exists;
- the Feature is `ACTIVE`;
- the Feature is `COMPLETE`;
- Feature-level integration verification has already run;
- every implementation detail is known;
- future reconciliation can never affect it.

The first durable Spec creation remains the Point-05 trigger that transitions the Feature from `READY_FOR_SPEC` to `ACTIVE`.

The ready handoff intentionally uses hierarchy-specific terminology:

- Epic headline concept → **Human-Evaluable Outcome**
- Feature headline concept → **Human-Evaluable Capability**
- Spec headline concept → **Behavioral Slice**

This reflects the locked decomposition model:

```text
Outcome
  ↓ decomposed into
Capabilities
  ↓ decomposed into
Behavioral Slices
```

The `FEATURE_READY` handoff must include at least:

- Artifact ID;
- lifecycle State;
- Human-Evaluable Capability;
- Observable Surface;
- Capability Scope Boundaries;
- Integration / Contract Boundaries;
- Non-Goals / Explicitly Excluded Scope;
- Declared Dependencies;
- Locked Assumptions / Constraints relevant to decomposition;
- Acceptance Intent;
- Verification Intent, noting that Feature-level integration proof is expected while exact evidence/mechanics remain owned by Point 09;
- Next Owner: `/spec`;
- final token `FEATURE_READY`.

The ready output is a compact handoff contract, not a duplicate copy of the Feature artifact.

#### Parent Epic activation is independent of Feature result

The first durable Feature creation may transition its parent Epic:

`READY_FOR_FEATURE_DECOMPOSITION → ACTIVE`

independently of whether the current Feature invocation ultimately returns `FEATURE_CONTINUE`, `FEATURE_WAITING`, `FEATURE_BLOCKED`, `FEATURE_READY`, or `HUMAN_DECISION_REQUIRED`.

Whenever `/feature` performs that parent transition, the output must surface it using the common envelope:

```text
Parent Lifecycle Transition:
Artifact: EPIC-003
From: READY_FOR_FEATURE_DECOMPOSITION
To: ACTIVE
Trigger: first durable Feature created
```

If the transition was recovered from an incomplete prior child-triggered operation, include the recovery reason as defined by the decomposition-integrity foundation.

### Expected outcome

Every major workflow action should have one obvious owner.

The developer should not need to wonder:

> Which command or agent am I supposed to use now?

## [ ] 14 — Claude Integration Strategy & Clean Frontier Handoff

### Why this matters

Claude should be part of the v0.2 workflow alongside GPT because its frontier reasoning and coding capability can add meaningful value to:

- architecture
- difficult debugging
- adversarial review
- high-risk design decisions
- complex implementation review

The economics changed materially with **Claude Opus 5.5**. Anthropic launched Opus 5.5 on September 22, 2026 at lower prices than Opus 5 and also increased subscription usage limits.

The v0.2 goal is therefore **not to decide whether Claude is desirable**. It is.

The goal is to determine the cleanest and most cost-controlled way to make Claude a practical part of this personal workflow.

### Current intended role split

- **GPT** — frontier reasoning, architecture, review, fallback and second opinion.
- **Claude** — frontier reasoning, architecture, difficult debugging, adversarial/independent review and selected complex coding tasks.
- **DeepSeek** — high-volume implementation, tests, routine changes, mechanical work and cost-sensitive iteration.

This is an opinionated personal strategy, not a generic model-routing framework.

### Determine

- [ ] Which workflow stages should deliberately invoke Claude.
- [ ] Which tasks genuinely justify Opus-class capability.
- [ ] When GPT alone is sufficient.
- [ ] When GPT + Claude independent review is worth the extra usage.
- [ ] Whether Claude Code + Claude Pro can provide a clean subscription-backed path.
- [ ] Whether direct Claude API usage is now economically reasonable for selected tasks.
- [ ] Whether a hybrid strategy is preferable.
- [ ] How Kilo prepares a bounded Claude handoff.
- [ ] Minimum required context.
- [ ] Structured handoff format.
- [ ] Structured response format.
- [ ] How Claude results return to the originating Kilo workflow.
- [ ] Non-interactive/headless invocation behaviour.
- [ ] Claude quota/rate-limit handling.
- [ ] API spend limits and cost guardrails.
- [ ] Failure behaviour.
- [ ] GPT fallback behaviour when Claude is temporarily unavailable.
- [ ] Whether manual approval is required anywhere.

### Required POC

Prove a complete controlled handoff:

Kilo → bounded task/context → Claude execution → structured result → Kilo workflow resumes

The POC should establish:

- reliable non-interactive invocation where used
- supported authentication behaviour
- Claude Pro/Claude Code viability
- direct API viability at current Opus 5.5 pricing
- structured output reliability
- context-size behaviour
- error detection
- quota/rate-limit detection
- cost visibility
- clean return of results

### Decision gate

The design decision is **which Claude access path to adopt**, not whether Claude has value.

Preferred order:

1. Use a clean, officially supported Claude Code/Pro path if it integrates reliably with our workflow.
2. If that is unsuitable, evaluate selective direct API use under an explicit budget.
3. If both paths have practical limitations, preserve a clean manual/assisted Claude review path rather than building fragile infrastructure.

Claude should be available to the v0.2 workflow, but **v0.2 must not become structurally dependent on Anthropic availability for basic operation**. If Claude is temporarily unavailable, GPT should allow the workflow to continue.

### Explicit non-goals

Do not turn this into:

- a generic ModelProvider framework
- universal model routing
- a model plugin marketplace
- provider-agnostic orchestration infrastructure
- automatic model benchmarking
- arbitrary agent-to-agent communication

### Expected outcome

A **clean, maintainable and budget-controlled way to use Claude together with GPT and DeepSeek** in the places where Claude materially improves the quality of our personal development workflow.
