# SubhForge v0.2.0 — Implementation Tooling

> Document authority and stable-section policy: see `design/README.md`.

> **Temporary implementation infrastructure:** this document owns the one-time
> machinery used to build SubhForge v0.2.0 from the frozen v0.2 architecture
> without turning chat history into the implementation state store.
>
> It is **not** product architecture, **not** a second work-management system,
> and **not** a permanent runtime dependency.
>
> The frozen implementation semantics remain owned by
> `V0.2-ARCHITECTURE.md`, `V0.2-WORKFLOW-CONTRACTS.md` and
> `V0.2-QUALIFICATION.md`. This tooling only coordinates implementation of
> those accepted contracts.

## 1. Purpose

The implementation phase should feel materially different from the architecture
phase.

The anti-pattern is:

```text
implementation item
→ long chat
→ architecture/context repeatedly reconstructed by hand
→ several routine decisions pushed to Subhadeep
→ code starts late
→ acceptance criteria are debated after implementation
→ chat becomes the project database
```

The intended model is:

```text
frozen architecture
→ durable IMP-ID
→ deterministic preflight
→ bounded implementation through stable v0.1.1
→ tests / verify / review
→ PR
→ deterministic closure evidence
→ next IMP-ID
```

The implementation tooling exists primarily to enforce:

- **less chat and less repeated explanation**;
- **PR-first implementation discipline**;
- **fixed acceptance gates before coding**;
- **durable resumability by implementation ID**;
- **automatic reconstruction of relevant authority/context**;
- **human interruption only for consequential decisions**;
- **no silent architecture drift during implementation**.

Chat is a control surface for starting work, asking questions and making genuine
decisions. It is **not** the implementation state store.

---

## 2. Scope and Non-Goals

### In scope

The temporary tooling may:

- derive and maintain a bounded v0.2 implementation manifest;
- validate that an implementation item is eligible to start;
- assemble the minimum authority/context packet for that item;
- invoke/reuse stable v0.1.1 delivery capabilities;
- enforce branch/PR/test/evidence discipline;
- detect architecture drift or unresolved human decisions;
- provide concise implementation status and next-work guidance;
- persist implementation progress/evidence outside chat.

### Explicit non-goals

The tooling must **not**:

- create a second permanent Project/Epic/Feature/Spec lifecycle;
- replace the v0.2 operational work graph being implemented;
- redesign the frozen architecture during ordinary coding;
- duplicate `/spec → /implement → /verify → /review` with a second delivery
  engine;
- add a new general-purpose autonomous agent framework;
- turn every technical implementation choice into a human decision;
- require Subhadeep to manually maintain bookkeeping that can be derived;
- become a prerequisite for using stable v0.2 after release.

> **This is scaffolding for building v0.2, not “SubhForge for building
> SubhForge.”**

---

## 3. Activation Preconditions

Implementation tooling becomes active **after** the one-time Architecture
Fitness Review is closed and `/arch-synthesize` declares the v0.2 architecture
ready for implementation freeze.

Before the first implementation item starts:

1. all blocking AR cases are closed or explicitly dispositioned;
2. accepted AR results are promoted to their single normative homes;
3. the internal architecture consistency gate is green;
4. RC/release implications are reflected in `V0.2-QUALIFICATION.md`;
5. the implementation manifest is generated from the frozen authority;
6. the implementation-control helper/commands pass their own deterministic
   tests.

No implementation item may be used as an excuse to bypass an unresolved
blocking Architecture Review case.

---

## 4. Durable Implementation Manifest

The implementation plan is persisted in:

`design/V0.2-IMPLEMENTATION-MANIFEST.md`

The manifest is **temporary operational implementation state** for building
SubhForge itself. It is not product architecture and does not redefine any
v0.2 lifecycle rule.

Each implementation item uses a durable `IMP-###` identity.

Minimum record:

```text
IMP-ID
Title
Status
Purpose
Normative authority references
Qualification / proof references
Dependencies
Scope
Explicit non-scope
Acceptance gate
Required deterministic tests
Required integration/model-bearing evidence
Human decision expected: YES | NO
Open decision / escalation references
Branch
PR
Evidence / result
Next action
```

Recommended implementation status vocabulary:

```text
TODO
READY
IN_PROGRESS
BLOCKED
PR_OPEN
VERIFIED
MERGED
DEFERRED
```

These are **temporary self-development statuses only**. They do not become the
v0.2 Product/Epic/Feature/Spec lifecycle.

Rules:

- implementation order follows accepted architecture dependencies, not arbitrary
  document order;
- one item should normally be small enough for one bounded implementation cycle;
- dependencies must reference durable `IMP-###` IDs;
- an item cannot be `READY` without an explicit acceptance gate;
- `MERGED` requires the PR and required evidence to exist;
- no implementation state depends solely on remembered chat history.

---

## 5. Capability Model

The implementation tooling deliberately has few capabilities.

| Capability | Responsibility | Authority boundary | Default execution |
|---|---|---|---|
| **Implementation Planner** | Derive/refine the `IMP-###` manifest from frozen architecture and qualification dependencies | Planning only; cannot change frozen architecture | Sol High for initial manifest; bounded updates thereafter |
| **Implementation Controller** | Eligibility, branch/PR discipline, state persistence, resume and closure checks | Deterministic coordination only | Python/deterministic first |
| **Context Assembler** | Build the minimum current authority/code/test packet for one IMP item | Read-only; cannot reinterpret missing authority | Deterministic retrieval first; bounded model explanation only when useful |
| **Existing v0.1.1 delivery flow** | Perform planning/specification, implementation, verification and review | Existing stable authority boundaries | Reuse `/spec → /implement → /verify → /review`; do not clone them |
| **Implementation Status** | Explain current item, blockers, PR/evidence and next eligible implementation work | Read-only | Deterministic projection first |

There is **no new general Implementation Agent** whose job duplicates Builder,
Verifier or Reviewer.

## 6. Entry Points

### `/impl-plan`

Used once after architecture freeze and later only when implementation evidence
requires a legitimate manifest adjustment.

Purpose:

- read frozen Architecture/Workflow/Qualification authority;
- derive the implementation dependency sequence;
- create/update `IMP-###` records;
- define acceptance gates before implementation starts;
- mark initially eligible work `READY`;
- identify where model-bearing/integration proof is actually required.

It must not create arbitrary work that lacks a normative or qualification reason.

### `/impl-start IMP-###`

Purpose:

1. run deterministic preflight;
2. reconstruct the item's bounded context;
3. create/use the correct implementation branch;
4. invoke the existing v0.1.1 delivery flow for the bounded item;
5. persist state/evidence as work proceeds.

A normal start should produce a concise execution brief, for example:

```text
IMP-007 — Status / work-plan projection
Authority: Architecture §4.3; Workflow §§11, 17.2
Dependencies: IMP-004, IMP-005 merged
Acceptance gate: defined
Human decision expected: NO
Proceeding.
```

The brief is intentionally small. Full authority is loaded by the tooling, not
repeated to Subhadeep.

### `/impl-check IMP-###`

Purpose:

- run deterministic item-completion checks;
- confirm required tests/evidence are current;
- confirm the PR references the `IMP-###` and governing authority;
- confirm no unresolved human decision or architecture contradiction remains;
- confirm no unauthorized architecture mutation occurred;
- determine whether the item is ready to merge/close.

This capability does not replace code review. It proves that the agreed
implementation contract has been satisfied mechanically where possible.

### `/impl-status [IMP-###]`

Read-only projection answering:

- current implementation item;
- completed / active / remaining items;
- next eligible item(s);
- dependency blockers;
- open PR/evidence state;
- unresolved decision/escalation;
- why an item is not eligible.

It must not require Subhadeep to reconstruct progress from old chats.

---

## 7. Deterministic Start Preflight

Before `/impl-start IMP-###` admits mutating work, prove at least:

1. the `IMP-###` exists;
2. status permits implementation;
3. every required predecessor is `MERGED` or explicitly satisfied;
4. every referenced normative section/file currently exists;
5. the acceptance gate is non-empty;
6. required proof/test expectations are declared;
7. no blocking Architecture Review case remains for the item's authority;
8. no unresolved `HUMAN_DECISION_REQUIRED` blocks the item;
9. the implementation base branch is current;
10. the work occurs on a dedicated item branch, not by direct mutation of the
    protected/base implementation branch;
11. the working tree/workspace identity is the intended SubhForge repository;
12. context assembly stays within the declared bounded-context rules.

Failure returns a specific reason and does not start implementation.

---

## 8. PR-First Discipline

Normal rule:

> **One bounded implementation item → one implementation branch → one PR.**

Exceptions are allowed only when a documented dependency/atomicity reason makes
multiple `IMP-###` items inseparable; the PR must name the reason.

PR requirements:

- title/body references the `IMP-###`;
- governing Architecture/Workflow/Qualification sections are cited;
- acceptance gate is summarized;
- tests/evidence are recorded;
- architecture changes are absent unless an explicit architecture-reopen path
  authorized them;
- implementation manifest state is updated through the tooling.

Direct implementation commits to the v0.2 base branch are not normal workflow.

---

## 9. Human-Decision and Conversation Budget

The implementation tooling applies Architecture §3.9:

> **Trustworthy autonomy, not maximum governance.**

For ordinary implementation:

- safely reversible local implementation choices are made by the responsible
  implementation/review agent;
- settled decisions are never re-asked merely because a session changed;
- related human decisions are batched where safe;
- a human question includes a recommendation and concrete trade-off rather than
  presenting a blank design problem;
- non-blocking decisions are persisted and work continues where safe;
- routine handoffs are performed by the tooling from durable state.

Target operating experience:

> Most `IMP-###` items should require **zero or one consequential interaction**
> from Subhadeep before PR review/merge.

This is an operating target, not permission to suppress genuine
`HUMAN_DECISION_REQUIRED` cases.

### Conversation-pressure signal

If an ordinary implementation item repeatedly requires extended back-and-forth,
the tooling/workflow should classify the cause rather than normalizing the
conversation.

Use one of:

```text
BAD_DECOMPOSITION
MISSING_AUTHORITY
ARCHITECTURE_CONTRADICTION
CONTEXT_RECONSTRUCTION_FAILURE
GENUINE_HUMAN_DECISION
IMPLEMENTATION_FAILURE
```

The first five are workflow/architecture evidence. They are not reasons to keep
asking ad-hoc questions indefinitely.

## 10. Architecture Freeze / Reopen Rule

Implementation proceeds on the presumption that the architecture is closed.

Ordinary implementation may **not** rewrite accepted architecture because a
different design appears nicer during coding.

Architecture is reopened only under the existing governing rule: contradiction,
implementation limitation, new evidence, dogfood failure, meaningful
cost/operational problem, or deliberate human architecture revision.

When such evidence appears:

1. stop only the affected implementation scope;
2. persist the evidence and impacted `IMP-###` item;
3. classify the issue as an architecture escalation;
4. Subhadeep decides whether architecture review/revision is warranted;
5. promote any accepted change to the normative home;
6. update the implementation manifest only after authority changes;
7. resume from durable `IMP-###` state.

The implementation tool never silently edits frozen architecture to unblock
itself.

---

## 11. Context Contract

For one `IMP-###`, load only:

- the implementation item;
- referenced Architecture/Workflow/Qualification sections;
- required predecessor interfaces/evidence;
- directly relevant current source code/tests;
- current branch/PR state;
- open blocker/escalation references;
- only the repository history required to understand the affected code.

Do not reload:

- the entire architecture by default;
- all previous implementation-item discussions;
- broad project history merely for reassurance;
- hidden chain-of-thought from earlier sessions.

Resume re-reads current durable authority and implementation state.

---

## 12. Completion / Closure Gate

An implementation item may become `MERGED` only when:

1. acceptance gate is satisfied;
2. required deterministic tests pass;
3. required integration/model-bearing evidence exists;
4. reviewer outcome permits merge;
5. PR is merged;
6. no blocking implementation/architecture/human-decision record remains;
7. the implementation manifest records the resulting commit/PR/evidence;
8. adjacent deterministic consistency checks remain green.

A merged PR without required proof is not sufficient.

Conversely, the tooling must not require unrelated FULL/system qualification for
every small item when targeted proof is enough. Release-level qualification
remains owned by `V0.2-QUALIFICATION.md`.

---

## 13. Implementation Sequence Relationship

The manifest must respect Architecture §29A's implementation dependency order:

```text
Authority planes + selected work-backend foundation
        ↓
Stable FR/NFR identity + traceability
        ↓
Planning / decomposition / truthful DAG
        ↓
Status + resume + work-plan projection
        ↓
Spec implement / verify / review
        ↓
Feature verification + human acceptance
        ↓
Epic verification + human acceptance
        ↓
Reconciliation
        ↓
Intelligent smoke + dogfood qualification
```

The exact `IMP-###` decomposition is created only **after Architecture Fitness
Review**, because accepted AR outcomes may legitimately change implementation
details.

The manifest may refine this sequence into smaller independently testable items,
but it may not violate the governing dependency order without an explicit
architecture decision.

---

## 14. Build Timing and Size Constraint

The temporary implementation tooling itself should be built **after architecture
freeze and before IMP-001**.

Target:

- one focused setup session;
- a small manifest/controller/context/preflight surface;
- deterministic tests;
- minimal Kilo command/agent additions;
- reuse existing v0.1.1 delivery commands.

If implementation tooling starts requiring its own large architecture effort,
multiple new autonomous agents, or substantial product-like lifecycle machinery,
stop and simplify.

> **The tooling must save more coordination time than it costs to build and
> maintain.**

---

## 15. Temporary Lifecycle and Removal

This capability exists only to build and qualify **SubhForge v0.2.0 itself**.

It may be retired after all of the following hold:

1. all required `IMP-###` items are `MERGED` or explicitly dispositioned;
2. stable v0.2.0 release qualification is accepted;
3. no production v0.2 workflow depends on `/impl-*`;
4. the final implementation manifest/evidence is sufficient to reconstruct how
   v0.2 was built;
5. any useful generic deterministic helper has been deliberately promoted into
   normal SubhForge infrastructure rather than retained accidentally through the
   temporary tooling.

At retirement:

- remove temporary `/impl-*` commands/agents/controllers;
- remove surviving runtime dependencies on the temporary manifest;
- keep/archive the implementation manifest if useful as release history;
- rely on Git/PR history for implementation evidence;
- retain only helpers that have an explicit permanent v0.2 owner.

> **Architecture Review tooling helps decide the building. Implementation
> tooling helps construct it. Stable v0.2 should need neither scaffold.**
