# SubhForge v0.2.0 — Implementation Tooling

> Purpose: define the **small amount of temporary tooling and the exact working
> process** used to build SubhForge v0.2.0 after Architecture Review.
>
> This document does **not** define v0.2 architecture. Architecture remains in
> `V0.2-ARCHITECTURE.md`, workflow behavior in
> `V0.2-WORKFLOW-CONTRACTS.md`, and release proof in
> `V0.2-QUALIFICATION.md`.

## 1. Goal

Build v0.2.0 using **stable v0.1.1 as the delivery engine**, while avoiding the
long design-style conversations that were necessary during architecture work.

The intended flow is:

```text
Architecture Review closes
        ↓
v0.2 architecture freezes
        ↓
create v0.2 implementation manifest
        ↓
pick next IMP item
        ↓
small deterministic preflight
        ↓
use v0.1.1 to spec / implement / verify / review
        ↓
PR + merge
        ↓
record result
        ↓
next IMP item
```

Chat is used to start work or resolve genuine decisions. It is not the
implementation tracker.

---

## 2. Existing v0.1.1 Mechanisms We Reuse

We do **not** replace these.

| Existing v0.1.1 mechanism | How it is used while building v0.2 |
|---|---|
| `/spec` | Prepare the bounded implementation unit and implementation-ready behavior |
| `/implement` | Implement the bounded change |
| `/verify` | Run factual verification and required tests |
| `/review` | Review the implementation and decide whether changes are required |
| `/diagnose` | Investigate an unknown failure when verification cannot identify the cause |
| `/fix` | Apply bounded fixes after known/reproduced failures |
| Git branch + PR workflow | One reviewable change at a time; no normal direct implementation on the v0.2 base branch |
| Existing deterministic tests / smoke mechanics | Reused where applicable instead of inventing another qualification engine |

The exact v0.1.1 behavior remains owned by the v0.1.1 implementation. This
document only says **how we use it to build v0.2**.

## 3. New Temporary Capability We Need

Only three new things are required.

### 3.1 v0.2 Implementation Manifest

File:

`design/V0.2-IMPLEMENTATION-MANIFEST.md`

Created **after Architecture Review freezes the design**.

Each item receives an `IMP-###` ID and records:

```text
IMP-ID
Title
Status
Architecture / Workflow / Qualification references
Dependencies
Scope
Acceptance criteria
Required tests/evidence
Human decision expected: YES | NO
Branch / PR
Result
```

Statuses:

```text
TODO → READY → IN_PROGRESS → PR_OPEN → MERGED
              ↘ BLOCKED
```

The manifest answers:

- what remains;
- what is next;
- why it is next;
- what proves it complete.

It is temporary build-state for SubhForge v0.2. It is not a new permanent v0.2
work-management model.

### 3.2 Small Deterministic Implementation Helper

A small Python helper, for example:

`tools/v02_implementation.py`

It needs only four operations:

```text
plan
preflight IMP-###
status
check IMP-###
```

Meaning:

| Operation | Responsibility |
|---|---|
| `plan` | Validate/generate the implementation manifest after architecture freeze |
| `preflight IMP-###` | Prove the item is allowed to start |
| `status` | Show current/next/blocked implementation items |
| `check IMP-###` | Prove required PR/tests/evidence exist before the item closes |

This helper is deterministic wherever possible. It does **not** implement code,
review code, or make architecture decisions.

### 3.3 PR Contract

Each implementation PR must identify:

- `IMP-###`;
- architecture/workflow authority implemented;
- acceptance criteria;
- tests/evidence;
- whether architecture changed.

Normally:

> **one IMP item → one branch → one PR**

## 4. Exact Development Process

For each implementation item:

### Step 1 — Select work

Run implementation `status` and choose the next eligible `IMP-###`.

No manual reconstruction from old chat.

### Step 2 — Preflight

Run:

`preflight IMP-###`

It checks:

- dependencies are merged;
- authority references exist;
- acceptance criteria exist;
- no blocking human/architecture decision is open;
- repository/base branch is correct;
- implementation is on a dedicated branch.

If preflight fails, do not start coding.

### Step 3 — Prepare the bounded work using v0.1.1

Use existing v0.1.1 `/spec`.

The Spec must stay inside the selected `IMP-###` scope and its frozen authority.

### Step 4 — Implement using v0.1.1

Use existing `/implement`.

Local/reversible implementation choices are made by the implementation agent.
They are **not** routinely pushed to Subhadeep.

### Step 5 — Verify using v0.1.1

Use existing `/verify`.

If verification finds:

- known defect → `/fix`;
- unknown cause → `/diagnose` then `/fix`;
- architecture contradiction / genuine human decision → stop only the affected
  item and escalate.

### Step 6 — Review using v0.1.1

Use existing `/review`.

Review decides whether the implementation satisfies the bounded Spec and
governing authority.

### Step 7 — PR

Open/update the implementation PR.

The PR contains the `IMP-###`, authority references, acceptance result and
test/evidence summary.

### Step 8 — Closure check

Run:

`check IMP-###`

It confirms:

- acceptance criteria satisfied;
- required tests/evidence exist;
- review is acceptable;
- PR is merged;
- no unresolved blocker remains;
- architecture was not silently changed.

Then mark the item `MERGED` and move to the next one.

---

## 5. When Subhadeep Is Asked a Question

Default expectation:

> Most implementation items should need **zero or one consequential interaction**
> from Subhadeep before PR review/merge.

Ask Subhadeep only when the existing architecture/workflow requires a genuine
human decision, for example:

- product intent changes;
- architecture must change;
- risk/waiver acceptance is required;
- implementation exposes a material trade-off not settled by authority.

Do **not** ask for:

- routine implementation choices;
- information already present in authority;
- repeated confirmation after session/context changes;
- manual status or handoff coordination.

Where safe, related decisions should be batched into one question.

---

## 6. Architecture Change During Implementation

Architecture is presumed frozen.

If implementation reveals a real contradiction or implementation limitation:

1. stop the affected `IMP-###`;
2. record the evidence;
3. do **not** silently modify architecture;
4. Subhadeep decides whether architecture must reopen;
5. update normative authority if approved;
6. update affected implementation items;
7. resume.

A merely “nicer design” is not enough to reopen architecture.

---

## 7. What We Are Explicitly NOT Building

We are **not** adding:

- permanent `/impl-*` Kilo commands;
- another Planner/Builder/Verifier/Reviewer stack;
- another Epic/Feature/Spec lifecycle;
- another operational work graph;
- another autonomous development framework.

Stable v0.1.1 already performs the software-delivery work.

The temporary additions are only:

```text
Implementation Manifest
+ small deterministic helper
+ PR discipline
```

---

## 8. Setup Order

After Architecture Review:

```text
1. Freeze architecture
2. Create V0.2-IMPLEMENTATION-MANIFEST.md
3. Build/test tools/v02_implementation.py
4. Start IMP-001
5. For every IMP:
      preflight
      → /spec
      → /implement
      → /verify
      → /review
      → PR
      → check
      → merge
6. Run dogfood/release qualification from V0.2-QUALIFICATION.md
7. Release stable_v0.2.0
8. Remove/retire temporary implementation tooling
```

---

## 9. Success Test

The implementation process is working when Subhadeep can usually say:

```text
Start the next v0.2 item.
```

and SubhForge can determine:

- which item is next;
- what authority applies;
- what needs to be implemented;
- what tests prove it;
- which branch/PR owns it;

without requiring a long planning conversation.

> **v0.1.1 does the engineering work. The temporary implementation tooling only
> keeps that work ordered, bounded and easy to resume.**
