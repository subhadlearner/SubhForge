# SubhForge v0.2.0 — Architecture Review Workbench

## Purpose

This document defines the lightweight Kilo-based workbench to set up **after `stable_v0.1.1` is delivered and accepted, and before executing the Architecture Fitness Review**.

Its purpose is to make the review efficient, durable, and evidence-driven without creating a second SubhForge.

The repository is the memory. Kilo is the execution workbench. Models are bounded specialists. Subhadeep remains the architectural decision-maker.

## Governing Rule

> **Do not build a mini-SubhForge to review SubhForge.**

The workbench must stay intentionally boring:

- repository-local Markdown commands;
- repository-local review artifacts;
- isolated PoC/spike folders;
- Git history;
- explicit model routing;
- human acceptance of architecture decisions.

No new workflow engine, graph, state machine, orchestration service, database, telemetry stack, or production SubhForge code is required merely to run the review.

If setting up the workbench starts consuming more than one normal working session without evidence that additional setup is necessary, stop and simplify.

## Relationship to the Architecture Fitness Review

The authoritative review charter is:

`design/V0.2-ARCHITECTURE-FITNESS-REVIEW.md`

This workbench exists only to execute that charter efficiently.

Sequence:

`stable_v0.1.1 → workbench setup → Architecture Fitness Review → accepted verdict → v0.2 design reconciliation/update`

The current `V0.2-DESIGN-TRACKER.md` remains an input to challenge during the review. It must not be silently rewritten while review conclusions are still evolving.


Create only the files actually needed as the review proceeds. Do not pre-generate ceremony.

## Minimal Command Responsibilities

### `/arch-next`

- read the Architecture Fitness Review;
- read review status and failure ranking;
- select the highest-priority unresolved review case;
- load only the relevant design/repository context;
- prepare the case for research.

### `/arch-research <AR-ID>`

- examine the failure/invariant;
- inspect current SubhForge design and implementation evidence;
- compare relevant established engineering practices;
- propose the smallest robust options;
- identify unresolved uncertainty;
- write findings into the review case.

### `/arch-spike <AR-ID>`

Use only when reasoning cannot establish enough confidence.

- work only in `poc/architecture-review/<AR-ID>/`;
- implement the smallest experiment that answers the architectural question;
- add/run focused tests;
- record commands, observations, and limitations;
- do not modify production SubhForge code unless explicitly approved.

### `/arch-review <AR-ID>`

- independently challenge the research/spike result;
- look for missing failure modes, unsupported assumptions, unnecessary complexity, and weaker alternatives;
- recommend `KEEP`, `MODIFY`, `REMOVE`, `ADD`, or further investigation;
- do not treat the current design as authority merely because it already exists.

### `/arch-record <AR-ID>`

After Subhadeep accepts the decision:

- persist the accepted decision and reasoning;
- update STATUS / DECISION-LOG / COVERAGE-MATRIX as needed;
- record validation required and impact on the existing v0.2 design;
- mark the case ready for the next review item.

## Model Routing

Model assignment is a cost/quality decision, not an architectural dependency.

Suggested default:

| Activity | Model class |
|---|---|
| Mechanical status/Markdown updates | inexpensive capable model |
| Repository exploration / initial research | economical or mid-tier model |
| Small PoC/spike implementation and debugging | DeepSeek or equivalent economical coding model |
| Architecture challenge/review | Sol / Sonnet class |
| High-risk disputed synthesis | strongest justified reasoning model, e.g. Sol High / Opus class |
| Final decision | Subhadeep |

Do not spend premium-model tokens on mechanical updates or routine PoC plumbing when a cheaper model can produce the evidence.

## Agent / Kilo Isolation

Prefer repository-local commands first. Add custom review agents only if command-level model routing and permissions prove insufficient.

If custom agents are introduced:

- keep them project-local;
- use unique names such as `subhforge-arch-research`, `subhforge-arch-spike`, `subhforge-arch-review`;
- do not reuse or override built-in/general Kilo agent names;
- give each role only the tools/permissions it needs;
- do not change existing SubhForge agents merely to support the review.

The workbench must remain isolated from the stable v0.1.1 behaviour.

## Review Case Template

Each `AR-xxx` case should remain small and self-contained:

```text
ID / Title
Failure mode / invariant
Why it matters
Current SubhForge behaviour
Relevant established practice
Options considered
Open uncertainty
Spike required? yes/no
Evidence / observations
Independent reviewer challenge
Recommended decision
Accepted decision: KEEP / MODIFY / REMOVE / ADD
Reasoning
Validation required
Impact on current v0.2 design
Human acceptance
```

## Decision Authority

Models research, experiment, challenge, and recommend.

They do not silently make final architecture decisions.

```text
AI research / spike / review
          ↓
evidence + recommendation
          ↓
Subhadeep accepts / rejects / redirects
          ↓
accepted decision recorded in Git
```

For genuine ambiguity or material trade-offs, human judgement remains authoritative.

## Bounded Context Rule

A review task should normally load only:

- the Architecture Fitness Review;
- STATUS / FAILURE-RANKING;
- the active `AR-xxx` case;
- relevant sections of the current design;
- relevant implementation files/evidence;
- the linked PoC, if one exists.

Do not load broad chat history or the entire repository by default.

The review process should itself dogfood the bounded-context principle being evaluated for v0.2.0.

## Spike Discipline

The Architecture Fitness Review currently expects roughly 4–5 highest-value spikes, selected by risk and uncertainty.

For each spike:

- answer one architectural question;
- prefer one working session maximum;
- isolate the code under `poc/architecture-review/`;
- record evidence, not opinions;
- delete or archive disposable PoC code later unless it has continuing value.

A spike is evidence. It is not automatically production architecture.

## Workbench Success Criteria

The workbench is successful if it reduces review plumbing while keeping decisions durable.

It should make a normal review session look approximately like:

```text
/arch-next
/arch-research AR-xxx
/arch-spike AR-xxx      # only if needed
/arch-review AR-xxx
Subhadeep decides
/arch-record AR-xxx
```

The workbench has failed if maintaining the review tooling itself becomes a meaningful project.

## Cleanup / Promotion After the Review

At the end of the Architecture Fitness Review, explicitly decide what happens to the workbench:

- keep genuinely useful commands as SubhForge tooling;
- promote only proven concepts into the v0.2 design;
- retain review evidence/decision records;
- remove disposable PoCs and review-only machinery that no longer provides value.

Nothing becomes permanent merely because it was useful during the review.
