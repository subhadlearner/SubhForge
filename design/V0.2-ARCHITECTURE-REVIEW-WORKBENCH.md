# SubhForge v0.2.0 — Architecture Review Workbench

## Purpose

This document defines the lightweight Kilo-based workbench to set up **after `stable_v0.1.1` is delivered and accepted, and before executing the Architecture Fitness Review**.

Its purpose is to make the review efficient, durable, bounded, and evidence-driven without creating a second SubhForge.

The repository is the memory. Kilo is the execution workbench. Models are bounded specialists. Subhadeep remains the architectural decision-maker.

## Governing Rule

> **Do not build a mini-SubhForge to review SubhForge.**

The workbench must stay intentionally boring:

- one project-local custom review agent at most;
- a small set of repository-local Markdown commands;
- repository-local review artifacts;
- isolated PoC/spike folders;
- Git history;
- explicit model routing;
- human acceptance of architecture decisions.

No new workflow engine, graph, state machine, orchestration service, database, telemetry stack, or production SubhForge code is required merely to run the review.

### Workbench Freeze Rule

Once `/arch-plan`, `/arch-case`, `/arch-spike`, `/arch-review`, and the one-time `/arch-synthesize` closing step are sufficient to execute the review, **no further workbench capability should be added unless an actual architecture review case is blocked without it**.

The initial workbench setup should fit inside one normal working session. If it starts becoming a project, stop and simplify.

---

## Relationship to the Architecture Fitness Review

The authoritative review charter is:

`design/V0.2-ARCHITECTURE-FITNESS-REVIEW.md`

This workbench exists only to execute that charter efficiently.

The intended sequence is:

```text
stable_v0.1.1
      ↓
Architecture Review Workbench setup
      ↓
/arch-plan
      ↓
approved AR backlog
      ↓
/arch-case → optional /arch-spike → /arch-review → human decision
      ↓
all AR cases closed
      ↓
/arch-synthesize
      ↓
revised v0.2.0 design/tracker reviewed and accepted
      ↓
stable_v0.1.1 SubhForge implements v0.2.0 using the normal Spec-driven flow
```

The current `V0.2-DESIGN-TRACKER.md` remains an **input to challenge** during the review. It must not be silently rewritten while review conclusions are still evolving.

## Fixed Model and Claude Access Policy

The architecture-review workbench should not spend time choosing models during execution. The default routing is fixed here and should be encoded directly into the Kilo command definitions when the workbench is created.

### Claude access rule for this review

**Do not use the Anthropic API budget for Architecture Fitness Review work by default.**

The v0.2 design has already validated the Claude handoff path in §14 ("Claude integration & handoff"):

- Claude Code + Pro subscription, headless, was proven by the TODO-3 POC;
- Kilo prepares a bounded transient handoff packet under `.kilo/handoffs/HO-###.md`;
- Claude writes the structured result to the declared `.result.json` path;
- the originating Kilo command validates the result schema;
- Claude findings return as **evidence, not authority**;
- the manual assisted Claude Code path remains available if headless handoff is unavailable.

The Architecture Review Workbench must **reuse that tested handoff contract rather than inventing another Claude integration**.

For this review:

1. Any Sonnet/Opus work uses the tested **Claude Code + Pro handoff** path.
2. The in-Kilo Anthropic API provider is **not used** unless Subhadeep explicitly overrides this rule for a specific case.
3. If Claude subscription quota or handoff execution is unavailable, the command must surface the condition rather than silently consuming Anthropic API budget.
4. GPT/Sol remains the fallback reasoning path when Claude handoff cannot be used.
5. Claude remains read-only for architecture review unless a future explicit decision changes that rule.

This is a review-specific cost policy. It does not rewrite the broader v0.2 Claude strategy in `V0.2-DESIGN-TRACKER.md`.

### Fixed command/model mapping

| Command | Default model / execution path | Escalation rule |
|---|---|---|
| `/arch-plan` | **GPT-5.6 Sol — High reasoning** | None by default. This is the authoritative initial decomposition pass. |
| `/arch-case <AR-ID>` | **GPT-5.6 Sol — Medium reasoning** | Use **Sol High** automatically when the AR is ranked HIGH/CRITICAL, cross-cutting, or the Medium pass returns material uncertainty not suitable for a spike alone. |
| `/arch-spike <AR-ID>` | **DeepSeek** | Escalate to Sol only if DeepSeek cannot complete the bounded experiment reliably after the defined attempt limit; do not switch to Claude for routine PoC coding. |
| `/arch-review <AR-ID>` | **Claude Sonnet via the tested Claude Code + Pro handoff** | Use **Claude Opus via the same handoff** when the AR is HIGH/CRITICAL, materially cross-cutting, disputed, or the Sonnet result is `INSUFFICIENT_CONTEXT` / materially inconclusive. Never fall through to Anthropic API automatically. |
| `/arch-synthesize` | **GPT-5.6 Sol — High reasoning** | If synthesis exposes a material contradiction, reopen/create an AR. Do not use a stronger model to paper over an unresolved decision. |

### Independence rule

The normal architecture case path intentionally uses different model families:

```text
/arch-case
  GPT-5.6 Sol
       ↓
optional /arch-spike
  DeepSeek
       ↓
/arch-review
  Claude Sonnet/Opus via handoff
       ↓
Subhadeep decision
```

This separation is deliberate:

- Sol performs the primary architecture reasoning;
- DeepSeek produces economical empirical evidence when needed;
- Claude independently challenges the conclusion;
- Subhadeep owns the final architecture decision.

### Risk classification drives escalation

`/arch-plan` must record a risk class on every AR case:

`LOW | MEDIUM | HIGH | CRITICAL`

That classification drives model routing automatically:

- LOW/MEDIUM `/arch-case` → Sol Medium;
- HIGH/CRITICAL `/arch-case` → Sol High;
- LOW/MEDIUM `/arch-review` → Claude Sonnet handoff;
- HIGH/CRITICAL `/arch-review` → Claude Opus handoff.

A later command should not ask Subhadeep which model to use unless the configured model/path is unavailable and the documented fallback cannot proceed safely.


## One Custom Agent

Use a single project-local agent:

`subhforge-arch-review`

Its purpose is not to encode architecture intelligence. Its purpose is to provide a safe permission boundary for the review commands.

Conceptually it should:

**Allow**
- read the repository;
- inspect the existing v0.2 design and current implementation;
- edit `design/architecture-review/**`;
- edit `poc/architecture-review/**`;
- run focused commands/tests required by architecture spikes.

**Deny by default**
- production changes under `forge/**`;
- changes to existing stable SubhForge behaviour;
- silent edits to `V0.2-DESIGN-TRACKER.md`;
- silent edits to `V0.2-ARCHITECTURE-FITNESS-REVIEW.md`;
- destructive repository operations.

The commands supply the role-specific instructions and model choice. Do **not** create a custom agent per command unless real evidence later proves the single boundary insufficient.

# Review Commands

## 1. `/arch-plan` — Build the Review Backlog

### Responsibility

Convert the Architecture Fitness Review from principles/failure modes into concrete architecture review cases.

### Inputs

The planner should inspect:

- `V0.2-ARCHITECTURE-FITNESS-REVIEW.md`;
- current `V0.2-DESIGN-TRACKER.md`;
- current SubhForge code relevant to v0.2 assumptions;
- known v0.1.x limitations/failures/evidence available in the repository;
- relevant established industry architecture/practices;
- credible external engineering skills/framework patterns relevant to the
  failure/capability, including the initial reference set named in the
  Architecture Fitness Review.

### Output

Create/update:

- `FAILURE-RANKING.md`;
- `COVERAGE-MATRIX.md`;
- initial `STATUS.md`;
- `SKILL-CANDIDATES.md` as the lightweight engineering-skill candidate register;
- `MCP-CANDIDATES.md` as the lightweight external-tool/MCP candidate register;
- concrete `AR-xxx` cases under `design/architecture-review/cases/`.

### Planning Rules

The planner must:

1. map failure modes and invariants to actual current architecture decisions;
2. rank risks using the Architecture Fitness Review's Likelihood × Damage approach;
3. group overlapping concerns into meaningful architecture questions;
4. avoid mechanically creating one AR per failure mode;
5. identify which ARs require:
   - analysis/research only;
   - repository inspection;
   - architecture spike/PoC;
   - no further work because evidence is already sufficient;
6. propose approximately **8–12 meaningful AR cases**, not dozens of checklist items;
7. identify roughly **4–5 highest-value spike candidates**, subject to evidence;
8. identify where a review case can likely be accelerated by studying a
   credible existing skill/framework implementation before designing anything;
9. ensure at least one review case explicitly examines **SubhForge's
   engineering-skill architecture and external-skill adoption strategy**,
   including which capabilities belong in commands, agents, reusable skills,
   deterministic tools/MCPs, or project-local rules;
10. seed `SKILL-CANDIDATES.md` with capability gaps and credible sources,
    with particular attention to software design, architecture, domain
    modelling, testing architecture, research/prototyping, and review quality;
11. ensure at least one review case explicitly examines **MCP / external-tool
    integration architecture and security**, including the trust boundary,
    read-only/write policy, least privilege, tool allowlisting, human approval,
    untrusted-output/prompt-poisoning posture, failure degradation, auditability,
    and authority persistence rules;
12. seed `MCP-CANDIDATES.md` only with integrations tied to concrete needs;
    candidates may include Microsoft/.NET/Azure knowledge, GitHub, AWS/Azure
    platform access, or HITL/notification tooling, but none are mandatory;
13. do not recommend promotion/enablement of a skill or MCP candidate until its
    corresponding Fitness Review admission gate has been evaluated;
14. stop for Subhadeep to review and accept/reorder the backlog before case execution begins.

### Model

Use **GPT-5.6 Sol — High reasoning**.

`/arch-plan` also assigns each AR a risk class (`LOW | MEDIUM | HIGH | CRITICAL`) so later commands can route models without another human model-selection decision.

This is not the place to optimize aggressively for token cost because a poor review decomposition can omit the very risks the review exists to find.

## 2. `/arch-case <AR-ID>` — Analyse One Architecture Question

### Responsibility

Take one approved AR and determine the architectural answer as far as reasoning and repository evidence allow.

### Inputs

Normally load only:

- Architecture Fitness Review;
- active `AR-xxx` case;
- relevant current v0.2 design sections;
- relevant implementation files/evidence;
- relevant established practices;
- STATUS / FAILURE-RANKING only as needed.

Do not load broad chat history or the entire repository by default.

### Required Analysis

The command should:

1. restate the architectural question precisely;
2. inspect the current architecture/code;
3. identify the failure/invariant being protected;
4. compare relevant established industry approaches and, where useful,
   inspect concrete existing skills/framework implementations;
5. for each external implementation considered, distinguish:
   - the problem it solves;
   - its useful mechanism/principle;
   - its assumptions;
   - its fit/mismatch with SubhForge;
   - what to adapt versus what not to copy;
   - for any MCP/tool implementation considered, its trust source, exposed
     tools, credentials/permissions, read/write capability, untrusted-output
     posture, update model, failure behaviour, and authority boundary;
6. apply the SubhForge philosophy:
   **borrow the principle, not the enterprise machinery**;
7. identify viable options and trade-offs;
8. recommend the smallest robust option;
9. determine whether the remaining uncertainty is material enough to require a spike.

### Model

Use the risk class assigned by `/arch-plan`:

- `LOW` / `MEDIUM` → **GPT-5.6 Sol — Medium reasoning**;
- `HIGH` / `CRITICAL` → **GPT-5.6 Sol — High reasoning**.

If a LOW/MEDIUM case becomes materially cross-cutting or uncertain during analysis, promote the AR risk class and rerun/continue with Sol High rather than selecting a different model ad hoc.

Cheaper models may assist mechanical repository exploration, but they are not the architecture analyst.

## Skill Candidate Register

`design/architecture-review/SKILL-CANDIDATES.md` is the review-time home for
potential engineering skills and capability gaps.

It is a **candidate register, not an install list**. Nothing in it is available
to production SubhForge merely because it is listed.

Each candidate entry should record:

```text
Capability
What engineering capability are we trying to improve?

Need / Evidence
What current weakness, quality goal, failure mode or dogfood observation
justifies evaluating this capability?

Existing SubhForge Coverage
Which commands / agents / skills / deterministic tools already overlap?

Candidate Sources
Repository/path/version-or-commit/license for each credible option.

Useful Principle / Mechanism
What does the source do that appears valuable?

Assumptions / Mismatches
Authority, lifecycle, tracker, concurrency, persistence, tool, model/harness,
human-in-loop and context assumptions.

Right Mechanism?
SKILL | COMMAND | AGENT | DETERMINISTIC_TOOL_OR_MCP | PROJECT_RULE | NO_CHANGE

Context / Cost Impact
How and when is it loaded? What token/tool cost does it introduce?

Security / Permission Review
What can it read, write, execute or call externally?

Validation Plan
Focused test / spike / review case / dogfood use.

Decision
REJECT | WATCH | ADAPT | ADOPT_AS_IS

Promotion Evidence
Required before anything enters forge/skills/.

Provenance
Exact upstream source and local adaptation notes.
```

### Promotion rule

A candidate enters `forge/skills/` only after:

- the Architecture Fitness Review's **Skill Admission Gate** passes;
- any required focused validation/spike is complete;
- Subhadeep accepts the decision;
- a `SOURCE.md` records provenance and local adaptation;
- the skill is added to the curated skill README;
- relevant routing/context behaviour is tested;
- dogfooding validates high-impact skills where practical.

Prefer a **small global engineering core + on-demand technology skills +
project-local skills** over a large always-loaded global catalogue.

The register should be pruned: rejected candidates stay only when the reason is
useful to prevent repeated re-evaluation; otherwise remove noise.

## MCP Candidate Register

`design/architecture-review/MCP-CANDIDATES.md` is the review-time home for
MCP/external-tool candidates.

It is a **candidate register, not a connection list**. Listing a server does
not authorize SubhForge to install, connect to, authenticate against, or expose
its tools.

Each candidate entry should record:

```text
Capability / Need
What concrete SubhForge or project-delivery problem would this integration
solve?

Candidate Server / Source
Provider, repository/package/endpoint documentation, version/update model.

Server Class
KNOWLEDGE | REPOSITORY | CLOUD_PLATFORM | HITL_NOTIFICATION | OTHER

Why MCP / External Tool?
Why is this better than a skill, deterministic local code, normal CLI/API use,
or no new capability?

Required Tools
Exact tool/namespaces needed; everything else remains unavailable.

Environment Scope
LOCAL | DEV | TEST | STAGING | PROD, with PROD requiring explicit justification.

Permission / Credential Scope
Identity, resources, actions, read/write level, secret location/handling.

Security Review
Trust/source, prompt/tool poisoning, untrusted output, schema/update risk,
supply-chain risk, data exposure, destructive actions.

Authority Boundary
What returned information/actions may influence, and what can never become
authoritative without normal SubhForge persistence/decision rules?

Failure / Degradation
What happens when the server is unavailable, unauthorized, malformed, slow, or
returns suspicious content?

Context / Cost Impact
Tool-discovery size, latency, token implications, expected call frequency.

Validation Plan
Safe-path, denied-path, malformed/untrusted-output, permission and failure tests;
spike/dogfood evidence where needed.

Decision
REJECT | WATCH | READ_ONLY_PILOT | APPROVE_BOUNDED

Approved Boundary
Only when approved: exact server/version/config, tool allowlist, permissions,
environment and human-approval rules.

Re-review Trigger
Material server/tool/schema/version/permission/authentication change.
```

### MCP promotion / enablement rule

Before an MCP integration becomes part of normal SubhForge use:

- the Architecture Fitness Review's **Security-first MCP Admission Gate** must
  pass;
- the concrete use case and why MCP is the right mechanism must be recorded;
- exposed tools must be allowlisted;
- credentials must be least-privilege and environment-scoped;
- write/high-impact operations must have explicit human authorization rules;
- authoritative SubhForge truth must remain outside MCP;
- failure/degradation behaviour must be tested;
- any material upstream/server schema or permission change must have a defined
  re-review trigger;
- Subhadeep must explicitly accept the bounded integration.

Prefer a **small set of high-value MCP integrations** over broad connectivity.

## External Reference Discipline

External repositories and skill libraries are **evidence and design input**,
not authorities.

The review may inspect them directly to accelerate understanding, but it must
not silently import their workflow assumptions.

For reusable ideas:

- prefer primary sources: the skill itself, its repository documentation,
  official platform documentation, source code, and ADRs;
- record the upstream repository/path and commit or version when a specific
  external skill materially influences an AR decision;
- compare more than one credible approach when the decision is important and
  alternatives exist;
- do not create a popularity contest or copy the largest framework;
- distinguish a useful **engineering principle** from a source-specific
  **workflow mechanic**;
- preserve SubhForge's authority, reconciliation, bounded-context,
  deterministic-correctness, cost, and human-decision rules.

Matt Pocock's engineering skills are an initial high-value reference set
because several overlap directly with current SubhForge concerns. They are not
the default answer. The review should actively look for other credible options
where they could produce a better fit.

The desired outcome is faster architectural learning:

```text
SubhForge problem
      ↓
credible existing approaches
      ↓
understand why they work
      ↓
compare assumptions
      ↓
adapt / reject / spike
      ↓
SubhForge decision
```

## Spike Handoff Contract

If `/arch-case` concludes that a spike is required, the active AR file must contain a complete **Spike Contract** before `/arch-spike` is run.

DeepSeek should not have to rediscover what the architecture question means.

The Spike Contract must state:

```text
Spike Question
What exact uncertainty must this experiment resolve?

Hypothesis
What do we currently expect?

Why Reasoning Is Insufficient
What material uncertainty remains?

Relevant Current Behaviour
Which current SubhForge design/code assumption is being tested?

Experiment Scope
What is the smallest code probe/PoC required?

Allowed Work Area
poc/architecture-review/<AR-ID>/**

Inputs
Which interfaces/files/contracts may be inspected?

Non-Goals
What must the spike NOT attempt to design or implement?

Success Evidence
What observation would support the hypothesis?

Failure / Contradiction Evidence
What observation would invalidate or weaken it?

Required Outputs
- PoC/code
- focused test(s)
- commands run
- observed result
- limitations
- concise verdict

Production Mutation
Forbidden unless explicitly approved.
```

The Spike Contract is the handoff between architectural reasoning and economical experimental implementation.

## 3. `/arch-spike <AR-ID>` — Run a Pointed Architecture Experiment

### Responsibility

Execute the Spike Contract written by `/arch-case`.

The spike does **not** independently redefine the question and does not decide the architecture.

### Rules

- work only under `poc/architecture-review/<AR-ID>/`;
- perform the smallest experiment necessary;
- add/run focused tests;
- record commands and observations;
- record contradictory evidence honestly;
- do not modify production SubhForge code;
- do not broaden scope because an interesting adjacent idea appears;
- return evidence to the AR case.

### Model

Use **DeepSeek** by default.

The expensive reasoning has already happened in `/arch-case`. The spike's job is pointed implementation/testing, making it the appropriate place to optimize cost.

If DeepSeek cannot complete the bounded experiment reliably within the command's defined attempt limit, escalate to **GPT-5.6 Sol**. Do not use Claude for routine spike implementation, and do not silently spend Anthropic API budget.

## 4. `/arch-review <AR-ID>` — Independent Challenge and Decision Proposal

### Responsibility

Challenge the entire case whether or not a spike was required.

### Inputs

- original AR question;
- current design/code evidence;
- `/arch-case` analysis;
- Spike Contract and spike results when present;
- relevant industry practices;
- Architecture Fitness Review principles.

### Required Review

The reviewer should actively look for:

- unsupported assumptions;
- correlated model reasoning;
- missing failure modes;
- accidental overengineering;
- under-engineered safety boundaries;
- alternatives not considered;
- PoC limitations;
- conclusions that do not follow from the evidence;
- conflicts with other accepted AR decisions.

The reviewer then proposes:

- `KEEP`;
- `MODIFY`;
- `REMOVE`;
- `ADD`;
- or further investigation.

### Independence Rule

Prefer a **different strong model/model family from the one that performed `/arch-case`** where practical.

Example:

- case analysis: Sonnet → review: Sol High/Opus;
- case analysis: Sol → review: Sonnet/Opus.

This reduces the chance of one model simply validating its own earlier assumptions.

### Human Decision

The reviewer recommends. **Subhadeep decides.**

After Subhadeep explicitly accepts/rejects/redirects:

- record the accepted decision in the AR case;
- update `DECISION-LOG.md`;
- update `COVERAGE-MATRIX.md`;
- update `STATUS.md`;
- record validation required;
- record impact on the existing v0.2 design;
- mark the AR closed only when the decision is genuinely settled.

### Model

Use the risk class assigned by `/arch-plan`:

- `LOW` / `MEDIUM` → **Claude Sonnet via the tested Claude Code + Pro handoff**;
- `HIGH` / `CRITICAL` → **Claude Opus via the tested Claude Code + Pro handoff**.

Do **not** invoke the Anthropic API automatically.

If the Claude handoff is unavailable or quota-limited, surface that condition. GPT-5.6 Sol is the documented fallback reasoning path only when continuing without Claude is acceptable; otherwise wait for an explicit human decision.

Claude's result remains evidence/recommendation. Subhadeep remains the decision authority.

# 5. `/arch-synthesize` — One-Time Architecture Review Closure

This command runs **only after every required AR case is closed**.

It is the bridge between the Architecture Fitness Review and the new v0.2 design.

### Inputs

- Architecture Fitness Review;
- all closed AR cases;
- Decision Log;
- Coverage Matrix;
- current `V0.2-DESIGN-TRACKER.md`;
- current code where necessary to understand design impact;
- accepted spike evidence.

### Responsibility

Produce a coherent revised v0.2 architecture/design from the accepted review decisions.

The synthesis must:

1. preserve accepted AR decisions;
2. resolve how those decisions interact as a whole;
3. identify contradictions or gaps between accepted ARs;
4. compare the resulting architecture against the Fitness Review coverage matrix;
5. identify obsolete portions of the old v0.2 design;
6. produce the proposed revised v0.2 design/tracker;
7. preserve useful existing design decisions that survived the review;
8. avoid adding new architecture that was never justified by an AR.

### Contradiction Rule

`/arch-synthesize` may **not silently invent a new decision** to reconcile contradictory accepted ARs.

If synthesis discovers a material unresolved contradiction/gap:

- record a synthesis issue;
- stop;
- create/reopen the smallest necessary AR;
- resolve it through the normal review flow;
- resume synthesis afterward.

### Human Acceptance

Subhadeep reviews and accepts the synthesized v0.2 design.

Only after acceptance does it become the design authority for v0.2 implementation.

### Model

Use **GPT-5.6 Sol — High reasoning**.

The job is architectural integration, not mechanical Markdown generation. If synthesis exposes a material contradiction or unresolved gap, reopen/create the smallest necessary AR; do not switch models merely to force a conclusion.

# After Architecture Review Closure

Once `/arch-synthesize` produces an accepted revised v0.2 design:

        ↓

        ↓

The architecture-review workbench does not become the implementation workflow.

`stable_v0.1.1` remains the tool used to build v0.2.0 after the design is accepted.

## Decision Authority

Models:

- decompose;
- research;
- inspect;
- experiment;
- challenge;
- synthesize;
- recommend.

They do not silently make final architecture decisions.

```text
AI evidence + recommendation
          ↓
Subhadeep accepts / rejects / redirects
          ↓
accepted decision recorded in Git
```

Human judgement remains authoritative for genuine ambiguity and material architectural trade-offs.

## Bounded Context Rule

A review operation should load the minimum context needed for correctness.

### `/arch-plan`

May inspect broadly because its job is decomposition and coverage.

### Per-case commands

Should normally load only:

- Architecture Fitness Review;
- active AR case;
- relevant current design sections;
- relevant code/evidence;
- linked PoC;
- related accepted AR decisions when dependency exists.

Do not rely on long chat history.

The review process should itself dogfood the bounded-context principle being evaluated for v0.2.0.

---

## Spike Discipline

The Architecture Fitness Review expects only the highest-value uncertain questions to become spikes.

Target roughly **4–5 spikes**, not one PoC for every AR.

For each spike:

- answer one architectural uncertainty;
- prefer one working session maximum;
- isolate code under `poc/architecture-review/`;
- record evidence, not opinions;
- treat PoC code as disposable unless later promoted deliberately.

A spike is evidence. It is not automatically production architecture.

## Workbench Success Criteria

A normal case should look like:

```text
/arch-case AR-xxx
        ↓
spike needed?
   no        yes
   │          │
   │      /arch-spike AR-xxx
   │          │
   └──────┬───┘
          ↓
/arch-review AR-xxx
          ↓
Subhadeep decides
          ↓
AR closed and decision persisted
```

Planning and closure happen once:

```text
/arch-plan
   ↓
execute AR backlog
   ↓
all required ARs closed
   ↓
/arch-synthesize
   ↓
accepted revised v0.2 design
```

The workbench has failed if maintaining the review tooling itself becomes a meaningful project.

---

## Cleanup / Promotion After the Review

At the end of the Architecture Fitness Review, explicitly decide what happens to the workbench:

- retain review evidence and accepted decisions;
- retain commands only if they continue to provide value;
- promote only proven architectural concepts into SubhForge;
- remove disposable PoCs and review-only machinery that no longer provides value.

Nothing becomes permanent merely because it was useful during the review.
