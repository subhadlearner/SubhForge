# SubhForge v0.1 Lessons Learned

**Status:** Historical audit input for v0.2  
**Evidence cutoff:** frozen tag `research_v_0.1_h10` at `91109c041c508d96d6e1f948b6503db454cf1679`  
**Scope:** H01-H10, including H08b; not a v0.2 architecture or requirements document

## Executive conclusion

v0.1 proved that a durable, resumable AI-assisted delivery workflow is feasible. Its strongest mechanisms were repository-backed truth, deterministic enforcement of mechanical invariants, bounded model authority, fail-closed recovery, and explicit evidence freshness.

It also proved that verification infrastructure can become more complex and expensive than the workflow it is meant to protect. By H10, the deterministic suite had grown to 249 tests and 395.343 seconds on the reference Windows host, while the intended release target remained 180 seconds. The planned release-qualifying FULL smoke still had not run. Continuing through H11-H14 would have deepened investment in the harness without proportionate confidence in real project delivery.

The correct outcome was to freeze v0.1 as a research/prototype baseline, preserve its evidence, and carry only independently justified mechanisms into a clean v0.2 build.

## What worked

### Repository truth and disciplined execution

- Git-tracked state, evidence and decisions survived chat/session loss.
- One active hardening item, one bounded branch/PR, a fixed invariant and an explicit acceptance gate kept changes reviewable.
- Closing commits and test evidence made the hardening history reconstructable.
- Explicit user authorization before merge preserved human control over consequential changes.

This discipline should remain, but the ceremony should scale with risk rather than become uniform overhead.

### Deterministic mechanics, probabilistic judgment

The principle **deterministic infrastructure/mechanics, probabilistic agents** held up well.

Deterministic helpers were effective for:

- workspace provisioning and identity;
- schema and state-transition validation;
- fingerprints, manifests and evidence freshness;
- snapshot/restoration;
- clocks, ledgers and budget enforcement;
- negative-path scoring after a model made the actual judgment.

Models remained responsible for planning, implementation, verification judgment, review, rerouting and other semantic work. This avoided replacing real reasoning with smoke-specific lookup behavior.

### Isolation, failure containment and recovery

H01-H03 established important safety foundations:

- model-bearing work was rooted in a disposable repository rather than the SubhForge source checkout;
- source access and mutation were guarded mechanically;
- interrupted work gained explicit `ACTIVE -> COMPLETED | ABORTED | INTERRUPTED` semantics;
- restart-safe recovery revalidated the source fingerprint;
- malformed canonical state and invalid transitions failed closed instead of being silently repaired.

These are real product-quality lessons, not merely smoke-test details.

### Evidence identity and freshness

H04 demonstrated that passing checks and fresh evidence are different facts. A deterministic verification-time mutation allowed checks to pass while Contract-v1 identity became `MISMATCH`, correctly blocking delivery and making zero reviewer calls.

That separation—claim result, evidence identity, freshness and delivery eligibility—should remain central in v0.2.

### Bounded resume, rerouting and human waits

H05-H07 demonstrated useful patterns:

- resume and upstream rerouting can be evaluated from normal persisted evidence;
- expected answers can remain hidden from the reasoning agent;
- scored attempts can remain immutable while interrupted unscored attempts recover safely;
- human authorization wait time can be excluded only through an allow-listed, evidence-bound gate;
- bare waiting, retries, crashes and inactivity must not stop a cost/runtime clock.

These mechanisms are valuable when implemented once at the lifecycle boundary.

### Fail-closed path and repository identity

H09-H10 closed an important gap: path containment alone does not prove repository ownership. Mutating helpers must bind to the exact disposable repository, branch, run, baseline and Git administration context before acting.

This is a reusable security/safety rule for v0.2 tooling.

## What failed or cost too much

### The first smoke design did not test the real workspace topology

The initial design assumed that telling a child to operate in a sibling disposable path provided isolation. In reality, Kilo children inherited the parent project/worktree. H01 therefore had to redesign the handoff around an actually rooted disposable workspace.

**Lesson:** prove the real harness execution topology with a tiny integration probe before designing a large test matrix around it.

### Synthetic qualification grew faster than delivery confidence

H05-H08b expanded into many prepared states, snapshots, hidden scorers, ledgers, restoration rules, segments and model-bearing subprobes. H08b alone targeted a fixed 50/51-invocation specification.

This achieved strong local assertions, but it did not produce equivalent confidence that SubhForge could efficiently deliver a real multi-file project. H13's small integrated Kilo proof and H14's release-qualifying FULL run were never reached.

**Lesson:** synthetic fixtures should protect narrow invariants; real dogfood must provide the primary end-to-end confidence.

### Deterministic test cost became a product problem

Observed full-suite evidence shows the growth:

| Milestone | Full forge/scripts evidence |
|---|---:|
| H02 | 87 tests; runtime not recorded in the closure row |
| H03 | 105 tests; runtime not recorded in the closure row |
| H06 | 156 tests / 236.188s |
| H07 | 171 tests / 238.704s |
| H08 | 197 tests / 215.393s |
| H08b | 229 tests / 263.863s and 297.511s |
| H09 | 232 tests / 306.177s and 304.280s |
| H10 | 249 tests / 395.343s |

These rows are not a controlled same-host benchmark and must not be read as the marginal cost of each hardening item. In particular, H10's recorded same-host starting point was 359.448s and its final result was 395.343s—about 9.99% slower—not a roughly 30% H09-to-H10 regression. The defensible conclusion is that the growing suite repeatedly remained far above the intended 180-second release target.

The temporary 300-second budget received an accepted H08b-specific variance and explicit over-ceiling exceptions at H09 and H10. Those decisions avoided disproportionate tuning on the frozen prototype, but the repeated exceptions meant 300 seconds no longer functioned as a hard ceiling.

**Lesson:** test-runtime and model-call budgets must shape the design from the beginning. A green but slow feedback loop is not healthy, and a ceiling that repeatedly needs exceptions must trigger redesign, scope reduction or an explicit budget reset.

### The harness accumulated contracts that needed another harness

By H10, run-ID rules existed in multiple helpers and a new dry orchestration/contract validator was proposed as H11 to validate the smoke system itself. That was a clear complexity signal, although it does not by itself decide whether a smaller v0.2 validator is justified.

**Lesson:** use a single owner for each machine contract and stop when verification machinery requires a comparable verification subsystem of its own.

### Release confidence arrived too late

The plan deferred the smallest assembled real-Kilo integration proof to H13 and the final FULL qualification to H14. This allowed substantial deterministic hardening before the complete route was proven economically viable.

**Lesson:** establish a thin walking skeleton and one bounded real canary early, then deepen deterministic coverage around failures actually observed.

### Budget controls arrived after complexity accumulated

The tracker keeps the 30-minute FULL budget authoritative and H08/H08b expose a large 50/51-invocation qualification design, but no completed FULL run proves that the 30-minute limit was exceeded. The measured overrun is instead in the deterministic suite: it remained above the 180-second target and later crossed the temporary 300-second allowance. Batching Git work, reusable seeded fixtures and no-rerun rules reduced deterministic overhead only after the harness had already expanded.

**Lesson:** every live call and expensive fixture needs a named failure, an evidence owner, a retry limit and a cheaper reason why deterministic proof is insufficient. Budgets must be validated by measured evidence rather than inferred from design size.

## What v0.2 must preserve

1. **Durable authority:** Git/repository artifacts, not chat history, own accepted intent, state, evidence and next action.
2. **Human authority:** Subhadeep approves consequential decisions and merges; model findings remain advice/evidence.
3. **Deterministic boundaries:** schemas, identity, transitions, dependency mechanics, freshness, permissions and recovery are validated deterministically.
4. **Bounded model authority and context:** agents receive only the authority and tools required for the current work item.
5. **Fail-closed safety:** ambiguous identity, malformed state, stale evidence, failed restoration or unauthorized mutation blocks progress visibly.
6. **Resumability and diagnosis:** interrupted work records truthful state and an actionable next step without fabricating completion or elapsed time.
7. **Evidence freshness:** passed checks do not remain trusted after relevant claims or implementation identity change.
8. **Workspace/provider isolation:** construction harnesses and providers remain replaceable and cannot become product authority or runtime dependencies.
9. **One bounded change at a time:** narrow PRs, explicit acceptance gates and recorded closure evidence remain the default.
10. **Real cost observability:** runtime, model calls, retries and provider spend are engineering constraints, not after-the-fact accounting.

## What v0.2 must not repeat

- Do not design a large FULL matrix before proving the real end-to-end harness topology.
- Do not treat exhaustive live-model combinations as the primary assurance strategy.
- Do not use synthetic workflow fixtures as a substitute for real-project dogfood.
- Do not duplicate machine-significant contracts across helpers.
- Do not create broad deterministic machinery for semantic judgments that belong to bounded agents or humans.
- Do not postpone the walking skeleton, integrated canary or runtime measurement until late hardening.
- Do not accept growing test/runtime cost merely because individual additions are locally justified.
- Do not silently expand a bounded verification item into an H11-sized subsystem.
- Do not claim release qualification when final integration, dogfood or release gates did not run.
- Do not reuse v0.1 code merely because it exists; require current v0.2 architectural justification.

## Input to the v0.2 design audit

Checklist Item 5 should use these lessons as questions, not as pre-decided architecture:

- Does each proposed mechanism protect an accepted requirement and a credible failure?
- Is there one authoritative owner for each machine-significant contract?
- Can the walking skeleton and a real dogfood path run before broad hardening?
- Is each risk mapped to the cheapest sufficient evidence layer: deterministic test, focused integration, rare live canary, or dogfood?
- Are runtime, context, invocation, retry and provider-cost budgets explicit?
- Can temporary harness/scaffolding be removed without changing product semantics?
- Would removing a mechanism materially reduce correctness, recoverability or delivery confidence?

One known conflict requires explicit disposition in Item 5: this retrospective treats the proposed H11 dry orchestration/contract validator as a complexity signal, while [V0.2-QUALIFICATION.md](V0.2-QUALIFICATION.md) §24 rule 5 says dry orchestration/contract validation belongs below smoke. The audit must decide whether to keep a small single-owner validator, narrow or replace that rule, or remove the mechanism. The two positions must not remain unresolved.

If the answer is unclear, simplify, defer, or record a reversible assumption before adding machinery.
