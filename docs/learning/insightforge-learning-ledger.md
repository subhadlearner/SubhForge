### IF-L001 — Test critical invariants with adversarial counterexamples

- **InsightForge ticket / milestone:** [T6 — Writer, Fact-Checker and citation Passages (#7)](https://github.com/subhadlearner/insightforge-agent/issues/7); [merged PR #28](https://github.com/subhadlearner/insightforge-agent/pull/28).
- **Observation (verified):** The initial T6 implementation passed its reported 679 non-live tests, but independent source review found that the Writer's capitalised-word heuristic skipped sentence-initial words. Replacing the cited Evidence item's subject, `BYD`, with `Tesla` at the beginning of a Claim could therefore evade the named-entity check while preserving the same numbers. The focused correction added sentence-initial checks and regression cases; the owner subsequently ran 681 passing non-live tests, 31 passing T6 acceptance cases, 17 passing pipeline tests, and a clean import-linter check before merging.
- **Evidence:** [Pre-fix Writer at `64609d6`](https://github.com/subhadlearner/insightforge-agent/blob/64609d6443c56d5c34ca7f7cb1af1c444dd4464d/src/insightforge_agent/pipeline/write.py); [fix commit `dc5231f`](https://github.com/subhadlearner/insightforge-agent/commit/dc5231f5e95f4ca20ae164759d0e0114cb7ad782); [regression tests at the fixed commit](https://github.com/subhadlearner/insightforge-agent/blob/dc5231f5e95f4ca20ae164759d0e0114cb7ad782/tests/pipeline/test_t6_writer_fact_check.py). Test counts are from the owner's local verification log, not from an independently reproduced CI run.
- **Interpretation / root cause (hypothesis):** Existing positive and negative cases exercised the known validation rules but missed a simple adversarial subject substitution at a sentence boundary. High test counts alone did not demonstrate that the named-entity invariant held for that case.
- **Transferable lesson:** For important correctness and authorization invariants, pair normal acceptance tests with a few deliberate contract-breaking counterexamples. Reviewers should challenge *how* a rule can be bypassed, not only whether representative inputs pass.
- **Proposed SubhForge application:** Evaluate adding narrowly scoped, deterministic negative probes to existing qualification/smoke scenarios for high-impact contracts, such as unauthorized readiness transitions, invalid artifact/dependency references, or unsupported evidence claims. Do **not** introduce a blanket new test stage or expensive model calls on this evidence alone.
- **How to validate:** Select two or three existing high-risk SubhForge invariants; design one counterexample for each that resembles valid input while violating its contract. Confirm the probe fails before the relevant safeguard (or reliably rejects the injected violation), passes with the safeguard, and measure added runtime and false positives. Adopt only if the defects caught justify the ceremony/cost.
- **Decision status:** **Proposed learning recorded**; no SubhForge workflow, implementation or qualification change approved.
- **Related SubhForge decision:** None identified yet; any adoption requires its normal design/reconciliation and qualification gates.

### IF-L002 — Decompose epics into demonstrable vertical slices with early end-to-end evidence

- **InsightForge ticket / milestone:** [T12 — Diff Agent (#13)](https://github.com/subhadlearner/insightforge-agent/issues/13), [merged PR #53](https://github.com/subhadlearner/insightforge-agent/pull/53); subsequent [T14 UI (#15)](https://github.com/subhadlearner/insightforge-agent/issues/15), [T15 dashboard/export/share (#16)](https://github.com/subhadlearner/insightforge-agent/issues/16), [T18 provider verification (#19)](https://github.com/subhadlearner/insightforge-agent/issues/19) and [T20 final hardening (#49)](https://github.com/subhadlearner/insightforge-agent/issues/49).
- **Observation (verified from issue/PR scopes):** InsightForge's completed backend T12 delivered persisted Findings, Diffs and Alerts and passed reported offline tests, while the user-facing Diff/Alert UI is assigned separately to later T15, which itself depends on T14. Full Anthropic/provider verification and demo acceptance are also later tasks. Thus, closing T12 proved an important backend contract but did **not** yet prove the complete user journey from Watchlist creation to visible Diff/Alert through the UI. The owner recognized this delayed integration confidence before T13 started. The T12 test totals are implementer-reported, not independently rerun here.
- **Evidence:** [T12 issue and its eight acceptance criteria](https://github.com/subhadlearner/insightforge-agent/issues/13); [merged PR #53 with regression/verification evidence](https://github.com/subhadlearner/insightforge-agent/pull/53); [T14 UI scope](https://github.com/subhadlearner/insightforge-agent/issues/15); [T15 UI and endpoints scope/dependencies](https://github.com/subhadlearner/insightforge-agent/issues/16); [T18 final Anthropic verification dependencies](https://github.com/subhadlearner/insightforge-agent/issues/19); [T20 pre-submission end-to-end audit](https://github.com/subhadlearner/insightforge-agent/issues/49).
- **Interpretation / root cause (hypothesis):** Work was decomposed substantially along architectural subsystems (backend pipelines, scheduler, Diff, then UI), making a large integration boundary remain unexercised until late. Component-first tickets are not inherently wrong, but without explicit end-to-end acceptance checkpoints they postpone evidence about interfaces, deployment, real user behavior and integration defects. A passing ticket-level test suite cannot substitute for a complete user journey.
- **Transferable lesson:** During Project → Epic → Feature → Spec decomposition, prefer **thin vertical slices** that cross the relevant UI/API/domain/persistence boundaries and produce a visible, testable user outcome. Plan prerequisite infrastructure as enabling work, but ensure each user-facing Epic has an early walking-skeleton slice and explicit integrated acceptance evidence. Do not equate “Epic complete” with “all layers individually implemented.”
- **Proposed SubhForge application:** Evaluate a decomposition/readiness check requiring each user-facing Epic to identify (a) a demonstrable end-to-end journey and success criterion, (b) the earliest small vertical Feature that exercises it, (c) necessary cross-layer contracts/dependencies, and (d) a verification/qualification path with UI + backend + persistence where applicable. Epic completion should require evidence that the integrated journey works in a local/test environment, not merely Spec/Feature unit tests. Explicitly permit justified backend-only or infrastructure Epics and non-UI projects, but require an equally appropriate consumer-facing integration contract/test. Avoid making every Spec unnecessarily full-stack or demanding production deployment.
- **How to validate:** In a SubhForge dogfood decomposition (e.g. the planned VidyaBeacon School Companion), create two candidate Epics: one subsystem-first and one with an initial thin UI→API→storage workflow. Compare time to first demonstrable outcome, interface defects discovered before Epic completion, integration rework, test-runtime/provider cost and human coordination. Run the existing Spec/Feature/Epic verification mechanisms against the chosen decomposition; adopt any new readiness gate only if the evidence supports its value and the low-ceremony constraint.
- **Decision status:** **Proposed learning recorded**; no SubhForge PRD, architecture, workflow or qualification change approved.
- **Related SubhForge decision:** Assess during decomposition/readiness and verification design/reconciliation; account for existing v0.2 PRD lifecycle wording about local/test environments and Epic verification. Do not bypass authority or introduce a new universal gate without owner acceptance.

### IF-L003 — Re-verify the repair neighborhood, not only the original review finding

- **InsightForge ticket / milestone:** [T14 — Next.js UI (#15)](https://github.com/subhadlearner/insightforge-agent/issues/15); [merged PR #56](https://github.com/subhadlearner/insightforge-agent/pull/56), especially repair commits [`1f8eab7`](https://github.com/subhadlearner/insightforge-agent/commit/1f8eab7a3f851878b2d7db8b54957cd2cfe9772c) and [`7c32474`](https://github.com/subhadlearner/insightforge-agent/commit/7c3247419d54f35a041efeb0d688240721a6fc29).
- **Observation (verified):** Independent review of T14 found that attached PDFs could be silently ignored when the Documents source was off. Commit `1f8eab7` correctly forced Documents on while a PDF was attached, but the first repair represented the forced value inside the same displayed toggle object passed back to form state. If the User changed Web or Earlier Reports while a PDF was attached, the displayed `documents: true` value was copied into the stored choice; after the PDF was removed, Documents incorrectly stayed on. A follow-up review identified that second-order regression. Commit `7c32474` changed the toggle component to report only the source actually changed, keeping the forced Documents value derived rather than persisted, and added regressions for both original Documents-off and Documents-on choices. The owner reported 88 passing frontend tests, 13/13 Playwright scenarios, clean typecheck and a passing production build after the final repair.
- **Evidence:** [T14 PR #56](https://github.com/subhadlearner/insightforge-agent/pull/56); [`source-toggles.tsx` at the first repair](https://github.com/subhadlearner/insightforge-agent/blob/1f8eab7a3f851878b2d7db8b54957cd2cfe9772c/web/components/source-toggles.tsx); [`brief-form.tsx` at the first repair](https://github.com/subhadlearner/insightforge-agent/blob/1f8eab7a3f851878b2d7db8b54957cd2cfe9772c/web/components/brief-form.tsx); [final repair](https://github.com/subhadlearner/insightforge-agent/commit/7c3247419d54f35a041efeb0d688240721a6fc29); [final regression tests](https://github.com/subhadlearner/insightforge-agent/blob/7c3247419d54f35a041efeb0d688240721a6fc29/web/tests/persona-boundary.test.tsx). Test counts are owner-reported, not independently rerun here.
- **Interpretation / root cause (hypothesis):** The first repair was locally correct for the reported symptom but changed the relationship between **stored User choice** and **derived effective state**. Verification focused on attach/remove behavior, not on neighboring interactions while the derived override was active. This is a general repair-loop risk: a plausible fix can satisfy the original failing example while violating an adjacent invariant.
- **Transferable lesson:** After a review-driven fix, verification should prove both **finding closure** and **non-regression across the smallest affected contract neighborhood**. In particular, when a fix changes state ownership, authority, caching, retry, derived values or lifecycle transitions, test one or two adjacent interactions that could accidentally persist, bypass or stale that state. “The original review comment is fixed” is weaker evidence than “the governing invariant still holds around the repair.”
- **Proposed SubhForge application:** Evaluate strengthening the existing Builder → Verifier → Reviewer repair loop so a REWORK/fix handoff carries the affected invariant/contract and the smallest adjacent regression surface. Verifier should re-run the proving test for the original finding plus targeted regression evidence for materially touched boundaries; Reviewer should judge that evidence rather than only reread the changed line. Reuse the existing fix/verify/review lifecycle and evidence-freshness semantics; do **not** add a new universal stage or require broad full-suite reruns for every small correction.
- **How to validate:** During a SubhForge dogfood, inject or encounter a defect whose obvious repair changes a state/authority boundary. Create one repair that closes the original failing case but introduces an adjacent regression, then evaluate whether the current fix → verify → review flow catches it before acceptance. Compare defect-detection value, extra test/runtime cost and reviewer ceremony. Adopt a narrower repair-neighborhood rule only if it catches meaningful regressions at acceptable cost.
- **Decision status:** **Proposed learning recorded**; no SubhForge workflow, implementation or qualification change approved.
- **Related SubhForge decision:** Assess against existing repair, verification, review and evidence-freshness contracts during v0.2 design/reconciliation or dogfood qualification. Prefer an incremental rule/evidence refinement over a new lifecycle mechanism.

### IF-L004 — Classify limitations before turning them into backlog obligations

- **InsightForge ticket / milestone:** [T14 — Next.js UI (#15)](https://github.com/subhadlearner/insightforge-agent/issues/15); [merged PR #56](https://github.com/subhadlearner/insightforge-agent/pull/56); [T15 (#16)](https://github.com/subhadlearner/insightforge-agent/issues/16); [T20 final hardening (#49)](https://github.com/subhadlearner/insightforge-agent/issues/49).
- **Observation (verified):** PR #56 closed all six T14 acceptance criteria while documenting five deliberate limitations/boundaries. They were not treated uniformly as unfinished work. T15 functionality remained owned by T15 rather than being duplicated; live runtime-estimate refinement remained an uncommitted enhancement because T14 required only a pre-submit estimate; localhost-only `next dev` behavior remained an accepted local-development constraint. Two residual risks were deliberately carried into T20: a real browser PDF end-to-end path for final integration evidence, and the duplicated frontend/backend “no defaults → web only” rule for later consistency review. T20 itself explicitly says it is a selective pre-submission hardening pass, not an obligation to implement every improvement. T14 was then closed with all acceptance checkboxes complete.
- **Evidence:** [closed T14 issue #15](https://github.com/subhadlearner/insightforge-agent/issues/15); [merged PR #56 and its Deliberate limitations](https://github.com/subhadlearner/insightforge-agent/pull/56); [T15 ownership in issue #16](https://github.com/subhadlearner/insightforge-agent/issues/16); [T20 purpose/principles and T14 deferred observations](https://github.com/subhadlearner/insightforge-agent/issues/49).
- **Interpretation / root cause (hypothesis):** Review and implementation naturally surface more observations than a delivery ticket should own. If every limitation, nice-to-have or architectural possibility becomes mandatory follow-up work, review creates backlog inflation, obscures real acceptance defects and increases token/runtime/human cost. Conversely, discarding every non-blocking observation loses useful risk and learning. The useful control point is **disposition**, not automatic implementation.
- **Transferable lesson:** Before converting a review observation into work, distinguish at least conceptually between: **acceptance blocker/correctness defect**, **already-owned later scope**, **accepted operating/scope boundary**, **evidence-backed hardening candidate**, and **optional enhancement**. Only create or carry an obligation when its owner, reason and expected value are clear. A known limitation can be complete-for-now without being forgotten.
- **Proposed SubhForge application:** Evaluate whether Reviewer/reconciliation outputs should require an explicit disposition for non-blocking findings before creating downstream obligations. The mechanism should reuse existing authority, issue/work-item and human-decision semantics rather than inventing a parallel backlog. It should support the owner's cost/value judgement: preserve evidence and rationale, but avoid converting “could be better” into mandatory implementation. This is especially relevant to final hardening, dogfood findings and architecture-review observations.
- **How to validate:** During SubhForge dogfooding, take a real review containing a mixed set of defects, later-scope items, accepted boundaries and improvements. Apply the existing workflow with an explicit disposition pass and compare it with treating every finding as work: measure missed blockers, unnecessary follow-up items, human decision load, token/runtime cost and whether valuable observations remain traceable. Adopt only the minimum classification/recording needed to improve those outcomes.
- **Decision status:** **Proposed learning recorded**; no new status vocabulary, workflow transition or backlog mechanism approved.
- **Related SubhForge decision:** Assess during Reviewer/reconciliation and qualification design. Preserve the existing principle that low-value ceremony and speculative scope are not justified merely because a reviewer can imagine an improvement.


### IF-L005 — Preserve domain meaning across API, UI, export and public projections

- **InsightForge ticket / milestone:** [T15 — Watchlist dashboard, Diff view, alerts, export, PDF and share links (#16)](https://github.com/subhadlearner/insightforge-agent/issues/16); final independently approved PR [#57](https://github.com/subhadlearner/insightforge-agent/pull/57) at reviewed head `5f30031caba324869efb948e2019a3de6fbaf83f` (merge/issue closure pending when this learning PR was prepared).
- **Observation (verified):** T15 repeatedly exposed defects where persisted domain state was technically present but its meaning was weakened or distorted at a projection boundary. Examples included dropping Finding polarity in Dashboard/Diff/Alerts, labelling every incoming Diff Finding as "Current" even for `older_ignored` and `ambiguous`, losing Historical Claim context in Markdown, over-applying Alert wording ("Change detected on") to generic Diff provenance, and initially exposing an unrestricted private fact-check summary through the public share DTO. Independent review forced each projection to preserve the authoritative T12/T14 semantics: polarity became explicit, Diff uses "Previously established" / "This Run", Historical markers survive export, Diff and Alert temporal wording remain distinct, and the public DTO became an explicit allow-list.
- **Evidence:** [PR #57](https://github.com/subhadlearner/insightforge-agent/pull/57); [Diff presentation at final reviewed head](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/web/components/watchlist-diff-view.tsx); [Alert presentation](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/web/components/alerts-view.tsx); [Report delivery/public projection](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/src/insightforge_agent/pipeline/report_delivery.py); [T15 UI regressions](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/web/tests/t15-ui.test.tsx).
- **Interpretation / root cause (hypothesis):** Cross-layer work tends to treat projection code as "just presentation," but a projection can silently change semantics by omitting a qualifier, using a stronger label, collapsing two states, or forwarding an internal structure wholesale. These defects can survive strong domain tests because the authoritative model itself remains correct; the corruption happens while translating that model for another audience.
- **Transferable lesson:** Treat API/UI/export/public-share projections as **semantic contracts**, not passive formatting. For each high-value domain invariant, identify the minimum meaning that must survive every projection (for example polarity, authority/currentness, provenance, confidence/verification state, temporal uncertainty and privacy classification), and test that each consumer preserves it without adding stronger claims.
- **Proposed SubhForge application:** During Spec/Feature design and verification, evaluate a lightweight "projection contract" check for artifacts that cross boundaries such as internal model → API → UI, authoritative artifact → generated summary, or private evidence → public/reviewer view. The check should name only material semantics that must survive and data that must be intentionally omitted. Reuse existing verification/review evidence rather than adding a new lifecycle stage.
- **How to validate:** In a SubhForge dogfood, choose one feature with an authoritative model exposed through two or more projections. Seed cases that differ only in a meaning-bearing field (e.g. accepted vs stale authority, affirmed vs negated state, current vs historical evidence). Verify each projection remains distinguishable and does not leak hidden/internal fields. Compare defects caught and ceremony added before adopting any general rule.
- **Decision status:** **Proposed learning recorded**; no SubhForge workflow, schema, PRD or qualification change approved.
- **Related SubhForge decision:** Assess within existing artifact contracts, verification/review and evidence-freshness design. Prefer explicit projection expectations on the relevant Spec over a universal framework.

### IF-L006 — A durable capability needs a durable management path, not only durable storage

- **InsightForge ticket / milestone:** [T15 — Watchlist dashboard, Diff view, alerts, export, PDF and share links (#16)](https://github.com/subhadlearner/insightforge-agent/issues/16); final independently approved PR [#57](https://github.com/subhadlearner/insightforge-agent/pull/57) at reviewed head `5f30031caba324869efb948e2019a3de6fbaf83f` (merge/issue closure pending when this learning PR was prepared).
- **Observation (verified):** T15 initially satisfied revocation at the storage/API level: share records were durable, independently revocable and survived restart. But the UI kept the only usable `share_id` in React state. After the owner created a link and reloaded or revisited the Report, the durable public capability could remain valid for seven days while the owner had no normal UI path to rediscover and revoke it. The final repair added owner-scoped active-share listing from the same durable records; the Report UI reloads active shares, supports multiple independent links, and can revoke a link after navigation/restart. Browser regression now proves create → public access → private reload → rediscovery → revoke → public refusal.
- **Evidence:** [PR #57](https://github.com/subhadlearner/insightforge-agent/pull/57); [share repository](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/src/insightforge_agent/stores/shares.py); [delivery/share endpoints](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/src/insightforge_agent/api/delivery.py); [Report share actions](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/web/components/report-actions.tsx); [T15 browser acceptance](https://github.com/subhadlearner/insightforge-agent/blob/5f30031caba324869efb948e2019a3de6fbaf83f/web/e2e/t15.spec.ts).
- **Interpretation / root cause (hypothesis):** The implementation proved persistence and mutation independently but initially omitted the lifecycle path needed to regain control after ephemeral client state disappears. For long-lived capabilities, jobs, leases, approvals or external effects, "the record survives restart" is insufficient if the actor cannot later discover or manage the surviving obligation/capability.
- **Transferable lesson:** Whenever a system creates a durable capability or obligation that remains meaningful after the creating interaction ends, verify the full **manage-after-restart lifecycle**: durable identity, rediscovery/listing, current status, safe mutation/revocation/cancellation, and independent handling of multiple instances. Durability should include durable **control reachability**, not only durable bytes.
- **Proposed SubhForge application:** Evaluate adding this question to design/review of persistent workflow state: "If the initiating session/context disappears, how does the authorized actor rediscover and manage the surviving item?" Apply selectively to things such as pending human decisions, interrupted workflow obligations, resumable handoffs, waivers or external side effects. Do not force CRUD/history UI for every persisted record; require only the management path justified by the contract.
- **How to validate:** During SubhForge dogfood, pick one durable lifecycle object (for example an interrupted stage or HUMAN_DECISION_REQUIRED obligation). Create it, discard the original execution/session context, restart/reopen, then prove the correct actor can rediscover and resolve/cancel/reconcile it without duplicate creation or hidden stale state. Measure whether this catches a real failure mode before adopting a broader design check.
- **Decision status:** **Proposed learning recorded**; no SubhForge workflow, UI, storage or lifecycle change approved.
- **Related SubhForge decision:** Assess against existing interruption recovery, obligation tracking and authority contracts during v0.2 dogfood/reconciliation. Reuse current status/ownership mechanisms rather than introducing a parallel management subsystem.

### IF-L007 — Evaluation fixtures must represent the capability the test claims to prove

- **InsightForge ticket / milestone:** [T16 — Sample brief library and evaluation (#17)](https://github.com/subhadlearner/insightforge-agent/issues/17); [merged PR #58](https://github.com/subhadlearner/insightforge-agent/pull/58), domain-coverage commit [`49af97a`](https://github.com/subhadlearner/insightforge-agent/commit/49af97ae1736cffb9886196058b8f3e33e6f4e2c).
- **Observation (verified):** The initial T16 offline end-to-end world ran five differently named Briefs, but scripted cloud, semiconductor and solar research—and the medical-device document Brief's web comparison—used EV-oriented search queries and pages. The pipeline could COMPLETE and report favorable metrics on unrelated material. The final T16 repair supplied 13 clearly fictional, domain-specific recorded pages, corresponding scripted plans, Northwind document text and subject-neutral extraction/summary fakes. Seven new parametrized/negative checks failed against the earlier fixture setup and passed with the fix; they inspect persisted Sub-tasks, Sources, extracted entities, Evidence headings, Run summaries and Claim-to-Passage citations. Negative substitutions prove that an apparently successful Run can still fail subject/provenance assertions. No production code changed in that repair.
- **Evidence:** [Pre-repair scripted world at `967f73b`](https://github.com/subhadlearner/insightforge-agent/blob/967f73bbef523155483f1441137b5b6ca637c2ae/tests/evaluation/world.py); [domain-specific world at `49af97a`](https://github.com/subhadlearner/insightforge-agent/blob/49af97ae1736cffb9886196058b8f3e33e6f4e2c/tests/evaluation/world.py); [recorded domain Sources](https://github.com/subhadlearner/insightforge-agent/blob/49af97ae1736cffb9886196058b8f3e33e6f4e2c/tests/fixtures/search/eval_domains.json); [domain and negative tests](https://github.com/subhadlearner/insightforge-agent/blob/49af97ae1736cffb9886196058b8f3e33e6f4e2c/tests/evaluation/test_eval_cli.py); [merged PR #58](https://github.com/subhadlearner/insightforge-agent/pull/58). GitHub CI at this head passed the offline test tiers (1,887 tests total) and import contracts; the 19 integration tests were reported as passing locally by the implementer, but were skipped in that CI environment.
- **Interpretation / root cause (hypothesis):** Scripted end-to-end tests can overstate capability if their fixtures exercise a mechanically valid workflow but not the task's meaningful content. Distinct scenario labels and green orchestration scores do not demonstrate that source selection, subject scope and downstream evidence are relevant. Conversely, subject-specific scripted checks establish observable fidelity, **not** that a real model reasons correctly.
- **Transferable lesson:** A qualification case should declare not only its expected state transition but also the **relevance of the evidence trace to the scenario**. For capability claims, check that accepted inputs, tool results, authority/context references and produced artifacts actually correspond to the task being qualified. Use a small deliberately off-scope or swapped-evidence negative control where relevant. Distinguish deterministic trace fidelity from real-agent semantic quality.
- **Proposed SubhForge application:** During DI-013 qualification and existing smoke/dogfood design, inspect one or two agent-facing scenarios (for example Project/Epic/Feature decomposition or a Builder → Verifier → Reviewer handoff) for misleading fixture reuse. Check that the final authoritative artifacts and relevant tool/action records concern the actual requested scope and accepted authority—not a generic unrelated project that merely passes mechanical lifecycle checks. Reuse Qualification §24.11's outcome-based grading and negative-canary approach; **do not** add another test tier, universal industry matrix, expensive judge or new lifecycle gate.
- **How to validate:** In an existing small qualification scenario, deliberately substitute another Spec's research/context/evidence while preserving syntactic validity. Demonstrate that the existing or narrowly augmented deterministic checks reject the irrelevant trace even if the model/script reaches a nominally successful state. Confirm a corresponding valid scenario passes. Record what still requires real-agent dogfood, plus incremental runtime/cost/false-positive burden; adopt only if the added assertion catches a material blind spot.
- **Decision status:** **Proposed learning recorded**; no SubhForge qualification, workflow, PRD, schema or implementation change approved.
- **Related SubhForge decision:** Evaluate within accepted Qualification §24.11 and DI-013's scenario/rubric freeze; do not silently add a new acceptance rule.

### IF-L008 — Qualification results need defined denominators, complete scope and comparable conditions

- **InsightForge ticket / milestone:** [T16 (#17)](https://github.com/subhadlearner/insightforge-agent/issues/17); [merged PR #58](https://github.com/subhadlearner/insightforge-agent/pull/58), correctness fix [`967f73b`](https://github.com/subhadlearner/insightforge-agent/commit/967f73bbef523155483f1441137b5b6ca637c2ae).
- **Observation (verified):** T16 review uncovered several misleading evaluation outcomes despite otherwise green tests. A pooled Anthropic fact-check result below the 80% remediation threshold could report `required` before verifying all five Briefs had a usable measurement; the reverse case could say `not_required` when one completed Brief checked no Claims. Provider comparability could read `true` for an all-`unchecked` metric (an undefined pass rate), and the comparison initially omitted material Evidence thresholds and runtime services. Corrective tests established the counterexamples before fixes. The final evaluator requires an actual nonzero metric denominator per Brief, reports incomplete Anthropic remediation as `undetermined`, and compares only metrics measured on the same Briefs under equivalent recorded conditions/services. Fact-check verdicts are additionally checked for unique, matching draft Claim coordinates and Evidence IDs.
- **Evidence:** [T16 deterministic metric validation](https://github.com/subhadlearner/insightforge-agent/blob/967f73bbef523155483f1441137b5b6ca637c2ae/src/insightforge_agent/evaluation/metrics.py); [remediation and comparability logic](https://github.com/subhadlearner/insightforge-agent/blob/967f73bbef523155483f1441137b5b6ca637c2ae/src/insightforge_agent/evaluation/report.py); [comparator regression cases](https://github.com/subhadlearner/insightforge-agent/blob/967f73bbef523155483f1441137b5b6ca637c2ae/tests/evaluation/test_comparability.py); [80% threshold cases](https://github.com/subhadlearner/insightforge-agent/blob/967f73bbef523155483f1441137b5b6ca637c2ae/tests/evaluation/test_remediation.py); [effective condition recording](https://github.com/subhadlearner/insightforge-agent/blob/967f73bbef523155483f1441137b5b6ca637c2ae/src/insightforge_agent/evaluation/cli.py).
- **Interpretation / root cause (hypothesis):** A plausible aggregate value hides its limitations unless the system carries **coverage, denominator and execution comparability** into the decision. `0`, `unmeasured`, `incomplete` and `not comparable` are not interchangeable.
